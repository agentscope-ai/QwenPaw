# 心跳

「心跳」在 QwenPaw 里指的是：**按固定间隔，用你写好的一段「问题」去问 QwenPaw，并可选择把 QwenPaw 的回复发到你上次对话的频道**。适合做「定期自检、每日摘要、定时提醒」——不用你主动发消息，QwenPaw 到点就干活。

多智能体模式下，**每个智能体**各自有一份 **HEARTBEAT.md** 和 **heartbeat** 配置（在该智能体的 workspace 目录里）。在 [控制台](./console) 里也可以打开或关闭心跳、改间隔等（**控制 → 心跳**）。

如果你还没看过 [项目介绍](./intro)，建议先看一眼那里对「心跳」和「频道」的说明。

---

## 心跳是怎么工作的？

1. 在当前智能体的 workspace 里有一个**心跳查询文件**（默认文件名为 **HEARTBEAT.md**，可用环境变量 `QWENPAW_HEARTBEAT_FILE` 改名）。里面写的是**每次心跳要问 QwenPaw 的内容**（一段或几段话都行，QwenPaw 会当成一条用户消息）。
2. 当配置里 **`enabled` 为 true** 时，系统按你配置的 **every**（间隔字符串或五段 Cron）执行一次：读取该文件 → 用这段内容去问 QwenPaw → QwenPaw 回复。
3. **发不发到频道** 由配置里的 **target** 决定：
   - **main**：只跑 QwenPaw，不把回复发到任何频道（适合只做「自检」、结果自己看日志或别处）。
   - **last**：把 QwenPaw 的回复发到你**上次和 QwenPaw 对话的那个频道/会话**（例如上次你在钉钉和它聊，这次心跳的回复就发到钉钉）。

还可以设置 **active hours**（活跃时段）：只在每天的某段时间内跑心跳（例如 08:00–22:00），其余时间不跑。

---

## 第一步：写 HEARTBEAT.md

**路径（多智能体，常见情况）**：`<QWENPAW_WORKING_DIR>/workspaces/<agent_id>/HEARTBEAT.md`。
`<QWENPAW_WORKING_DIR>` 默认是 `~/.qwenpaw`，也可用环境变量 `QWENPAW_WORKING_DIR` 覆盖；`<agent_id>` 与当前智能体一致（例如 `default`）。

文件名默认 `HEARTBEAT.md`，可通过 **`QWENPAW_HEARTBEAT_FILE`** 改成别的名字；路径始终是「该智能体 workspace 根目录 + 该文件名」。

内容就是「每次要问 QwenPaw 什么」，纯文本或 Markdown 都行，QwenPaw 会整体当作一条用户消息。

示例（你可以按自己需求改）：

```markdown
# Heartbeat checklist

- 扫描收件箱紧急邮件
- 查看未来 2h 的日历
- 检查待办是否卡住
- 若安静超过 8h，轻量 check-in
```

初始化时如果执行过 `qwenpaw init`（没加 `--defaults`），会提示你是否编辑 HEARTBEAT.md；选是会用系统默认编辑器打开。你也可以之后随时用任何编辑器改这个文件，保存即可，下次心跳会用到新内容。

## 第二步：配置心跳

![heartbeat](https://img.alicdn.com/imgextra/i2/O1CN0197MAPx2002prwqU5N_!!6000000006786-2-tps-3822-2070.png)

推荐在 console 的 **心跳**页面进行配置。如果想通过修改agent.json实现，参考以下内容。

**间隔、开关、发到哪、执行超时、活跃时段** 读自当前智能体的 **`workspaces/<agent_id>/agent.json`** 里的 **`heartbeat`** 字段（与控制台保存的配置一致）。
从旧版迁移时，历史上写在根目录 **`config.json`** 的 `agents.defaults.heartbeat` 会合并进默认智能体的 `agent.json`；新配置请以 **`agent.json` 为准**。

| 字段               | 含义                                                                                                                                                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **enabled**        | 是否开启心跳。**默认 false**；只有为 **true** 时才会按计划执行。                                                                                                                                                      |
| **every**          | 多久跑一次：间隔字符串（如 `"30m"`、`"1h"`、`"2h30m"`、`"90s"`），**或** 空格分隔的 **五段 Cron**（分 时 日 月 周几，与定时任务相同的五段写法，例如每天 9:00：`"0 9 * * *"`）。使用 Cron 时由进程内调度器的时区解析。 |
| **target**         | **main** 不发送到频道；**last** 发到该智能体 `state/last_dispatch.json` 运行状态记录的频道；**inbox** 发送到收件箱中。                                                                                                |
| **timeoutSeconds** | 单次心跳执行的最长时间，单位秒。**默认 300**，有效范围 **1–3600**。                                                                                                                                                   |
| **activeHours**    | 可选，只在每天这段时间内跑：`{ "start": "08:00", "end": "22:00" }`。                                                                                                                                                  |

`every` 未写时的默认间隔以程序内置为准（当前默认约为 **6 小时**，仍以你环境里的版本为准）。若 `every` 写了但为空、无法解析或不大于 0，则回退到 **30 分钟**（无法解析的情况还会打一条 warning）。

示例（开启心跳，只跑 QwenPaw、不发到频道，每 30 分钟）——写在对应智能体的 **`agent.json`** 中：

```json
{
  "heartbeat": {
    "enabled": true,
    "every": "30m",
    "target": "main"
  }
}
```

示例（发到上次对话的频道，每 1 小时，且只在 08:00–22:00 跑）：

```json
{
  "heartbeat": {
    "enabled": true,
    "every": "1h",
    "target": "last",
    "timeoutSeconds": 300,
    "activeHours": { "start": "08:00", "end": "22:00" }
  }
}
```

改完保存 `agent.json` 即可：服务在跑时会原地生效，无需重启（详见下方「运行语义」）。

## 运行语义

以下行为由心跳的实现方式决定，而不是由上面的字段决定，也是用户最容易踩到的部分。

### 「无事可报」不会被过滤

- **main**（默认）：照常执行，但结果**永不投递**——「安静」只是不发送的副作用；这一轮仍会写入该智能体的 `main` 会话历史。
- **last**：这一轮的每个事件都会推到你上次对话的频道/会话，所以「无事就别出声」要靠模型自己判断——请在 HEARTBEAT.md 里写明。
- **inbox**：不推送到频道，只往收件箱写一条记录——成功写 `heartbeat_result`，超时写 `heartbeat_timeout`，失败写 `heartbeat_error`。

当前时间不在 `activeHours` 内、心跳文件不存在或文件为空时，这一 tick 会被**静默跳过**（只有 debug 日志，不给频道发任何消息）。`target: "last"` 但没有可用的上次投递目标（从未记录，或记录里缺少频道 / user / session）时，同样退化为「只跑不投递」。

### 运行重叠

心跳任务自身没有设置并发上限，因此沿用调度器默认值：上一次 tick 还在执行时又到点的 tick 会被**跳过而不是排队**（任务使用 APScheduler 默认的 `max_instances=1`；`misfire_grace_time` 为 60 秒，只决定一次到点最多允许迟多久执行）。心跳不走频道队列，也不占用定时任务那种按任务计的并发额度，并且始终跑在该智能体的 `main` 会话上。如果同一会话上已有另一轮在跑（例如控制台请求显式指定了同一个 session id），两轮会**并发执行**；两者都会保存会话状态，后写的那次会覆盖先写的。

### 智能体不会回复自己的消息

不少内置频道会在消息处理器开头丢弃「发送者就是智能体自己账号」的事件——Matrix 会比较事件发送者与智能体自己的 user id，DingTalk 会跳过带 `is_bot` 标记的消息，Mattermost 会比较发送者与 bot id；并非每个频道都实现了这一点。这一丢弃正是防止「心跳 → 回复 → 房间回声」形成循环的机制；它是各频道各自的约定，不是心跳配置项。

### HEARTBEAT.md 与 AGENTS.md 心跳段是两回事

- **HEARTBEAT.md** 每次 tick 都会读取：整份文件（去掉首尾空白）作为**一条 user 消息**发到 `main` 会话。该轮会打上「来自心跳」的标记，因此智能体会跳过自动记忆检索。
- **`AGENTS.md` 里的心跳段**（`<!-- heartbeat:start -->` 到 `<!-- heartbeat:end -->` 之间）属于系统提示词：心跳开启时去掉标记、保留正文；心跳关闭时整段删除，所以关掉心跳的智能体根本看不到这些说明。

### 改配置无需重启

开启、关闭或修改任意心跳字段都会原地生效：在控制台保存会重排该任务；直接改 `agent.json` 则由配置监听（约 2 秒）发现，并通过智能体重载重新注册该任务。都不需要重启服务。

> **「心跳」在代码里指多种互不相关的机制。** 除了本文档讲的「智能体自唤醒」，SSE 空闲保活、工具审批保活、各频道 WebSocket ping、定时任务事件循环看门狗也都被叫作 heartbeat；只有第一种由 `agent.json` 里的 `heartbeat` 配置。

## 和「定时任务」的区别

|          | 心跳                       | 定时任务 (cron)              |
| -------- | -------------------------- | ---------------------------- |
| **数量** | 只有一份（HEARTBEAT.md）   | 可以建很多个                 |
| **间隔** | 一个全局间隔               | 每个独立设定时间             |
| **投递** | 可选发到「上次频道」或不发 | 每个独立指定频道和用户       |
| **适用** | 固定的一套自检/摘要        | 多条不同时间、不同内容的任务 |

> 需要「每天 9 点发早安」「每 2 小时问待办并发到钉钉」这类多条任务？请使用 [定时任务](./cron)（或 [CLI](./cli) 的 `qwenpaw cron create`），而不是心跳。
