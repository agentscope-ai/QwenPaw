# 记忆自进化与主动交互（Beta）

> 本文承接[长期记忆](./memory)，只讲那篇没有展开的两件事：**同一条长期知识如何随时间被改写**，以及 **`/proactive` 主动交互到底怎样工作**。记忆目录、文件格式、索引原理、检索机制和完整配置都在[长期记忆](./memory)中。

QwenPaw 里有两条相互配合、但各自独立运行的链路：

| 链路       | 数据来源                                     | 产出                                           |
| ---------- | -------------------------------------------- | ---------------------------------------------- |
| 记忆自进化 | `memory/` 每日记忆                           | `digest/` 长期知识                             |
| 主动交互   | 长期记忆、外部通知与日程注册表（ReMe 侧产出） | `memory/<date>/interests.yaml` 里的当日主动议程 |

Auto-Dream 只写 `digest/`；主动议程由 ReMe 一条**独立的 proactive 链路**产出。`/proactive` 读的正是后者——它**不再自己扫会话、不再截屏、也不再启动一个绕过工具授权的助手**，只负责把 ReMe 排好序的议程呈现给你，由你决定要不要推进。

## 一、记忆怎样“进化”

静态记忆只能追加和检索。自进化记忆要回答一个更难的问题：**新证据会怎样改变已经知道的事情？**

### 一条结论被改写四次

假设上周你告诉 QwenPaw：“生产发布前先验证 staging，发布说明要写清风险和回滚步骤。”几天后团队又补了一条例外：“紧急 hotfix 经负责人批准可以先发布，但事后必须补做检查。”

这些话散落在不同日期的对话里。Auto-Dream 每天运行时，不会为每句话新建一个文件，而是找到**同一个**长期节点，并只选一种动作改写它（四种动作的定义见[长期记忆](./memory)）：

| 时间     | 动作          | 节点发生了什么变化               |
| -------- | ------------- | -------------------------------- |
| 第 1 天  | `CREATE`      | 建立“生产前验证 staging”这条流程 |
| 第 3 天  | `CORROBORATE` | 另一次发布再次确认，可信度提高   |
| 第 8 天  | `REFINE`      | 补上发布说明、风险与回滚步骤     |
| 第 20 天 | `CORRECT`     | 加入经批准的紧急 hotfix 例外     |

到第 20 天，`digest/procedure/production-release.md` 已经变成这样：

```markdown
---
name: 生产发布流程
description: 常规发布必须验证 staging；紧急 hotfix 使用经批准的例外流程。
---

# 生产发布

## 常规流程

1. 在 staging 验证版本。
2. 编写发布说明，并列出风险和回滚步骤。
3. 验证通过后才能进入生产环境。

## 紧急 hotfix 例外

只有取得事故负责人批准后才可跳过完整 staging；必须记录原因，并在事后补做检查。

relates_to:: [[digest/personal/release-communication-preference.md]]
depends_on:: [[digest/procedure/rollback-verification.md]]

## Sources

- [[memory/2026-08-01/release-planning.md]]
- [[memory/2026-08-08/release-notes.md]]
- [[memory/2026-08-20/hotfix-retrospective.md]]
```

关键不是文件变长了，而是四件事同时成立：

- **重复变成了可信度**，而不是四条互相矛盾的记录；
- **细节变成了可执行步骤**，下次可以直接照着做；
- **冲突变成了有适用范围的例外**，而不是把旧结论一笔删掉；
- **每条结论都还能回到来源**，`## Sources` 保留了它是怎么形成的。

除了 `[[...]]`，节点还可以用 `relates_to::`、`depends_on::` 这类带语义的关系字段说明“它和谁有关、依赖谁”，检索命中一个节点后就能顺着这些关系继续展开。

### 每次进化只看必要的输入

Auto-Dream 不会每天从头重读整个 `memory/`：

- **扫描窗口**：只看目标日期及其**前一天**发生过变化的每日记忆；
- **单次上限**：一轮最多抽取 5 个记忆单元，宁可分几天慢慢沉淀，也不会一次塞满 `digest/`；
- **断点记录**：成功处理过的输入会写入 dream catalog，下次不再重复整合；
- **失败可重试**：失败的路径**不会**被标记完成，所以下一次运行还会再试一遍；
- **只写 `digest/`**：`memory/` 永远保留“当时看到了什么、怎么判断的”，Auto-Dream 从不回头改写它。

这也是为什么长期记忆可以一直修正而不丢历史：结论可变，现场不可变。

### 兴趣主题与当日议程

主动议程不由 Auto-Dream 产出。ReMe 有一条**独立的 proactive refresh 链路**：从每日记忆与外部通知里提炼提议，去重成主题，规划成场景卡，再选出当日议程，最后写入两份文件（目录名跟随 `daily_dir`，QwenPaw 默认为 `memory`）：

- `memory/<date>/interests.yaml`——当天的 `topics`（每条带 `kind`、置信度、证据路径）、排好序的 `agenda`，以及本轮被压制的 `suppressed`；
- `memory/_proactive.yaml`——可重建的 truth source，保存长生命周期的 `open_topics`、`resolved` 墓碑、`schedules` 日程注册表与 `deliveries` 投递记录。

提议只有四种类型，且都不是必需项：一轮可以只产出其中任意子集，也可以一条都没有。

| 类型              | 它在提什么                                              |
| ----------------- | ------------------------------------------------------- |
| `reminder`        | 你自己的计划与日程，以及外部信源里必须告知你的通知与事件 |
| `follow_up`       | 你交代过但没闭环、或一直在关注的事项有了新进展           |
| `new_idea`        | 基于 Agent 自身资源（数据、技能、工具）可委托给你的工作  |
| `interest_extend` | 你关心主题的细化与延伸内容                               |

`reminder` 的优先级高于其余三类：到期日程会被**固定**在当日议程最前，按到期时间由近到远排列，既不会被压制也不会被换掉；发现类条目则始终保有 `min_discovery_slots`（默认 2）个名额，所以日程排满的一天也不会退化成一张纯日历。ReMe 自身把发现类议程上限定为每天 6 条。

每条议程都带一句自然口吻的开场白（`opener`）和一个最小可执行动作（`next_action`），QwenPaw 直接原文呈现，不再让模型重写一遍。Auto-Dream 不读取也不写入这两份 proactive 产物。

## 二、`/proactive`：让 Agent 先开口

前面讲的都是“你问它才答”。`/proactive` 反过来：**在你没提问的时候，判断有没有一件事值得现在主动告诉你。**

内容来自长期记忆，而不是临时猜测。ReMe 的 proactive 链路已经从每日记忆、外部通知和日程注册表里提炼出了当日议程；QwenPaw 只做三件事：**读取、去重、呈现**。

打开之后你会看到的效果是：你这两天一直在推进某个框架的迁移，晚上离开电脑半小时后，收件箱里多了一张卡片：

> **主动议程建议 (2)**
>
> **1. 记忆检索链路的质量回归** `follow_up`
> 下次发布前先回顾最近的检索回归。
> ↳ 可以让我：对比失败查询与上一个索引快照
>
> **2. 迁移指南更新** `interest_extend`
> 官方上周发布了 3.0 迁移指南，API 变更部分和你昨天遇到的报错相关。
> ↳ 可以让我：把变更点整理成一页对照表
>
> 以上条目来自长期记忆的主动议程。收件箱不支持直接执行，想推进哪一条，在聊天里告诉我编号或标题即可。

**这条消息不是模型即兴写的，也没有谁替你干了什么**——它就是 ReMe 事先排好的议程原文。整条呈现路径**零 LLM 调用、零工具执行**：Agent 永远只是把建议摆出来，不会把某条议程当成指令自己去执行。

### 开关在哪里

主动议程**默认关闭**。在 **运行配置 → 长期记忆 → 主动议程** 面板里打开总开关之后，`/proactive` 才可用。开关关闭时：命令只回一句“请先打开主动议程”，空闲监听不会武装，每日定时任务也不会注册。

### 三种触发方式

| 触发方式     | 何时发生                       | 结果落在哪里                  | 是否强制重跑 extraction |
| ------------ | ------------------------------ | ----------------------------- | ----------------------- |
| `/proactive` | 你手动执行                     | **当前聊天**里回一条议程回执  | 否（仅在议程为空时）    |
| 空闲轮次     | 武装后满足空闲条件             | **收件箱**                    | 否（仅在议程为空时）    |
| 每日定时任务 | `proactive_cron`（默认 18:00） | **收件箱**，默认全量          | 是                      |

三者读的是同一份议程，差别只在落点和是否强制刷新：

- **`/proactive` 立即回执**：命令本身不等待空闲。它当场读取议程，把最高的 `proactive_max_items`（默认 3）条拼成一条消息回到你所在的聊天，**同时**武装空闲监听（默认 30 分钟阈值，`/proactive 45` 可改）。到期的 `reminder` 始终排在最前。
- **空闲轮次与定时任务只写收件箱**：这两个是自动触发的面，不会往你正在进行的对话里插话。收件箱是阅读面，卡片本身不能执行；想推进哪一条，回聊天里说编号或标题。
- **`/proactive now`**：跳过等待，立刻做一轮“强制 refresh + 推送收件箱”，适合刚导入一批素材想马上看到议程。它走的是推送路径，因此同样需要打开“收件箱通知”。

### 读取优先，为空才刷新

每次触发走的都是同一条路径：

1. 调 ReMe 的 `proactive` job **只读**现成议程（到期提醒已固定在最前）；
2. 用本地投递台账过滤掉冷却期内已经给你看过的条目；
3. **只有过滤后为空**，才调 `proactive_refresh` 从 topic extraction 开始重跑一遍，然后再读一次；
4. 这种按需刷新受 `proactive_refresh_min_interval_minutes`（默认 120 分钟）限流，避免反复触发一条昂贵的链路。

定时任务和 `/proactive now` 不做第 3 步的判断，而是**总是**先 refresh，保证每天的推送反映当天素材，而不是一份过期的 `interests.yaml`。

refresh 本身也不会无谓花钱：没有每日记忆变化、没有新的外部通知、也没有到期日程时，ReMe 会在调用 LLM 之前直接结束；只有时钟算出到期提醒时，链路会零 LLM 调用地走完，确保当天议程拿到提醒。

### 什么时候才算“该出手了”（空闲轮次）

空闲监听每 30 秒检查一次。要真正推一轮，下面几个条件必须同时满足——它们的作用几乎都是“避免打扰”：

| 检查项     | 规则                                                          | 为什么需要                   |
| ---------- | ------------------------------------------------------------- | ---------------------------- |
| 功能已开启 | `proactive_enabled` 为真                                       | 总开关关掉，整条路径停摆     |
| 允许推送   | `proactive_inbox_push_enabled` 为真                            | 可以只要聊天回执、不要推送   |
| Agent 空闲 | 当前没有正在执行的任务                                         | 你正在用它干活时不插话       |
| 空闲够久   | 距最后一次活动 ≥ 空闲阈值（默认 30 分钟）                      | 只在你离开时才考虑主动       |
| 开启也够久 | 距 `/proactive` 打开的时刻同样 ≥ 空闲阈值                      | 刚打开就弹一条会很突然       |
| 冷却       | 距上一次尝试 > 60 秒                                           | 条件持续满足时不会连发       |
| 无并发     | 上一轮已经结束                                                 | 同一时间只跑一个             |
| 推送间隔   | 距上一次收件箱推送 ≥ `proactive_refresh_min_interval_minutes`  | 一天不会反复轰炸             |

这里的“最后一次活动”取的是**当前 workspace 里所有聊天中最新的 `updated_at`**，不是只看你输入 `/proactive` 的那个聊天。所以你在另一个聊天里干活，也算你还在忙。

### 没有内容时怎么办

自动触发的面（空闲轮次、定时任务）在议程为空时**完全静默**：不写收件箱、不发通知，只留一行日志。收件箱是阅读面，一张“今天没有内容”的卡片只是噪音。

手动执行的 `/proactive` 则会明确回一句，并按原因区分：

| 情况                  | 你会看到                                            |
| --------------------- | --------------------------------------------------- |
| ReMe 未启动或读取失败 | 提示去 运行配置 → 长期记忆 检查配置后重试            |
| 刷新被限流            | 说明距上次刷新不足 N 分钟，本次沿用现有议程          |
| 议程都已投递过        | 说明最近 N 条已推送，冷却期内不再重复展示            |
| 刷新后仍然没有内容    | 说明今天暂时没有值得主动提醒的新议程                 |

### 不会重复给你看同一件事

去重有三层，任何一层命中，该条目本轮就不出现：

1. **ReMe 写侧**——agenda 步骤按 `redelivery_cooldown_days` 压制已投递过的候选，并把原因记进 `suppressed`，可审计；
2. **ReMe 读侧**——`proactive` job 按 `deliveries` 与冷却窗口扣掉已投递条目，并返回 `delivered_ids`；
3. **QwenPaw 本地台账**——`<metadata_dir>/proactive_delivered.json` 记录每一条实际展示过的议程。它负责 ReMe 看不到的两件事：ReMe 侧写入失败时的兜底，以及**跨天去重**（同一主题第二天又出现在新的 `interests.yaml` 里）。

`reminder` 是这三层冷却的唯一例外。日程到期就得说，而 reminder 的 `topic_id` 由稳定的日程标题派生，若照常压制，一条周期性提醒在投递一次之后就会在整个冷却窗口里静默。因此 ReMe 的写侧与读侧、以及 QwenPaw 的本地台账，都会放行 `kind == "reminder"` 的条目；其余三类（`follow_up` / `new_idea` / `interest_extend`）照常去重。

每次真正展示之后，QwenPaw 会尽力调 ReMe 的 `proactive_feedback` job 回传这批条目（`topic_id`、`agenda_date`、`delivered_at`、`channel`、`status`、`external_ref` 等）。回传是**可选契约**：其他 Agent 框架不回传时，ReMe 的行为与从前完全一致。`status` 只向前推进（`shown` → `executed` / `dismissed`），而 `failed` 不阻止下一轮重新投递。

### 隐私与安全边界

相比旧版，这条路径的权限面小得多：

- **不截屏**，也**不读取会话原文**——它读的是 ReMe 从长期记忆里提炼出的议程文本；
- **没有 bypass 助手**，不启动任何带工具的子 Agent；
- **零 LLM 调用、零工具执行**：呈现路径是纯字符串拼装，议程条目不会被当成指令执行；
- 唯一的模型消耗发生在 ReMe 的 `proactive_refresh` 内部，且只在有素材变化时发生。

需要留意的是，议程内容毕竟来自你的长期记忆，因此可能提到你确实说过的私事。另外，空闲监听的状态**只存在于进程内存中**，QwenPaw 重启后需要重新执行 `/proactive` 武装；总开关与定时任务配置则持久保存在 `agent.json` 里。

## 三、配置与命令

### `/proactive` 命令

```text
/proactive           # 立即回执当日议程，并武装空闲监听（默认 30 分钟）
/proactive on        # 同上
/proactive 45        # 同上，空闲阈值改为 45 分钟（须为正整数）
/proactive now       # 立刻强制重跑一次议程并推送到收件箱
/proactive off       # 停止空闲监听
```

参数写错时会提示用法。总开关关闭时，命令只回一句“请先在 运行配置 → 长期记忆 中打开主动议程”。空闲监听的状态只存在于进程内存中，QwenPaw 重启后需要重新执行 `/proactive`。

### 手动运行 proactive job

```text
/reme proactive                       # 只读当日议程，不刷新
/reme proactive date="2026-10-12"     # 读指定日期的议程
/reme proactive include_delivered=true # 连已投递过的条目一起返回
/reme proactive_refresh               # 从 topic extraction 重跑一遍
```

`proactive` 是只读 action，可直接从聊天调用；`proactive_refresh` 会消耗模型资源并写入结果，因此和 `auto_dream` 一样，需要发起请求的聊天身份先完成审批，经过身份验证的控制台可作为管理员审批。执行 `/reme help` 可查看当前可用且允许从聊天调用的全部 action。

### Auto-Dream 手动运行

```text
/reme auto_dream                    # 立即执行一次 Auto-Dream
/reme auto_dream hint="关注某个主题" # 带提示执行一次
```

平时不需要手动跑：Auto-Dream 默认每天定时执行一次。
手动运行需要发起请求的聊天身份先完成审批；经过身份验证的控制台可作为管理员审批。

### 与本页相关的配置项

以下几项位于 `agent.json` 的 `running.reme_light_memory_config`，也都能在 **运行配置 → 长期记忆** 面板里修改。完整配置（目录、Embedding、Daily Paper、Auto Fin、索引维护、其他 Backend）见[长期记忆](./memory)。

| 配置项                               | 默认值           | 说明                                                    |
| ------------------------------------ | ---------------- | ------------------------------------------------------- |
| `dream_cron_enabled`                 | `true`           | 是否定时运行 Auto-Dream                                 |
| `dream_cron`                         | `"0 23 * * *"`   | 5 段 Cron 表达式；触发后随机延迟 0–60 秒启动             |
| `auto_dream_inbox_push_enabled`      | `true`           | Auto-Dream 有实际变化或执行失败时推送到 Inbox            |
| `auto_memory_interval`               | `5`              | 每累计 N 个用户回合运行 Auto-Memory                     |
| `auto_memory_search_config.enabled`  | `false`          | 是否在每个普通用户请求前自动检索记忆                     |
| `proactive_enabled`                  | `false`          | 主动议程总开关；关闭时 `/proactive` 只解释如何开启       |
| `proactive_max_items`                | `3`              | `/proactive` 回执与空闲轮次单次呈现的条数（1–10）        |
| `proactive_inbox_push_enabled`       | `true`           | 空闲轮次与每日任务是否推送到 Inbox                      |
| `proactive_cron_enabled`             | `false`          | 是否注册每日议程推送任务                                |
| `proactive_cron`                     | `"0 18 * * *"`   | 每日推送的 5 段 Cron；启用时必填，随机延迟 0–60 秒       |
| `proactive_cron_max_items`           | `0`              | 每日推送条数；`0` 表示全量（ReMe 自身上限 6 条/天）      |
| `proactive_delivery_cooldown_days`   | `3`              | 已投递条目的隐藏天数，ReMe 与本地台账共用（0–90）；`reminder` 豁免        |
| `proactive_refresh_min_interval_minutes` | `120`        | 按需刷新的最小间隔，同时限制空闲推送密度；`0` 不限制     |

Auto-Memory 间隔越小，进入 Auto-Dream 与 proactive extraction 的素材越新，但模型调用和 Token 消耗也越高。
