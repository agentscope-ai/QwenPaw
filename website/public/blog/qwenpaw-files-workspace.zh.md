# 从文件树到 Files 工作台：QwenPaw 如何把 Agent 的工作目录变得可见

当 Agent 只负责回答问题时，聊天记录似乎就是全部工作现场。可一旦任务变成“读一批资料、修改项目、生成报告、保存长期记忆”，真正持续变化的内容就不在聊天框里，而在文件里。

文件是 Agent 的工作记忆，也是人类检查结果、接手任务和继续协作的共同语言。问题是，传统的文件入口往往只是一个文件列表：能看到名字，却很难在同一个地方完成浏览、理解、修改和核对。

QwenPaw 最新的 **Files 工作台**，正是从这个问题出发。它把文件树从一个“导航控件”扩展成统一的工作界面，让用户可以在同一个地方浏览、预览、编辑、核对并继续引用文件。

![Files 工作台总览](https://img.alicdn.com/imgextra/i4/O1CN01GjiXT3fTIrJ5Bkx9_!!6000000006529-2-tps-2556-1223.png)

## 01 Agent 真正工作的地方是文件

一个典型的 Agent 任务通常会经历这样的过程：

1. 从项目目录读取代码、配置或资料；
2. 在对话中分析并提出修改方案；
3. 把结果写回文件，生成新的文档或媒体；
4. 让用户预览、编辑、比较，并把相关内容再次引用到 Chat；
5. 在后续会话中继续使用项目文件、Profile 和 Memory。

如果这些步骤分别发生在聊天附件、独立代码页、下载文件和系统文件管理器里，用户就必须不断猜测“这个文件现在属于哪里”“我看到的是哪个版本”“修改会写回哪个目录”。Agent 也需要在多个路径和 API 之间切换，文件上下文因此变得脆弱。

Files 工作台的目标不是再造一个完整 IDE，而是让 Agent 工作中最常见的文件动作拥有一个稳定、可解释的入口：**先找到文件，再看懂文件，必要时修改文件，最后把结果带回任务上下文。**

## 02 一个统一的 Files workspace

这次改造把原本分散在 Chat、Agent Workspace 和 Coding 页面中的文件体验，收敛到同一个 Files 域。它包含三个互相衔接的层次：

- **文件树**：按目录展开内容，显示文件类型并支持分页加载；
- **文件预览**：在不离开当前任务的情况下查看 Markdown、图片、PDF、CSV 和纯文本；
- **编辑工作区**：使用 Monaco 编辑器打开多个文件，保留标签页、光标和撤销状态。

从 Chat 里点击附件时，文件首先以 Preview 抽屉打开，而不是立即下载。需要更大的操作空间时，可以把抽屉展开为完整 Workspace；从侧边栏进入 Files，则直接打开完整工作区。两种入口共享同一套导航、预览和编辑能力，但会分别保存 Agent 级与 Session 级的标签页状态，不会把两个工作现场混在一起。

![Chat 文件预览抽屉](https://img.alicdn.com/imgextra/i3/O1CN01TTmgqymDpqH5CGAk_!!6000000002889-0-tps-2560-1226.jpg)

## 03 文件树不只是列出文件名

### 从根目录开始，逐层读取

文件树不会在第一次打开时把整个目录递归展开，而是按需读取当前目录的直接子项。展开文件夹时，前端请求下一页内容；后端对单页数量、相对路径长度和路径穿越进行限制，并在访问符号链接时重新校验最终路径。

这种方式让普通项目可以快速进入工作状态，也让 Project Directory 的切换拥有清晰的边界。文件树中的路径统一以相对 POSIX 形式传递，Windows 的盘符、反斜杠和保留名称则在 API 边界完成跨平台处理。

### 两种目录身份，一棵树里切换

Agent 同时需要两类目录：

| 目录                          | 保存什么                                             | 适合什么时候查看              |
| ----------------------------- | ---------------------------------------------------- | ----------------------------- |
| Project Directory             | 用户项目、代码、资料、Git 工作区和任务产物           | 进行当前项目工作              |
| Agent Configuration Directory | Profile、Memory、会话、技能、缓存等 QwenPaw 自有数据 | 检查 Agent 的配置与长期上下文 |

Files 不把它们拆成两个互不相关的产品，而是在同一个文件树顶部提供根目录切换。若两个路径实际指向同一目录，界面会自动合并身份，避免重复展示。

除此之外，工作台还提供 **Profile** 和 **Memory** 入口。Profile 文件可以启用、停用和拖动排序；Memory 则继续使用日记、摘要等领域 API。它们都复用同一套预览与编辑界面，但不会因此失去自己的语义。

## 04 从“看一眼”到“改一处”：预览、编辑与 Diff

打开文本文件后，Files 会在 Preview 和 Edit 之间切换。编辑器按文件路径维护模型，因此切换标签页时可以保留光标、撤销栈和未保存修改。Markdown、代码、配置和 CSV 都可以在同一工作区里处理；图片和 PDF 则使用只读预览。

当文件被外部进程修改时，工作台会通过文件监听发现变化，并提示当前编辑内容与磁盘版本之间的差异。对于每个变更块，用户可以单独选择 **Keep** 或 **Undo**，也可以一次性保留或撤销全部变更。保存操作仍由用户触发，`Cmd/Ctrl+S` 会把确认后的文本写回原文件。

这套交互解决的是 Agent 协作中的一个高频问题：Agent 可能已经生成了结果，但用户需要先逐段检查，再决定哪些修改进入项目。Diff 不替用户做决定，而是把决定所需的上下文放在同一个界面里。

## 05 文件上传、下载与 Chat 引用

文件工作台还承担着任务输入输出的两端：

- 上传文件到当前选择的 Project Directory 或 Agent Configuration Directory；
- 下载工作区中的文件；
- 当目标文件已存在时，提供重命名、跳过和覆盖选项；
- 将文件或选中的代码片段复制回 Chat；
- 从 Chat 文件卡片和工具产物回到同一个 Preview / Workspace。

引用不是简单地把一段文本粘贴到输入框。Files 会保留文件路径与行号信息，让用户知道 Agent 看到的是哪个文件、哪一段内容。文件无法在当前 Project Directory 或 Agent Configuration Directory 中安全解析时，历史附件会退回只读预览，而不会假装它仍然可以编辑。

## 06 Project Directory：文件树背后的运行时边界

文件树是否好用，最终取决于 Agent 的工具是否和用户看到的是同一个目录。为此，Project Directory 已经从 Coding 页面的局部设置提升为运行时概念：

- Agent 可以设置默认 Project Directory；
- 单个 Chat Session 可以覆盖这个默认值；
- 目录变更会持久化到会话，并同步影响文件读取、保存、上传、下载和文件监听；
- Shell、代码分析、Git 和相关工具使用同一个有效目录。

这意味着用户在 Files 中切换目录后，不需要再去另一个设置页重复配置。Agent 也不会一边在工作目录里写文件，一边把结果展示成来自另一个目录的内容。

## 07 一个典型的文件工作流

假设你让 Agent 整理一个项目的发布说明，可以这样完成：

1. 在 Chat 中描述目标，让 Agent 读取 Project Directory 中的变更记录和文档；
2. 点击 Agent 生成的 Markdown 文件，在 Preview 中快速检查结构；
3. 展开到 Workspace，在 Monaco 中修改措辞或补充段落；
4. 如果文件被 Agent 或外部工具再次修改，用 Diff 逐块 Keep / Undo；
5. 将关键段落或文件引用复制回 Chat，让 Agent 根据你的反馈继续工作；
6. 回到 Files 工作台确认最终版本，并下载文件交付。

这条链路中，聊天负责意图，文件负责状态，Preview 和 Diff 负责检查，Files 工作台让整条链路始终处于同一份可见上下文中。

## 08 安全边界与当前取舍

Files 处理的是本地文件，因此安全边界必须比“能不能打开文件”更具体。当前实现会在后端检查敏感路径、工作区范围、路径穿越、Windows 保留名称和符号链接逃逸；文件写入使用原子保存，上传冲突也不会静默覆盖已有文件。

这次更新也没有把尚未完成的优化包装成 IDE 级能力。当前版本已经提供目录分页和分块读取接口，但前端在打开文本文件时仍会组装完整内容；超大目录尚未使用虚拟化，文件树搜索也还在后续规划中。对于普通 Agent 工作区，这些取舍让功能先保持稳定和可解释；对于大型代码仓库，我们会继续完善渐进式渲染、取消请求、内容缓存和目录搜索。

## 09 下一步：让文件体验继续“渐进”

Files 的下一阶段不是简单地堆叠更多按钮，而是让用户在不同规模的工作区里都能保持同样的确定感：

- 打开大文件时先展示首个分块，再逐步加载后续内容；
- 在切换标签页时取消无用的分块请求；
- 为大目录加入虚拟化和文件搜索；
- 完善 ETag 冲突的明确用户提示和恢复流程；
- 继续打磨移动端和窄窗口下的全屏文件体验。

这些工作会沿着同一个原则推进：先让文件状态可见，再让 Agent 的自动化动作可控，最后才把性能优化扩展到更大规模的项目。

## 总结

文件树看起来只是一个小组件，但它连接了 Agent 的项目目录、配置、记忆、工具产物和用户反馈。QwenPaw 这次的 Files 改造，把这条链路整理成一个统一 workspace，让目录浏览、内容检查和文件修改围绕同一组路径与状态展开。

从文件树展开目录，到预览、编辑、Diff、上传下载，再到 Chat 引用，用户始终面对的是同一份工作状态。对 Agent 来说，这意味着更少的路径歧义；对用户来说，这意味着更清楚地知道 Agent 正在读什么、改什么，以及下一步应该由谁确认。
