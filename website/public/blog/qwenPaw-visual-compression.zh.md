# QwenPaw 视觉压缩：把长上下文渲染成图片

## 什么是视觉压缩？

Agent 场景中的上下文开销，通常并不是因为用户的问题本身很长，而是因为同一批系统提示词、工具说明、文件内容和历史消息，会在每次“模型 → 工具 → 模型”的循环中被重复送入模型。随着交互轮数增加，真正新增的信息可能并不多，但模型每一轮都必须重新读取大量已有上下文。结果是，一次看似简单的任务，最终可能消耗数万甚至数十万 token。

一种常见的解决方式是文本摘要，例如 `/compact`：把较长的历史重新总结成一段更短的文本。它擅长保留主题和主要结论，但代价是完全改写原始历史。一旦摘要遗漏或写错某个细节，模型通常也没有证据判断错误发生在哪里。频繁生成摘要还可能破坏缓存命中；而对于超长系统提示词、大量工具定义等本身就高度重复的内容，文本摘要也很难从根本上解决问题。

一个有趣的优化方向，是把部分文本上下文渲染成图片，再交给多模态模型读取。文本输入的 token 开销通常会随文字长度近似线性增长，图片输入则更多取决于图像分辨率、视觉 patch 数量以及模型具体的视觉编码方式，而不完全取决于图片中包含多少字符。这带来了一个潜在的压缩空间：同一批历史消息、工具说明或文件内容，如果直接作为文本输入，可能需要十万个 token；如果经过紧凑排版并渲染为少量高密度图片，产生的视觉 token 可能低得多。换句话说，视觉上下文并不只是“让模型看截图”，而是在利用二维像素空间，重新编码原本只能线性展开的文本。对于需要频繁调用工具、持续运行很多轮的 Agent，这可能成为一种新的上下文压缩方式。

![image](https://img.alicdn.com/imgextra/i2/O1CN01yY4c4j29VUb5FtFhp_!!6000000008073-2-tps-1561-858.png)

当然“**像素中还有原文**”不等于“**模型能逐字读回原文**”。图片最终会变成视觉块；当字号、分辨率或注意力不足时，模型可能读错。因此，图片和摘要可以看作两种不同的有损方式：

- 摘要主动改写语义；
- 图片保留版面，却把识别责任交给视觉模型。

## QwenPaw如何进行视觉压缩

在QwenPaw 2.0.1 中，参考[pxpipe](https://github.com/teamchong/pxpipe)的实现引入了\*\*视觉压缩\*\*功能。在QwenPaw的实现中，如果开启了视觉压缩功能，那在模型请求发出之前，QwenPaw 会复制一份本轮的消息和工具定义，只改写这份临时请求。会话中保存的仍然是完整原文。下一轮开始时，系统会再次从原始消息判断哪些内容值得压缩。

它做的事情可以概括为：**保留最近和当前工作，折叠稳定的旧内容，保留回溯路径。**

- **保留最近和当前工作。** 当前用户请求、最近几轮消息、尚未结束的工具调用，以及核心工具协议，都会继续留在文本通道。QwenPaw 只会保守迁移较长、较稳定的背景说明。
- **折叠稳定的旧内容。** 较早的对话、长背景和大型成功 tool result 可以被分块渲染成图片。历史消息只有在跨过新的边界时才会重新分块，避免每轮重画全部内容，也让缓存更稳定。
- **保留回溯路径。** 内容太短、图片太多、排版不完整，或视觉成本没有明显低于原文本时，就继续使用文字而不做视觉渲染。不同部分会独立尝试、独立放弃。如果出现异常，比如媒体丢失或图片预算失控时，会整体回滚到原生请求。

![image](https://img.alicdn.com/imgextra/i1/O1CN018fyB8CrJq2H3bJe1_!!6000000002179-2-tps-1774-887.png)

真正生成图片时，QwenPaw 也不会总结或改写原文。它只整理多余空白，保留换行、缩进、角色标签和工具调用结构，再根据 `low`、`medium` 或 `high` 选择不同的文字密度。系统会先完成分页和成本估算，确认值得转换后才生成图片。相同内容和配置的情况下还可以复用本地渲染结果。

但**图片并不适合保存所有精确值**。路径、版本号、URL、数字和随机 ID 只要读错一个字符，结果就可能完全不同。Visual Compact 因此增加了两层保护：

- **真相表** 会从原文中提取一部分高风险字符串，以原生文本放在图片旁边，方便模型直接读取。
- **回溯工具** 则允许模型回到真正的源文本。每个被图片替换的内容块都会获得一个 ID；模型可以通过 **恢复工具** `recover_visual_context` 预览原文、搜索关键词、读取指定行，或者按字符位置继续翻页。

例如，模型先从视觉页面中理解一份很长的校验报告，需要确认其中的最终状态时，可以直接用对应的 Recovery ID 搜索 `final_status`。返回结果来自转换前的原文，而不是重新对图片做 OCR。

总结，QwenPaw 会把一次请求中的上下文分到三个通道：

- 文本承载当前任务、重要规则、工具协议和高风险字段；
- 图片承载长而稳定的背景、旧历史和大型结果；
- 恢复工具在需要精确确认时返回源文本。

## 在QwenPaw中使用视觉压缩

在**运行配置**\-**上下文管理中**启用视觉压缩，对话模型选择具备**多模态能力**的模型即可使用（[相关文档](https://qwenpaw.agentscope.io/docs/context)）。

- 模型是否具备多模态能力可以在**模型**界面检查
- 低/中/高模式对应压缩强度，默认选择低就好，压缩强度通常也已经足够。

## 视觉压缩效果观察

为了测试效果，我在本地设计了一个虚构的电商服务事故调查场景。工作目录里包含订单 CSV、服务日志、会议纪要、邮件、产品规范、JavaScript 源码和测试文件。Agent 需要连续完成九项任务，包括统计数据、分析日志、跨文件定位问题、从会议纪要中提取行动项、修改代码并运行测试，以及在不能重新读取文件时回忆之前见过的精确 ID。九项任务在同一个 session 中进行。越到后面，历史越长，比较接近真实 Agent 工作时遇到的上下文累积问题。

实验比较了四种模式：

- **Text only**：关闭视觉压缩，历史全部保留为文字；
- **Low**：只压缩明显较大的内容；
- **Medium**：更早开始压缩，图片排版也更密；
- **High**：压缩范围最广，排版最密。

每种模式独立运行三次，共 12 个 session、108 个任务，模型使用 Qwen3.7-Plus。

### 结果

| Mode      | Tasks passed | Input       | Uncached   | Cached      | Output    | Calls  | Images  | Compressed chars |
| --------- | ------------ | ----------- | ---------- | ----------- | --------- | ------ | ------- | ---------------- |
| Text only | **27/27**    | 3,185,875   | 283,934    | 2,873,088   | 12,594    | 42     | —       | —                |
| Low       | 25/27        | 563,740     | 123,164    | 440,576     | 10,952    | 40     | 243     | 5,490,583        |
| Medium    | 26/27        | **389,183** | **93,398** | **306,816** | **8,815** | **35** | **165** | **4,228,839**    |
| High      | 25/27        | 419,363     | 97,000     | 331,008     | 9,987     | 38     | 208     | 5,439,353        |

- **视觉压缩大幅减少了输入。** Low、Medium、High 的 Input 分别减少 **82.3%**、**87.8%** 和 **86.8%**。即使排除 cache-read，Uncached input 仍分别减少 **56.6%**、**67.1%** 和 **65.8%**。说明视觉压缩在长上下文、多轮场景下大幅减少了token开销；
- **Medium 综合效果最好。** 它的 Input、Uncached input 和模型调用次数都是三种视觉模式中最低的，27 个任务完成了 26 个。

  - 第一次运行时，Agent 因为解析错 CSV 列反复修改脚本，单次 Input 达到 720,376；后两次只有 389,183 和 350,166。
  - Low 有一次没有调用 recovery，直接表示无法找到答案；另一次正确生成了结果文件，但最终回复串入了上一项任务。Medium 唯一的失败是漏改了三个代码文件中的一个，更像普通的执行遗漏。
  - High 连续两轮失败在同一个精确记忆任务上：模型知道 recovery 工具存在，却没有真正调用。第一轮虽然成功，也用了三次 recovery 才找到答案。**更多 recovery 和模型调用可能抵消原本节省的 Token，走错路径时甚至会直接导致任务失败。**

**小结**：只看这次实验，Medium 的综合效果最好。但默认配置需要面对更多未知任务，因此仍推荐更保守的 **Low**，它会保留更多原生文字和最近历史，同时已经获得约 82% 的 Input 降幅。对于经过验证的长日志、长工具结果场景，可以使用 **Medium**；**High** 暂时需要谨慎使用。

## 总结

本文介绍了在 QwenPaw 新版本中使用“**视觉压缩**”的方式与体验。在原生多模态能力越来越强的未来，视觉辅助上下文、记忆的设计相信会越来越多。

### 视觉压缩最适合的内容

- **长而旧的语义背景。** 历史日志、旧 tool result、规范背景和会议记录通常需要理解主题与关系，而不是逐字抄写每个字符。
- **缓存尚未变热，或文本逼近窗口预算。** 此时减少输入表示更可能产生实际价值。
- **能够回源的内容。** 原文仍可通过 Recovery ID 定位时，图片只需要承担“先读懂”，不必承担“永久无损保存”。

### 视觉压缩的风险

- **逐字符精确值。** 短 hex、SHA、UUID、金额、版本号、路径、表格单元格和代码片段读错一个字符就可能完全错误。
- **安全规则与当前指令。** 图片中的指令可能不如原生 system/user 文本显著，不能假设换一种 role 或模态仍保持完全相同的服从强度。
- **不可恢复的外部状态。** 当前库存、订单状态、工作区文件内容等应重新查询真实 source，而不是把旧视觉页当成事实数据库。

### 谨慎看待视觉压缩的收益

需要注意的是，原本的文本可能已经进入较便宜的缓存命中。把它换成图片会改变前缀，第一次转换或边界推进时都可能重建缓存。与此同时，视觉预填充、本地渲染和模型行为分叉也会影响延迟。如果图片让模型多检查一次、多调用一次工具，额外一轮推理会再次携带整份上下文，足以吃掉局部的输入节省。

因此实际使用时，对视觉压缩的启用要相对保守，不能仅从token节省就决定使用场景。

- 原文本的缓存读取概率，图片前缀的稳定性；
- 模型多模态能力，是否需要多次recover才能完成任务，是否引入多轮额外工具调用开销；
- 实际模型计价，对image token和text token是否等价计费。

### 视觉压缩的未来

尽管计价上需要考虑的点更加复杂，但上下文空间的节约给长程任务提供了更大的空间。同时目前QwenPaw的实现还有很多改进空间，比如

- 提升Recover工具的召回能力
- 渲染参数调优
- 视觉压缩后的上下文布局

对以上部分进一步优化后，该功能将更加稳定好用。
