# 借鉴 TencentDB-Agent-Memory：给自研 Agent 记忆系统做一次「分层 + 符号压缩 + 混合检索」升级

> ⚠️ **声明**：本文是作者在自有 workspace 上的**私有工程实践记录**，并非 QwenPaw 框架内置功能。QwenPaw 原生提供 Scroll（情境历史）与 ReMe（长期记忆）两套记忆系统，详见 [官方文档](https://qwenpaw.agentscope.io/docs/memory)。本文描述的分层记忆、符号画布和混合检索均为作者自研的补充方案，基于 SQLite + FTS5 自建实现，不依赖也不替代 QwenPaw 原生记忆架构。

一句话：不换地基（SQLite+FTS5 很稳），加三根柱子——记忆分层（L0–L3）、符号压缩（Mermaid 任务画布）、混合检索（BM25 + 向量 RRF）。把记忆从「仓库存货」变成「可逐层下钻的图谱」。

---

## 一、为什么做这件事

看到 TencentDB-Agent-Memory 被讨论，研究了一下它到底强在哪、是否值得换。

三个结论：

1. **存储形态**：名称带「TencentDB」，但默认后端是本机 SQLite，数据落在本地文件。云端向量库需要显式配置才启用，不配不联网。
2. **强在哪**：它赢在把记忆做成有层级的金字塔——L0 对话 → L1 原子事实 → L2 场景块 → L3 用户画像，配合符号压缩和混合检索，让 Agent 不靠「海捞」而靠「逐层下钻」拿结论。
3. **弱在哪**：深绑特定框架、全流程靠 LLM 蒸馏记忆（每轮都烧模型）、benchmark 数字是自家对比。

**结论：不换，抄思路。** 借鉴「分层 + 符号 + 可下钻」三招，丢掉「框架绑定 + 全流程 LLM 烧钱 + 生态锁」三个包袱。

---

## 二、现状盘点：不是弱，是「记住了但不会组织」

以下能力对照基于作者自研的 SQLite + FTS5 记忆层（非 QwenPaw 原生架构）：

| 维度         | 自研现状                   | Tencent 那套           | 差距                    |
| ------------ | -------------------------- | ---------------------- | ----------------------- |
| 记忆存储     | 扁平表，一条一记录         | L0–L3 语义金字塔       | **缺分层**              |
| 检索         | 关键词（FTS5）             | BM25 + 向量 + RRF 混合 | **缺向量**              |
| 用户画像     | 手工维护一份 Markdown      | L3 Persona 自动蒸馏    | **缺自动化**            |
| 长任务上下文 | 全量历史存档 + 按需翻      | 符号画布压缩           | **缺压缩**              |
| 白盒追溯     | 可回原始对话轮次（反而强） | Persona→Atom→对话链    | 缺「记忆→来源」显式链接 |

一句话：**不是不行，是缺了分层组织。**

---

## 三、三根柱子（按性价比排序）

### 柱子一：记忆分层 L0–L3

把扁平表升级成带血缘的分层结构：

```
L3 用户画像（一次性 Markdown，日常偏好/习惯/目标/边界）
   ↑ 由 L2 蒸馏
L2 场景块（一次任务/一个决策来龙去脉）
   ↑ 多轮对话沉淀
L1 原子事实（一句确定的事实）
   ↑ 写入
L0 原始对话（历史，全程存档）
```

**DB 落地（小改）**：

- `memories` 表加 `layer`（0/1/2/3）+ `parent_id`（上下层下钻链）
- 加 `evidence_id`：每条 L1/L2 记录「从哪几轮对话蒸馏而来」，实现「画像→场景→事实→原始对话」全链路可回查

**关键决策：蒸馏只产出不自动覆盖。** 画像自动蒸馏容易失真，所以做成「候选画像 + traceback → 人工确认再入位」。

### 柱子二：符号记忆 —— Mermaid 任务画布

长任务执行到一半时，上下文塞满中介日志。把「已完成哪几步 / 卡在哪 / 关键产出在哪」压成一张 Mermaid 节点图，上下文里只放图（几百 token 级别），完整日志退到文件里。

- 命令：`init` 建画布 → `add` 加节点 → `update` 改状态 → `view` 输出 mermaid 段 → `drill <node_id>` 下钻读日志 → `close` 收尾
- 存储：JSON 文件存画布

在作者的长任务场景中观察到，上下文从放完整中介日志改为只放画布摘要后，无效上下文占用明显下降。

### 柱子三：混合检索 BM25 + 向量 RRF

纯关键词检索，记忆量大以后措辞不同就召回不到。加语义向量，检索时 FTS5 得分与向量相似度做 RRF 融合。

- 加 `embedding` blob 列，存量数据回填
- 本地轻量 embedding 模型（约 24M 参数，512 维），全程离线零 API 成本
- `memory-search --hybrid`：FTS5 命中 + 向量 topK 取并集，RRF 融合排序

在作者的 workspace 上观察到：用不同的措辞查询同一件事，纯关键词检索无命中，加入向量后能召回语义相关的记忆。这验证了「混合检索比纯关键词覆盖面更广」的直觉。

## 四、明确不抄

| 它的设计              | 为什么不做                             |
| --------------------- | -------------------------------------- |
| 深绑特定框架          | 自研方案要能自由改代码，不锁进别人生态 |
| 全流程靠 LLM 蒸馏记忆 | 每轮烧模型成本高；SQL 为主、LLM 点缀   |
| 云端向量后端          | 安全与隐私优先，本地文件已够用         |
| benchmark 数字        | 自家对比，不宜当硬指标                 |

---

## 五、成本与边界

- **零外部 API 费用**：嵌入走本地模型，检索全本地
- **零生态绑定**：改的全是自身的 SQLite 表结构 + 自研脚本
- **数据留在本地**：在本实现中，记忆数据存储在本地 SQLite，无云端存储
- **存量兼容**：增量迁移，历史数据原封不动

> 以上描述均为作者私有实现的情况，不代表 QwenPaw 框架原生记忆系统的行为。QwenPaw 原生记忆系统（Scroll + ReMe）的架构和配置详见[官方文档](https://qwenpaw.agentscope.io/docs/memory)。

---

## 六、复盘

- **方法论有效**：核心不是某个产品名，而是「分层组织 + 符号压缩 + 白盒可回溯 + 混合检索」四个工程思想，可以低成本自研实现。
- **最值得 echo 的点**：记忆分层让 Agent 从「每次把所有可能相关的记忆全捞出来猜」变成「先看画像/场景定方向，再按需下钻到原子事实」。
- **保持克制**：不为框架绑定和全 LLM 成本买单；值得借鉴的只是数据组织方式。

---

_如果你也在自研 Agent 的记忆层，最核心的一条建议：**先做分层，再做画布，最后补向量**。逐层把记忆从「仓库」变成「图谱」。_
