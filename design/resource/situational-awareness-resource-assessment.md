# 态势感知服务资源评估

生成时间：2026-06-22  
评估对象：Security Center / 态势感知服务上线资源需求  
评估结论状态：首期生产规格建议

## 1. 最终结论

态势感知服务首期上线按 **2 万日活被监控资产、每资产 50 条事件/日、100 万事件/日、30 天热数据、20 个运营人员同时在线、API 双实例与 DB 主备** 设计。

最终推荐规格：

| 组件 | 推荐规格 | 数量 | 说明 |
| --- | --- | ---: | --- |
| API 服务 | 4C8G | 2 台起 | 前置负载均衡；预留扩到 3-4 台 |
| 热数据主库 | 8C32G + 2TB NVMe/SSD | 1 台 | 承载 30 天热数据、索引、查询与写入 |
| 热数据备库 | 8C32G + 2TB NVMe/SSD | 1 台 | 主备/只读/灾备能力按实际数据库方案落地 |
| Redis | 2C4G | 1-2 实例 | 用于短期缓存、限流、会话或热点面板缓存 |
| 消息队列 | 托管队列或 3 节点轻量集群 | 1 套 | 用于削峰、重试隔离和 DB 写入保护 |
| 对象存储 | 180 天 1.5-3TB；1 年 3-6TB | 1 套 | 冷数据归档，需启用压缩和生命周期策略 |
| 负载均衡 | 标准七层或四层 LB | 1 套 | API 双实例入口与健康检查 |
| 监控告警 | CPU、内存、磁盘、队列堆积、写入失败、查询延迟 | 1 套 | 上线必需，不作为可选项 |

最低可上线但余量偏薄规格：

| 组件 | 最低规格 | 数量 | 前提条件 |
| --- | --- | ---: | --- |
| API 服务 | 4C8G | 2 台 | 峰值低于 300 EPS，业务峰值可控 |
| 热数据主库 | 4C16G + 1TB SSD | 1 台 | Gateway 重日志占比低，查询不做全文检索 |
| 热数据备库 | 4C16G + 1TB SSD | 1 台 | 接受较小余量 |
| Redis | 2C4G | 1 实例 | 仅缓存和限流 |
| 队列 | 托管队列 | 1 套 | 必须具备失败重试和堆积观测 |

严格建议采用推荐规格。最低规格只能作为预算受限时的短期上线方案，不适合作为安全事件爆发场景的生产基线。

| 代码位置 | 证据 | 对容量的影响 |

本评估采用的事件大小口径：

| 口径 | 估算值 | 用途 |
| --- | ---: | --- |
| 平均逻辑事件大小 | 8KB/条 | 计算每日逻辑数据量和冷归档量 |
| 热库物理占用 | 25-40KB/条 | 计算 DB 数据、索引、WAL/redo、膨胀和查询冗余 |
| Gateway 重日志占比敏感线 | 30% | 超过后热库应从 2TB 上调到 2-4TB |

## 3. 评估方法

本评估按四类互不重叠且覆盖完整资源压力的维度拆解：写入、读取、实时连接、数据生命周期。

这个拆解满足 MECE：

- 写入压力只覆盖上游系统提交事件、校验、队列、入库和失败记录。
- 读取压力只覆盖运营人员打开列表、详情、观察面板和聚合查询。
- 实时连接只覆盖 SSE/WebSocket 告警推送和在线连接维持。
- 数据生命周期只覆盖热数据、冷归档、备份、恢复和对象存储。

计算公式：

```text
日事件量 = 被监控资产数 * 单资产每日事件数
         = 20,000 * 50
         = 1,000,000 条/日

平均 EPS = 日事件量 / 86,400
         = 1,000,000 / 86,400
         = 11.6 EPS

峰值设计 EPS = 300-500 EPS
原因：安全事件具有爆发性，不能按平均 EPS 配置资源。

30 天热事件数 = 1,000,000 * 30
              = 30,000,000 条

每日逻辑数据量 = 1,000,000 * 8KB
               = 8GB/日

30 天逻辑热数据量 = 8GB * 30
                  = 240GB

30 天热库物理占用 = 30,000,000 * 25-40KB
                  = 750GB-1.2TB

推荐热库磁盘 = 热库物理占用 + 索引/WAL/redo/膨胀/备份窗口/增长余量
             = 2TB 起步
```

## 4. 资源规格解释

### 4.1 API 层

API 双实例是高可用底线，不是性能上限。100 万事件/日平均只有 11.6 EPS，但安全事件流量会出现短时爆发，因此 API 层按 300-500 EPS 验收。

推荐 `2 台 4C8G` 起步，原因：

- 足以承载 20 个运营人员在线和中等写入压力。
- 可通过负载均衡隔离单机故障。
- 预留扩容到 3-4 台，覆盖事件爆发和查询高峰。

### 4.2 热数据主库

30 天热数据为 3000 万条。按当前实现的多份投影存储方式，热库不能按请求体大小直接估算。推荐主库 `8C32G + 2TB NVMe/SSD`。

关键原因：

- 查询需要覆盖 24h/7d/30d 热数据。
- 观察面板需要 sourceSystem、eventTypeId、severity、occurredAt/receivedAt 等维度聚合或过滤。
- Gateway 日志事件包含较重文本字段，数据分布一旦偏重日志类，磁盘和索引都会快速增长。
- DB 主备和 WAL/redo 会进一步放大实际磁盘需求。

### 4.3 队列

队列是上线底线。没有队列时，事件爆发会直接冲击 DB，导致写入延迟、失败记录堆积和查询抖动。

队列必须支持：

- 上游写入削峰。
- 失败重试和死信。
- 堆积长度、消费延迟、失败率监控。
- 至少按 500 EPS 峰值写入进行验收。

### 4.4 Redis

Redis 不承载永久事件事实。它只用于：

- 热点观察面板缓存。
- 限流与短期去重。
- SSE/WebSocket 会话辅助状态。
- API 防抖和短期聚合缓存。

推荐 `2C4G` 起步。

### 4.5 冷数据与对象存储

冷数据按逻辑事件 8KB/条估算：

| 留存 | 事件数 | 逻辑数据量 | 对象存储建议 |
| --- | ---: | ---: | ---: |
| 180 天 | 1.8 亿 | 约 1.44TB | 1.5-3TB |
| 1 年 | 3.65 亿 | 约 2.92TB | 3-6TB |

对象存储建议开启压缩、分区目录和生命周期策略。冷数据不应继续压在热库主表中。

## 5. 上线边界与反对项

当前代码中的 `deploy/api/store.py` 使用 JSON 文件型 store，并通过锁进行读写。该实现适合本地验收、演示和小规模试点，不适合作为 2 万资产、100 万事件/日的生产持久化方案。

上线前必须完成或明确采用：

- 生产数据库替代 JSON 文件型 store。
- 队列削峰和失败重试。
- 按 `sourceSystem`、`eventTypeId`、`severity`、`occurredAt`、`receivedAt` 建立查询索引或聚合表。
- 30 天热数据分区或分表策略。
- 冷数据归档任务和对象存储落地。
- DB 主备、备份、恢复演练。

明确反对：

- 只按 2 万用户数估机器，不按事件量估。
- 只按平均 11.6 EPS 配置资源。
- 让热库长期保存 180 天或 1 年全量明细。
- 不上队列，直接由 API 写 DB。
- 用当前 JSON store 作为生产存储。
- 对 30 天全量明细做无索引扫描来支撑观察面板。

## 6. 扩容触发条件

触发任一条件时，应从最低规格或推荐规格继续扩容：

| 指标 | 扩容触发线 | 建议动作 |
| --- | --- | --- |
| API CPU | 持续 15 分钟超过 70% | 增加 API 实例 |
| API P95 写入延迟 | 超过 500ms | 增加 API 或检查队列/DB |
| 队列堆积延迟 | 超过 5 分钟 | 增加消费者或 DB 写入能力 |
| DB CPU | 持续 15 分钟超过 70% | 优化索引、增加只读/升级规格 |
| DB 磁盘 | 超过 70% | 扩容磁盘或提前归档 |
| 观察面板 P95 | 超过 2 秒 | 增加缓存、聚合表或只读副本 |
| Gateway 重日志事件占比 | 超过 30% | 热库从 2TB 上调到 2-4TB |

## 7. 验收标准

### 7.1 写入验收

控制点：连续 30 分钟提交 500 EPS 合法事件。  
观测点：

- 接口成功率 >= 99.9%。
- P95 写入延迟 < 500ms。
- 队列无不可恢复堆积。
- accepted event 可立即按列表和详情查询。
- 无已确认事件丢失。

### 7.2 混合异常验收

控制点：按 80% 合法、20% 非法/重复/冲突事件压测 30 分钟。  
观测点：

- 合法事件进入 accepted event。
- 非法事件进入 failed reception records。
- 重复事件符合幂等语义。
- 业务事件列表不被非法事件污染。

### 7.3 查询验收

控制点：20 个运营人员并发访问 24h/7d 观察面板、列表和详情。  
观测点：

- 页面/API P95 响应 < 2 秒。
- DB CPU 不长期超过 70%。
- 查询结果符合 sourceSystem、eventTypeId、severity、time range 过滤语义。

### 7.4 归档验收

控制点：热库达到 3000 万事件后执行冷归档。  
观测点：

- 30 天热查询不受冷归档影响。
- 冷数据可从对象存储按日期和来源追溯。
- 归档任务失败可重试。
- 归档后热库磁盘增长可控。

### 7.5 高可用验收

控制点：

- 停掉 1 台 API。
- 模拟 DB 主库故障。
- 模拟队列消费者短暂停止后恢复。

观测点：

- API 单机故障不影响整体服务入口。
- DB 故障在约定 RTO 内恢复。
- 队列恢复后可继续消费积压事件。
- 无已确认成功事件丢失。

## 8. 最终建议

本次上线应以推荐规格作为预算和部署基线：

```text
API: 2 * 4C8G, with load balancer, scalable to 3-4 instances
DB primary: 8C32G + 2TB NVMe/SSD
DB standby: 8C32G + 2TB NVMe/SSD
Redis: 2C4G
Queue: managed queue or lightweight HA queue cluster
Object storage: 180d 1.5-3TB, 1y 3-6TB
```

该规格对应的业务承诺是：2 万日活被监控资产、100 万事件/日、500 EPS 峰值验收、30 天热数据、20 个运营人员同时在线、API 双实例和 DB 主备。

如果后续增加全文检索、复杂统计大屏、工单流转、实时规则计算、跨字段任意搜索或 1 年热数据查询，本评估不再适用，需要重新进入资源评估。
