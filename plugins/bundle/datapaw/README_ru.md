DataPaw — это плагин анализа данных для QwenPaw. Он включает **12 BI-ориентированных навыков агента** — детектирование аномалий, drilldown по измерениям, атрибуционный анализ, разложение по временным факторам, адаптивные пороги, генерация HTML-отчётов и связующие навыки планирования / маршрутизации. С их помощью агент проходит BI-задачу от начала до конца на ваших локальных файлах: загрузка → очистка → анализ → drilldown → отчёт.

Наилучшие сценарии:

- **Многошаговый BI-анализ** — агент сам выбирает подходящий навык на каждом шаге и в конце выдаёт структурированный отчёт.
- **Атрибуция аномалий** — при изменении метрики последовательно отрабатывают адаптивные пороги → детектирование аномалий → разложение по временным факторам → drilldown по измерениям, и всё завершается HTML-отчётом.
- **Работа с локальными файлами** — передавайте агенту CSV / Excel / Parquet тремя способами: загрузка в чате, абсолютный путь в сообщении, или копирование в рабочую директорию агента. Анализ полностью выполняется через `execute_shell_command`.

Под капотом каждый многошаговый запуск оформляется как **DAG-граф задач**: каждый шаг — именованный узел, агент продвигается по одному узлу за раз, а прогресс сохраняется в сессии, что позволяет приостанавливать и продолжать выполнение. Состояние DAG наблюдаемо через SSE и редактируемо через REST API. **Фронтенд панели задач** (визуализация DAG + UI редактирования узлов) находится в активной разработке как часть того же самого плагина — см. раздел [Дорожная карта фронтенда](#дорожная-карта-фронтенда) ниже.

DataPaw работает полностью в вашем окружении; данные остаются там, где вы их положили.

## Быстрый старт

### Требования

| Параметр | Требование |
|---|---|
| **Версия QwenPaw** | **≥ v1.1.7** |
| **Python** | 3.10 ~ 3.13 |
| **LLM-провайдер** | Настроен в QwenPaw (DataPaw наследует активную модель) |

> Если ваша версия QwenPaw ниже v1.1.7, сначала обновитесь: `pip install --upgrade "qwenpaw>=1.1.7"`.

### 1. Установка плагина DataPaw

**Через Console (рекомендуется):**

1. Запустите QwenPaw (`qwenpaw app`), откройте http://127.0.0.1:8088/.
2. Нажмите «Plugin Manager» в левой боковой панели (под Settings), затем «Install Plugin».
3. Перетащите папку `datapaw/` в диалог установки или выберите ZIP-файл (DataPaw поставляется вместе с QwenPaw по пути `plugins/bundle/datapaw/`).
4. Дождитесь окончания установки.

**Через CLI:**

```bash
qwenpaw plugin install /path/to/datapaw
```

> После установки сделайте жёсткое обновление страницы (`Cmd+Shift+R` / `Ctrl+Shift+R`), чтобы в выпадающем списке агентов появился новый пункт «DataPaw».

### 2. Настройка

#### Модель LLM

Настройте LLM-провайдера и API-ключ в console **Settings → Models**. DataPaw наследует ту модель, что активна в данный момент — отдельная конфигурация не требуется. См. [документацию QwenPaw Models](https://qwenpaw.agentscope.io/docs/models).

#### Как передать данные агенту

DataPaw не содержит встроенных инструментов получения данных. Передать данные на анализ можно тремя способами в порядке удобства:

- **Загрузить файл в чате** — загрузка через console помещает файл в рабочую директорию агента (`media/` / `file_store/`), откуда агент его подхватывает.
- **Вставить абсолютный путь** — укажите путь в сообщении (например, `/Users/me/Downloads/data.csv`), и агент откроет файл через `read_file` / `execute_shell_command`.
- **Положить файл в рабочую директорию** — скопируйте CSV / Excel / Parquet напрямую в `~/.qwenpaw/workspaces/datapaw/` и ссылайтесь относительным путём.

Результаты анализа (промежуточные наборы данных, графики, отчёты) сохраняются в `~/.qwenpaw/workspaces/datapaw/artifacts/<session_id>/<graph_id>/<node_id>/` — см. [Раскладку артефактов](#раскладка-артефактов) ниже.

### 3. Использование

Выберите **DataPaw** в выпадающем списке агентов на странице чата. Попробуйте запрос вида:

```
Проанализируй ежедневный тренд посещаемости продукта X за декабрь 2025 и сформируй HTML-отчёт.
```

Ожидаемое поведение:

- Агент вызывает `analysis-plan-builder` и составляет план.
- Агент проходит план по одному узлу: каждый узел переходит `pending → ready → in_progress → done`.
- Финальный узел вызывает `bi-report-generation` и создаёт HTML-файл в корне артефактов.

## Встроенные навыки

Главная ценность DataPaw — в его навыках. Все 12 автоматически устанавливаются в рабочую директорию агента и активируются при старте.

### Управляющие навыки (связующее звено)

| Навык | Когда агент его использует |
|---|---|
| `data-intent-router` | Первое действие в каждом пользовательском ходе — классифицирует запрос и направляет в нужный пайплайн. |
| `analysis-plan-builder` | Превращает открытый аналитический запрос в структурированный план, подлежащий подтверждению. |
| `runtime-guide` | Правила выполнения: переиспользование, обработка ошибок, корректировка плана на лету, самопроверка. |

### Аналитические навыки

| Навык | Что делает |
|---|---|
| `bi-metric-analysis` | Сквозной пайплайн для одной метрики / области: наблюдение + детектирование аномалий + drilldown по измерениям. |
| `bi-anomaly-detection` | Пороговое детектирование точечных аномалий во временном ряду. |
| `bi-adaptive-threshold` | Выведение порога аномалии / влияния из собственной естественной вариации данных, без жёстко заданных значений. |
| `bi-attribution-analysis` | Вклад каждого измерения в изменение метрики; поддерживает аддитивные и средневзвешенные метрики. |
| `bi-dimension-drilldown` | Послойный drilldown для локализации измерений, обусловливающих движение. |
| `bi-time-impact-attribution` | Разложение изменения период-к-периоду на структурный / трендовый / событийный эффекты. |
| `bi-new-dimension-analysis` | Выявление вновь появившихся значений измерений (новый канал / SKU / функция) и оценка их влияния. |
| `bi-semantic-layer-guide` | Правила работы с семантическим слоем метрик / измерений, если он настроен. |

### Отчётность

| Навык | Что делает |
|---|---|
| `bi-report-generation` | Собирает результаты анализа и артефакты в читаемый HTML-отчёт. |

Каждый навык поставляется с `SKILL.md` (карточкой модели), а при необходимости и со вспомогательными скриптами и справочными документами в `skills/<name>/`. Агент сам читает SKILL.md по мере необходимости — вам делать ничего не нужно.

## Примеры использования

**Анализ дневного тренда с HTML-отчётом**

> Проанализируй ежедневный тренд посещаемости продукта X за декабрь 2025. Обнаружь аномалии, атрибутируй спады и сформируй HTML-отчёт.

DataPaw сначала построит DAG через `analysis-plan-builder`, проведёт `bi-anomaly-detection` → `bi-attribution-analysis` → `bi-report-generation` в порядке зависимостей, и в итоге создаст `report.html` в корне артефактов.

**Разовый простой вопрос**

> Какова медиана длительности сессии в `sessions.csv`?

Для достаточно простых вопросов DataPaw пропускает `create_plan` и отвечает напрямую через `execute_shell_command`.

## Дорожная карта фронтенда

Этот релиз содержит **backend** плагина DataPaw: агент, навыки, DAG-граф задач, REST API, SSE-события.

**Фронтенд DataPaw** — визуализация DAG, редактирование узлов в один клик, предпросмотр файлов в панели, рендеринг результатов fetch_data — активно разрабатывается как часть того же самого плагина. Он войдёт в `plugins/bundle/datapaw/` в одном из следующих релизов.

До этого момента можно полноценно работать с DataPaw через чат-агента; состояние DAG и артефакты наблюдаемы через поток SSE-событий и REST-эндпоинты ниже.

## Граф задач и API

Каждый многошаговый анализ оформляется как DAG, сохраняется в сессии и наблюдаем через REST + SSE.

### REST-эндпоинты (смонтированы на `/api/tasks/...`)

| Method | Path | Назначение |
|---|---|---|
| `GET`  | `/{session_id}` | Текущий DAG + сводка истории + сводка артефактов |
| `GET`  | `/{session_id}/dag` | Полный DAG активного графа |
| `GET`  | `/{session_id}/sop` | Текущий граф в формате YAML |
| `PUT`  | `/{session_id}/sop` | Загрузить новый SOP YAML (ставит агенту в очередь уведомление `[sop_replaced]`) |
| `PUT`  | `/{session_id}/dag` | Патч DAG (ставит уведомление `[dag_merged]`) |
| `GET`  | `/{session_id}/history/{plan_id}` | Просмотреть архивный граф |
| `GET`  | `/{session_id}/files{,/preview,/download}` | Список / предпросмотр / скачивание артефактов |

Эндпоинты записи защищены `_check_not_running` и блокируются на время работы агентского цикла. Схемы см. в `core/routers/tasks.py`.

## Архитектура

DataPaw интегрируется через систему плагинов QwenPaw. Исходный код хоста не модифицируется; всё подключается на старте.

```
plugins/bundle/datapaw/
├── plugin.json                # манифест
├── plugin.py                  # backend-точка входа: регистрация startup / shutdown хуков
├── constants.py               # общие константы + bootstrap sys.path
├── agents_setup.py            # записывает встроенный профиль агента + workspace + skills
├── hooks.py                   # runtime-патчи: smart agent factory, channel SSE, очистка при unload
├── prompts/MASTER.md          # промпт runtime-механики (DAG / plan-инструменты / правила артефактов)
├── agents/datapaw/{zh,en}/    # SOUL.md + PROFILE.md по языкам
├── skills/                    # 12 встроенных BI-навыков
└── core/                      # ядро реализации
    ├── agents/base.py         # DataPawAgent (наследует QwenPawAgent)
    ├── orchestration/         # TaskGraph / RuntimeStateManager / hint / events
    ├── routers/tasks.py       # роутер /api/tasks/*
    └── path_context.py        # переводчик путей: вид песочницы ↔ host
```

Системный промпт собирается из трёх слоёв:

1. Стандартные хост-файлы `AGENTS.md` / `SOUL.md` / `PROFILE.md` (соглашение хоста по per-agent промптам).
2. `MASTER.md` плагина — правила runtime DAG и руководство по plan-инструментам, добавляется после хост-набора.
3. Динамическая подсказка `<datapaw-analysis-environment>`, которая называет путь к workspace, корень артефактов и правила выполнения текущего запроса.

## Раскладка артефактов

Все выходные данные анализа попадают в рабочую директорию агента с разбиением по session / graph / node:

```
~/.qwenpaw/workspaces/datapaw/artifacts/
└── <session_id>/
    └── <graph_id>/
        └── <node_id>/
            ├── data.csv
            ├── chart.png
            └── report.html
```

`finish_subtask(files=...)` принимает относительные пути (без префикса `artifacts/`), а runtime разрешает их обратно в абсолютные пути хоста через `PathContext.resolve_artifact_path`.
