# Task 5.3 会话所有权、显式分享与服务端查询隔离设计

## 1. 目标

在不改变现有富消息、工具执行过程、审批、附件、图片、错误与最终回答展示协议的前提下，为 Console 会话建立完整的多用户访问边界：

- 每个会话具有唯一所有者。
- 会话默认仅所有者可访问。
- 所有者可以将会话显式分享给仍具备当前 Agent 使用权限的平台用户。
- 被分享用户只能查看完整会话历史，不具备任何写权限。
- 管理员默认不获得其他用户会话的读取权限；管理员同样遵循显式分享规则。
- PostgreSQL 成为会话所有权、分享关系和查询授权的唯一权威来源。
- 现有 `ChatManager`、`SafeJSONSession` 与 Agent 工作区文件暂时保留为内容投影，完整历史回放切换留给 Task 5.5。

本任务必须同时实现前端交互约束、后端接口鉴权和 PostgreSQL RLS，不能仅依赖隐藏菜单或禁用按钮。

## 2. 已确认的权限语义

### 2.1 会话所有者

所有者可以：

- 查看完整会话历史和工具执行过程。
- 继续发送消息。
- 停止自己的运行、处理自己的审批请求。
- 重命名、置顶、归档、恢复和删除会话。
- 使用当前会话允许的模型与项目目录能力。
- 管理会话的只读分享成员。

历史消息、工具事件和已完成审批作为审计事实不可被直接编辑。

### 2.2 只读分享成员

分享成员可以查看：

- 用户与助手消息。
- Thinking、工具调用、工具输出与进度。
- 已发生的审批过程及结果。
- 文件、图片、错误、最终回答及其他现有富事件。

分享成员不能：

- 发送消息或上传附件。
- 使用语音输入继续该会话。
- 停止运行或提交审批决定。
- 重命名、置顶、归档、恢复或删除会话。
- 切换会话模型、项目目录或其他运行参数。
- 添加、删除或修改分享成员。

前端展示明确的“只读分享”标识和只读说明；后端对所有写接口独立执行所有者检查。

### 2.3 管理员

管理员拥有普通用户的全部基础能力，但管理角色不会自动扩大私人会话读取范围：

- 管理员可以创建并拥有自己的会话。
- 管理员只有在会话所有者显式分享后才能读取其他用户会话。
- 管理员未被分享时访问其他用户会话统一返回 `404`。
- 管理员审计读取属于后续独立能力，不在 Task 5.3 中隐式实现。

## 3. 分享资格与生命周期

会话只能分享给同时满足以下条件的用户：

1. 用户存在且处于启用状态。
2. 用户不是会话所有者。
3. 用户尚未成为该会话分享成员。
4. 用户当前具备该会话所属 Agent 的使用权限。

“具备 Agent 使用权限”包括所有者、有效成员或平台公用 Agent 的可使用权限，但不包括仅用于保留历史的 `historical_read_only` 状态。

会话分享不会授予 Agent 权限，二者必须分别维护：

- Agent 权限被撤销时，分享记录保留，但用户立即无法访问会话。
- Agent 权限恢复后，仍存在的分享记录重新生效。
- 用户被禁用、Agent 被删除或会话被删除时，分享访问立即失效。
- 会话所有者撤销分享后，成员立即且永久失去访问，除非所有者重新添加。

## 4. 推荐架构

### 4.1 权威数据与内容投影

采用 PostgreSQL 权限权威与现有文件内容投影的渐进式架构：

```text
浏览器
  -> 会话 API / Console 写入口
      -> PostgreSQL conversations + conversation_members（权限权威）
      -> ChatManager / SafeJSONSession（现有内容投影）
      -> Task 5.2 messages / run_events / tool_calls（持续持久化）
```

选择该方案的原因：

- 保持原有会话富事件和工具过程展示协议不变。
- 避免在 Task 5.3 提前重写历史回放链路。
- 所有访问先经过 PostgreSQL 权限检查，不能直接通过 JSON 文件绕过。
- 为 Task 5.4 的实时流隔离和 Task 5.5 的 PostgreSQL 历史回放提供稳定边界。

不采用以下方案：

- JSON 文件作为分享权威：无法可靠实现数据库查询隔离与 RLS。
- Task 5.3 直接全面切换 PostgreSQL 回放：变更范围过大，容易破坏现有工具事件展示。

### 4.2 数据模型

复用现有 `conversations` 和 `conversation_members`，通过新迁移补齐约束、索引和 RLS。

`conversations` 保存：

- 会话 ID。
- 所有者用户 ID。
- Agent 数据库 ID。
- 标题、状态、频道、创建与更新时间。
- Task 5.2 已使用的运行与消息关联关系。

`conversation_members` 保存：

- 会话 ID。
- 用户 ID。
- 角色，Task 5.3 仅允许 `viewer`。
- 分享人和创建时间等必要审计字段。

数据约束：

- `(conversation_id, user_id)` 唯一。
- 所有者不能作为分享成员插入。
- Task 5.3 不预留编辑者、协作者等未确认角色。
- 分享删除采用明确删除成员关系；会话和历史内容仍按现有逻辑删除策略处理。

## 5. 服务端访问规则

### 5.1 读取授权

会话可读条件为：

```text
当前用户是会话所有者
或
当前用户存在 viewer 分享记录
且用户启用
且用户当前仍有 Agent 使用权限
```

任何条件不满足时统一返回 `404`，避免通过 `403` 判断会话是否存在。

### 5.2 写入授权

所有会话写入口都必须要求当前用户是所有者，包括：

- Console 发送消息。
- 停止运行、重连写通道和审批处理。
- 重命名、置顶、归档、恢复和删除。
- 模型、项目目录、附件与运行参数变更。
- 分享成员增删。

前端必须把当前目标会话 ID 传给写入口。服务端不能仅根据请求中的 `user_id` 或 Agent 推断写权限，也不能在分享查看者提交时静默创建或切换到其他会话。

### 5.3 后台运行身份

后台持久化和异步任务必须继承运行发起者的用户身份与会话所有权上下文：

- 不使用管理员身份作为通用后台身份。
- 不设置可绕过所有租户隔离的全局用户。
- 浏览器断开后，TaskTracker 可以继续执行，但权限上下文保持为原发起者。

## 6. API 设计

### 6.1 会话查询

```http
GET /api/chats?scope=all|owned|shared
GET /api/chats/{chat_id}
```

- `all`：默认值，返回自己的会话与分享给自己的会话。
- `owned`：仅返回自己的会话。
- `shared`：仅返回分享给自己的会话。

会话 DTO 新增：

```json
{
  "access_role": "owner | viewer",
  "read_only": true,
  "shared_by": "username"
}
```

所有者返回 `access_role=owner`、`read_only=false`；分享成员返回 `access_role=viewer`、`read_only=true`。

### 6.2 分享成员管理

```http
GET    /api/chats/{chat_id}/members
GET    /api/chats/{chat_id}/share-candidates
POST   /api/chats/{chat_id}/members
DELETE /api/chats/{chat_id}/members/{user_id}
```

- 只有所有者可以查看完整成员列表、候选人和修改成员。
- 分享成员只能获知自己当前以只读身份访问，不能枚举其他成员。
- 候选人接口只返回启用、具备 Agent 使用权限且尚未分享的用户。
- 重复添加同一成员采用幂等结果，不产生重复记录。
- 成员资格在读取时再次校验，不依赖候选列表的历史结果。

## 7. 前端设计

### 7.1 会话列表

会话抽屉和“会话”管理页面增加一致的范围筛选：

- 全部。
- 我的。
- 分享给我的。

分享会话展示“只读分享”标识，不能出现所有者专属的重命名、置顶、归档、恢复和删除菜单。

### 7.2 会话详情

打开分享会话时：

- 顶部展示只读说明和分享来源。
- 完整渲染历史消息与原有工具执行过程。
- 禁用或隐藏输入框、发送、附件、语音、模型、项目目录和审批控件。
- 不订阅具有写能力的运行控制通道。

所有者会话保持现有交互和功能，不改变富消息结构。

### 7.3 分享交互

所有者可在会话操作中打开“分享会话”对话框：

- 展示已分享成员。
- 从服务端候选列表选择用户。
- 添加时明确标注“仅查看”。
- 支持立即撤销。
- 服务端返回资格变化时刷新列表并展示明确错误。

## 8. PostgreSQL RLS

新迁移暂定为 `0009_conversation_sharing_rls`。

应用连接使用已验证的 `qwenpaw_runtime` 角色。该角色为非超级用户且没有 `BYPASSRLS`，能够实际受 RLS 约束。

每个请求事务设置当前用户上下文，例如：

```sql
SET LOCAL qwenpaw.user_id = '<uuid>';
```

连接归还连接池前必须结束事务并清除上下文，防止用户身份泄漏到下一请求。

策略范围：

- `conversations`：所有者或当前有效 viewer 可查询；只有所有者可更新或删除。
- `conversation_members`：所有者可查询和增删；viewer 只能验证自己的有效关系，不可枚举成员。
- `messages`、`attachments`、`approval_requests`：读取范围继承所属会话；写入只允许会话所有者或其合法后台运行上下文。
- 已存在的 `run_events`、`tool_calls` 等关联表同步采用所属会话约束，不能只保护会话主表。

应用层鉴权与 RLS 同时保留：应用层提供业务错误和 DTO 控制，RLS 作为防止遗漏查询条件的数据库防线。

## 9. 现有会话迁移与兼容

### 9.1 幂等补录

提供一次性迁移入口和可重复执行的协调逻辑：

- 扫描每个 Agent 现有 `chats.json`。
- 按 `ChatSpec.id`、Agent、所有者、标题、状态和时间幂等补录到 `conversations`。
- 不删除、不移动、不改写现有会话和 Session 内容文件。
- 输出扫描、补录、跳过和异常数量，便于验收。

### 9.2 旧 `default` 用户兼容

旧会话中的 `user_id=default` 不能直接写入 UUID 外键：

- 仅在能够根据 Agent 的已登记所有者安全确定真实用户时，将旧 `default` 会话映射给该 Agent 所有者。
- 不把所有旧会话统一归属给第一个管理员。
- 无法安全识别所有者的记录保留原文件并写入异常报告，不擅自扩大访问范围。
- 兼容补录完成后，原管理员自己的旧会话仍可见，其他用户不会获得访问。

### 9.3 新会话即时登记

新建空会话时立即创建 PostgreSQL 会话元数据，不再等到首次 Run 才登记。重命名、归档、恢复和删除同步更新 PostgreSQL。

## 10. 一致性与失败恢复

PostgreSQL 是权限权威，文件是当前内容投影。两种存储无法形成单一原子事务，因此采用幂等协调与失败关闭：

- PostgreSQL 中不存在合法会话记录时，接口不能退回 JSON 文件直接授权。
- 创建或同步权限元数据失败时返回明确 `503`，不会向其他用户暴露未完成登记的会话。
- 协调器可重复修复 PostgreSQL 元数据与 `ChatSpec` 投影的短暂不一致。
- 不因数据库暂时不可用而降级为全局文件访问。
- 任何异常同步都保留原数据并记录可诊断结果，不自动删除文件或数据库历史。

删除操作沿用逻辑删除或状态终结策略，避免误删工具事件、审批记录和附件引用。物理清理不属于 Task 5.3。

## 11. 测试设计

### 11.1 服务层与 API 测试

使用真实 PostgreSQL 建立管理员、用户 A、用户 B、用户 C 与同一 Agent：

1. A 创建会话后只有 A 可见。
2. A 分享给 B 后，B 可以读取完整历史。
3. B 的所有写请求被服务端拒绝。
4. C 访问返回 `404`。
5. 未被分享的管理员访问同样返回 `404`。
6. A 撤销分享后，B 立即无法访问。
7. 撤销 B 的 Agent 使用权限后，分享记录保留但访问失效；恢复 Agent 权限后重新可读。
8. 禁用 B、删除 Agent 或删除会话后访问失效。
9. 候选人过滤和重复添加满足资格与幂等要求。
10. 现有所有者会话操作保持正常。

### 11.2 RLS 测试

- 使用非超级用户 `qwenpaw_runtime` 执行查询。
- 验证遗漏应用层租户条件时，数据库仍阻止跨用户读取。
- 验证更新、删除、成员管理和消息写入仅对所有者开放。
- 验证连接池复用不会继承上一用户的 `qwenpaw.user_id`。
- 验证后台运行保持原发起者身份。

### 11.3 前端测试

- 三种范围筛选数量与列表内容正确。
- 分享会话标识、只读横幅和分享来源正确。
- viewer 不渲染所有者操作菜单和写控件。
- 即使手工构造请求，后端仍拒绝写操作。
- 富消息、工具过程、审批历史、文件、图片、错误和最终回答渲染无回归。

## 12. 用户可视化验收流程

1. 用户 A 创建会话并完成一轮包含工具调用的对话。
2. A 打开“分享会话”，选择具备该 Agent 权限的用户 B。
3. B 在“分享给我的”中看到该会话和“只读分享”标识。
4. B 打开后能够看到完整消息和工具执行过程，但不能发送、审批或修改会话。
5. 用户 C 和未被分享的管理员看不到该会话，直接访问返回不存在。
6. A 撤销分享，B 的列表和已打开页面立即失效。
7. 再次分享给 B，随后撤销 B 的 Agent 权限，确认会话不可访问；恢复 Agent 权限后确认只读访问恢复。
8. 回归验证 A 自己的聊天、停止、审批、重命名、归档和删除功能正常。

## 13. 分步实施边界

具体实施计划必须拆成可独立验收的前后端小步，每一步都保持现有功能可运行：

1. 数据模型、RLS 与真实 PostgreSQL 隔离测试。
2. 会话权限服务、现有会话补录和所有者 API。
3. 分享成员 API 与前端分享对话框。
4. 分享列表、只读详情与全部后端写入口保护。
5. 综合回归、迁移报告和用户可视化验收。

每一步完成后先提供测试结果和界面验收方法，经用户确认后再进入下一步。

## 14. 非目标与后续任务

Task 5.3 不包含：

- 管理员审计读取其他用户私人会话。
- 可编辑协作者或会话所有权转移。
- 外部访客、匿名链接或公开分享。
- 将全部历史消息切换为 PostgreSQL 回放。
- 分享成员订阅实时 SSE、运行状态及审批流隔离；该能力属于 Task 5.4。
- 完整 PostgreSQL 历史回放替换与前端投影切换；该能力属于 Task 5.5。

Task 5.3 只建立稳定、可验证的所有权、显式只读分享和服务端查询隔离基础。
