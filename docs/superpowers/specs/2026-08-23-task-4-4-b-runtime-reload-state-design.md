# Task 4.4-B 运行配置热重载状态设计

## 目标

运行配置已成功持久化、但当前 Agent 热重载失败时，系统必须明确返回并展示“已保存、待重载”，不得把持久化成功误报为保存失败，也不得回滚成未知状态。

## 状态模型

本任务只引入两个对用户有意义的运行状态：

- `applied`：配置已持久化，当前运行实例也已成功加载。
- `pending_reload`：配置已持久化，但当前运行实例尚未成功加载。

状态存放在当前服务进程的 `app.state` 中。服务重启后，Agent 从磁盘配置重新启动，原待重载状态自然失效，因此无需增加数据库字段或迁移。

## 后端流程

1. 沿用 Task 4.4-A 的 `If-Match/config_version` 校验。
2. 在路径锁内完成 `agent.json` 与配置修订持久化。
3. 释放路径锁后同步调用当前 Agent 的 `reload_agent`。
4. 重载成功时记录 `applied`；返回 `False`、管理器缺失或抛出异常时记录 `pending_reload`。
5. 保存接口始终返回已经持久化的运行配置，不因一般热重载失败回滚。
6. 新增运行状态查询接口和手动重试接口；重试成功后清除待重载状态。

Embedding 配置已有独立的测试、应用和安全回滚语义。本任务不改变该路径，避免把“配置本身不可应用”错误归类为一般 Agent 热重载失败。

## 前端流程

1. 保存接口成功后查询运行状态。
2. `applied` 显示原有“保存成功”。
3. `pending_reload` 显示持久化成功的警告，并提供“重试重载”。
4. 重试成功后提示已应用并移除警告；失败则保留警告。
5. 页面首次加载时也查询运行状态，使待重载提示在页面切换后仍可见。

## 兼容性

- 保持 `PUT /workspace/running-config` 的响应体仍为 `AgentsRunningConfig`。
- 单用户与多用户页面共用运行状态接口；多用户的版本保护保持不变。
- 不修改其他使用 `schedule_agent_reload` 的功能，仅收敛运行配置保存路径。

## 验收

- 正常保存后状态为 `applied`。
- 模拟 `reload_agent` 异常后，文件与版本已保存，状态为 `pending_reload`。
- 重试成功后状态回到 `applied`。
- 前端显示“已保存、待重载”，不显示“保存失败”。
- Task 4.4-A 的并发冲突行为继续通过。
