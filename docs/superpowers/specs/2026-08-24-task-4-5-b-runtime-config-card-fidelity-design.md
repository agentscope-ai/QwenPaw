# Task 4.5-B 运行配置卡片保真设计

## 1. 目标

在 Task 4.5-A 已建立运行配置访问边界的基础上，逐项核验并修复原运行配置页面的全部配置卡片，确保多用户架构没有改变原有配置字段、页面交互、数据落盘、服务端校验、热重载和失败恢复行为。

本任务必须保证页面显示的目标 Agent 与所有实际读写接口操作的目标 Agent 完全一致。管理员显式代管用户 Agent 时，主表单和卡片内部的独立接口都必须操作被代管 Agent，不能继续隐式依赖侧边栏当前选中的 Agent。

## 2. 已确认范围

### 2.1 包含

- 核对原运行配置页面中每个配置卡片及卡片内部的全部可交互字段。
- 核对表单字段、独立接口字段与后端配置模型之间的对应关系。
- 验证配置加载、修改、前端校验、后端校验、持久化、重新加载和热重载状态。
- 验证失败后页面状态、文件内容和运行时状态保持明确且可恢复。
- 修复管理员代管页面中独立接口仍可能操作侧边栏当前 Agent 的目标错位问题。
- 验证 owner、collaborator、管理员自己的 Agent、管理员显式代管和仅使用用户的权限边界。
- 保持 Task 4.4-A 的配置版本和并发冲突保护。
- 保持 Task 4.4-B 的 `applied/pending_reload` 状态与重试入口。
- 对记忆、Embedding、ADBPG 和循环卡片验证配置层面的加载、保存、校验、热重载和失败恢复。
- 每个内部任务都提供可以通过真实页面和后端证据验收的结果，并等待用户确认后继续。

### 2.2 不包含

- 不在本任务验证记忆提取、检索、梦境、每日论文等完整业务运行效果；这些属于 Task 4.5-C。
- 不在本任务验证循环模式执行任务时的完整终止、预算、Rubric 和任务完成效果；这些属于 Task 4.5-C。
- 不改变 `agent.json` 作为当前 Agent 运行配置内容源的存储边界。
- 不新增数据库表或迁移。
- 不迁移运行配置内容到 PostgreSQL。
- 不重新设计原有配置字段、默认值、配置卡片布局或产品语义。
- 不把用户个人时区错误地改造成 Agent 级配置。
- 不修改模型供应商和模型管理权限；普通用户仍只能使用管理员配置的模型。
- 不执行 Git commit、push、reset、分支或工作树操作。

## 3. 原功能基线与卡片清单

运行配置页面当前由固定卡片、后端选择驱动的动态卡片和独立保存控件组成。

| 配置区域 | 主要能力 | 当前数据路径 | 4.5-B 验收重点 |
|---|---|---|---|
| React Agent 基础设置 | 语言、个人时区、Shell 超时、Shell 程序、项目目录、增强编码能力、标题生成、记忆后端、计划模式 | 主运行配置接口、语言接口、个人时区接口、项目目录接口、编码模式接口、计划接口 | 独立接口目标 Agent 一致；即时保存与主表单保存互不覆盖 |
| Agent Loop | 迭代限制、死循环检测、Rubric、Goal、Mission、自定义模式和 Gate | `AgentsRunningConfig.loop` | 折叠区域字段不丢失；自定义数组和 Gate 参数完整往返 |
| LLM 重试 | 启停、重试次数、退避基础值和上限 | `AgentsRunningConfig.llm_*` | 前后端关联校验一致，尤其上限不得小于基础值 |
| LLM 限流 | 并发、QPM、暂停、抖动、获取超时 | `AgentsRunningConfig.llm_*` | 数值边界、0 表示禁用的语义和热重载状态 |
| Light Context | 对话路径、估算、压缩、Scroll、工具结果裁剪、视觉压缩 | `AgentsRunningConfig.light_context_config` | 动态/折叠字段完整保存，不覆盖未展开字段 |
| ReMe Light Memory | 自动记忆、梦境、每日论文、搜索、收件箱和调度参数 | `AgentsRunningConfig.reme_light_memory_config` | 主配置保存、状态提示、重载与待重建状态保持一致 |
| ADBPG Memory | 服务地址、密钥、隔离、超时、自动搜索 | `AgentsRunningConfig.adbpg_memory_config` | 可选对象初始化、密钥字段不丢失、后端切换完整往返 |
| Embedding Model | 后端、密钥、地址、模型、维度、缓存、批量和输入限制 | `reme_light_memory_config.embedding_model_config` | 连接验证、热更新、失败回滚和并发变更保护 |
| 工具执行级别 | STRICT、SMART、AUTO、OFF | 运行配置接口代理写回 Agent Profile | 配置文件与 Profile 一致，使用者不能修改 |

## 4. 设计原则

### 4.1 目标 Agent 必须显式传递

运行配置页面建立单一 `RunningConfigRequestContext`：

```ts
interface RunningConfigRequestContext {
  agentId?: string;
  governance?: boolean;
}
```

- 普通编辑路径可以省略 `agentId`，沿用当前选中 Agent。
- 管理员代管路径必须携带目标 `agentId` 和 `governance=true`。
- 页面内所有 Agent 级读取和写入都消费同一个上下文。
- 卡片不能自行从全局 Store 推断治理目标。
- 个人时区不消费 Agent 上下文，因为它属于当前登录用户。

本任务优先扩展已有接口的可选请求上下文，不创建第二套治理专用业务逻辑。

### 4.2 区分统一保存与即时保存

当前页面存在两种交互：

1. 主表单字段通过底部“保存”统一提交。
2. 语言、时区、项目目录、编码能力和计划模式等控件通过独立接口即时保存。

两类交互继续保留，避免侵入原有使用习惯。但需要建立明确规则：

- 即时保存字段不被后续主表单保存覆盖。
- 主表单保存失败不能伪装成即时保存字段失败。
- 即时保存失败时恢复控件原值并显示错误。
- 每个即时保存接口都必须具有与完整运行配置写接口一致的 Agent 编辑授权。
- 管理员代管时，除个人时区外，所有即时保存接口必须操作治理目标 Agent。

### 4.3 完整配置往返而非重建配置

前端保存继续以服务端加载的完整配置为基线，只覆盖页面实际修改的字段。嵌套对象采用递归合并，数组字段采用完整替换，防止以下数据丢失：

- 尚未渲染的动态卡片字段。
- 折叠面板中未注册到当前表单的字段。
- 后端新增但当前前端不认识的兼容字段。
- 自定义循环模式和 Gate 数组中的标识及参数。

保存成功后必须使用服务端返回配置更新前端基线，不能继续以提交前配置作为下一次合并基础。

### 4.4 服务端是最终校验边界

- 前端校验用于即时反馈，不能代替 Pydantic/业务校验。
- 后端收到完整配置后必须先验证，再写文件和递增配置版本。
- 校验失败返回稳定的 4xx 错误，不写文件、不递增版本、不触发热重载。
- 权限失败在读取目标文件或执行运行时副作用之前返回 `403`。
- 版本冲突继续返回 `409 config_version_conflict`。

### 4.5 持久化成功与运行时应用分离

- 配置文件保存成功且热重载成功：状态为 `applied`。
- 配置文件保存成功但 Agent 整体重载失败：状态为 `pending_reload`，保留已保存内容并允许重试。
- Embedding 等原有局部热更新失败且已有安全回滚契约：执行原有字段级回滚，不覆盖无关并发变更。
- 局部回滚遇到同字段并发修改：报告回滚冲突，不静默覆盖新值。
- 任何失败都不得让页面只显示笼统“保存成功”。

## 5. 请求上下文与组件边界

### 5.1 页面级上下文

`AgentConfigPage` 负责从普通路径或治理查询参数构造唯一的请求上下文，并将其传给页面 Hook 和包含独立接口的卡片。

推荐接口：

```ts
interface AgentConfigTarget {
  requestContext?: RunningConfigRequestContext;
  canEdit: boolean;
  isGovernance: boolean;
}
```

组件只消费目标上下文，不读取 URL，也不自行判断管理员身份。

### 5.2 主表单 Hook

`useAgentConfig` 继续负责：

- 访问能力加载。
- 完整配置或只读摘要分支。
- 配置版本管理。
- 主表单字段初始化和合并。
- 主表单保存。
- `pending_reload` 状态与重试。
- Agent 语言即时保存。
- 用户个人时区即时保存。

复杂的完整配置合并逻辑应提取为纯函数并单独测试，避免 Hook 同时承担递归合并细节和网络状态管理。

### 5.3 基础设置卡片

`ReactAgentCard` 及其内部项目目录、编码能力、计划模式控件接收相同的 Agent 请求上下文。对应 API 模块统一支持可选上下文：

- `projectDirectoryApi.get/update`
- `codingModeApi.get/toggle`
- `planApi.getPlanConfig/updatePlanConfig`

普通路径保持原接口行为；治理路径由服务端显式解析目标 Agent 并检查管理员治理权限。

### 5.4 其他配置卡片

主表单卡片不各自调用保存接口，继续通过 Form 与 `useAgentConfig` 协作。其职责限于：

- 渲染字段。
- 提供前端字段校验。
- 保持动态字段和数组字段注册正确。
- 触发已有的 Embedding 验证、状态查询或维护动作时使用相同请求上下文。

## 6. 后端授权设计

所有 Agent 级配置接口采用与 Task 4.5-A 相同的能力语义：

| 主体 | 读取完整配置 | 修改 Agent 配置 | 修改个人时区 |
|---|---:|---:|---:|
| owner | 是 | 是 | 是，仅自己的偏好 |
| collaborator | 是 | 是 | 是，仅自己的偏好 |
| user（仅使用） | 否，仅安全摘要 | 否 | 是，仅自己的偏好 |
| 平台公用 Agent 普通使用者 | 否，仅安全摘要 | 否 | 是，仅自己的偏好 |
| 管理员自己的 Agent | 是 | 是，普通路径 | 是，仅自己的偏好 |
| 管理员显式代管他人 Agent | 是 | 是，治理路径 | 是，但仍只修改管理员自己的偏好 |
| 管理员未显式进入治理 | 否 | 否 | 是，仅自己的偏好 |

管理员身份不能让独立接口静默绕过目标 Agent 治理入口。治理请求必须明确包含目标 Agent，并复用现有管理员治理审计边界。

## 7. 错误与恢复设计

### 7.1 页面加载失败

- 访问上下文失败：停止加载配置与卡片独立接口。
- 完整配置失败：显示页面级重试，不以默认配置覆盖服务端内容。
- 单个即时设置加载失败：该设置显示错误或不可用状态，不伪造默认值供用户保存。
- 管理员治理目标不存在或失效：清理页面数据并返回智能体治理列表。

### 7.2 前端校验失败

- 阻止主表单请求。
- 保留用户输入和当前标签页。
- 将错误定位到具体字段；动态或折叠字段必须可被定位。

### 7.3 服务端校验失败

- 不修改文件、版本和运行时。
- 页面保留编辑内容并显示服务端错误。
- 点击重置重新加载服务端有效配置。

### 7.4 权限变化

- 保存返回 `403` 时重新读取访问能力。
- 已降为仅使用权限时退出编辑表单并显示安全摘要。
- 不继续执行卡片内部的独立保存。

### 7.5 热重载失败

- 已保存但待重载使用持续可见警告。
- 用户可显式重试。
- 重试成功后状态切换为 `applied`。
- 重试失败继续保持 `pending_reload`，不丢失错误上下文。

## 9. 测试策略

### 9.1 纯函数与组件测试

- 完整配置深度合并不丢失未知字段。
- 数组字段按用户提交完整替换，不按对象索引错误合并。
- 自定义 Gate 的 ID、类型、启停和参数完整保留。
- 每张卡片的字段名与 TypeScript 配置类型一致。
- 独立控件接收并转发统一请求上下文。
- 即时保存失败恢复原值。

### 9.2 后端单元与集成测试

- Pydantic 数值和关联校验失败时无持久化副作用。
- owner/collaborator 正常读写。
- user 所有 Agent 配置写接口均在副作用之前返回 `403`。
- 管理员只有显式治理上下文可以读写他人 Agent。
- 每种合法配置保存后可以再次读取并等价解析。
- 配置版本只在实际成功保存时递增。
- 热重载成功、待重载、重试成功和重试失败状态明确。
- Embedding 回滚不覆盖无关并发修改，并能报告同字段冲突。

### 9.3 浏览器验收

每个内部任务至少包含：

1. 页面修改前截图或状态记录。
2. 修改并触发对应保存交互。
3. 刷新页面确认服务端回读。
4. 检查目标 Agent 配置文件或读取接口。
5. 切换另一个 Agent 确认没有串写。
6. 使用无权限账号验证只读或 `403`。
7. 构造一个失败路径验证页面恢复与服务端无错误落盘。

## 10. 验收标准

- 所有原运行配置卡片都有明确的字段和数据链路清单。
- 管理员代管页面的所有 Agent 级操作只作用于治理目标 Agent。
- 侧边栏当前 Agent 变化不会造成代管目标串写。
- 普通编辑路径保持原有交互与数据语义。
- 所有主表单字段和即时保存字段刷新后均能正确回读。
- 折叠、动态和未渲染字段不会因保存其他字段而丢失。
- 前端校验失败和后端校验失败都不会产生持久化或热重载副作用。
- 热重载失败能够区分“未保存”和“已保存、待重载”。
- Embedding 原有局部热更新和失败回滚行为继续成立。
- owner、collaborator、管理员普通路径、管理员治理路径和 user 只读路径均通过前后端测试。
- 每个内部任务均经过用户页面验收确认。
- 不提前把 Task 4.5-C 的记忆与循环综合运行验收混入本任务。

## 11. 方案取舍

### 11.1 采用：逐卡片纵向闭环

按配置区域同时检查前端、API、后端、持久化和运行时，能够在每一步提供真实可见成果，并及时发现跨层目标错位和字段丢失问题。

### 11.2 不采用：只补前端表单测试

这种方式无法证明后端授权、目标 Agent、文件落盘和热重载正确，也无法发现管理员代管时独立接口操作错误 Agent 的问题。

### 11.3 不采用：重写为单一配置接口

虽然统一接口表面更简单，但会改变语言、个人时区、项目目录、编码能力和计划模式的原有即时保存交互，侵入范围过大，不符合当前保真目标。
