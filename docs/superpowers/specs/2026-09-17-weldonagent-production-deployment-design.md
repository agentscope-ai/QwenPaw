# WeldonAgent 生产部署与外部白标设计

**状态：** 已确认
**日期：** 2026-09-17
**适用范围：** Linux Docker Engine、Windows Docker Desktop（Linux 容器模式）

## 目标与边界

本设计为多用户版本提供可重复的新服务器初始化流程，使管理员从 Clone 仓库开始即可完成镜像构建、PostgreSQL 初始化、数据库迁移、应用初始化和服务启动。源码、持久数据、密钥和运行状态相互分离，正式环境不依赖仓库内的 `tmp`、`data` 或开发者用户目录。

对外品牌统一为 **WeldonAgent**。登录页、聊天、浏览器标题、部署入口、容器名称和公开运维文档中不得出现 QwenPaw 或 CoPaw。内部 Python 包名、导入路径、数据库迁移实现、兼容环境变量和协议标识保持不变，避免破坏现有数据、插件和后续选择性合并上游更新。

本阶段交付全新部署和未来备份恢复能力，不迁移当前机器的数据，不删除当前 `tmp/task-2-1-acceptance/working`。

## 生产目录与数据所有权

代码目录只存放 Git 跟踪的源码和构建定义，持久数据放在独立数据根目录。更新源码、重新 Clone 或重建容器不得覆盖数据目录。

| 内容 | Linux 默认位置 | Windows 默认位置 | 容器位置 |
|---|---|---|---|
| 源码 | `/opt/weldonagent` | `D:/Apps/WeldonAgent` | `/app` |
| 应用数据根 | `/var/lib/weldonagent` | `D:/WeldonAgentData` | `/data` |
| 工作数据 | `<数据根>/working` | `<数据根>/working` | `/data/working` |
| 密钥凭据 | `<数据根>/secrets` | `<数据根>/secrets` | `/data/secrets` |
| 应用备份 | `<数据根>/backups` | `<数据根>/backups` | `/data/backups` |
| 日志 | `<数据根>/logs` | `<数据根>/logs` | `/data/logs` |
| PostgreSQL | `<数据根>/postgres` | `<数据根>/postgres` | `/var/lib/postgresql/data` |

运行态 PID、锁和健康状态放在容器内 `/data/run`。管理员可以通过环境文件修改数据根目录；生产示例不得将其默认设置为源码下的 `tmp`、`data` 或相对缓存目录。

密钥目录、生产环境文件和数据库数据不进入 Git，也不进入应用镜像。Linux 部署账户应独占数据目录写权限；Windows Docker Desktop 部署应将数据根目录限制给运行 Docker Desktop 的管理员账户。

## Docker 拓扑与命名

Linux 和 Windows 使用同一套 Linux 容器镜像和 Compose 定义。Windows 不维护独立应用镜像，也不在容器内依赖 PowerShell 或盘符路径。

| 对象 | 对外名称 |
|---|---|
| Compose 项目 | `weldonagent` |
| 应用服务及容器 | `agent-app` |
| 初始化服务 | `agent-init` |
| PostgreSQL 服务及容器 | `agent-pg` |
| 默认数据库 | `weldonagent` |
| 默认 schema | `weldonagent` |

`agent-pg` 仅在 Compose 内网开放 5432，不直接映射宿主机端口。`agent-app` 默认将宿主机 `127.0.0.1:18089` 映射到应用端口；需要局域网或反向代理访问时，由管理员在环境文件中显式修改监听地址。公网部署应由独立反向代理提供 TLS，应用继续保留自身多用户认证。

Compose 的健康检查验证 PostgreSQL、数据库版本、应用核心智能体和多用户模式，不以首页 HTTP 200 作为唯一就绪条件。应用容器在数据库不可用时不得进入已就绪状态。

## 配置兼容层

管理员只接触 `WELDON_*` 配置项，Compose 将其映射成容器内部现有的兼容变量。内部代码继续读取原环境变量和 Python 包，不进行大范围命名空间重构。

生产环境模板至少包含：

| 对外变量 | 用途 |
|---|---|
| `WELDON_DATA_ROOT` | 宿主持久数据根目录 |
| `WELDON_BIND_ADDRESS` | 宿主监听地址，默认 `127.0.0.1` |
| `WELDON_PORT` | Web 端口，默认 `18089` |
| `WELDON_DB_NAME` | 数据库名称，默认 `weldonagent` |
| `WELDON_DB_SCHEMA` | schema，默认 `weldonagent` |
| `WELDON_DB_USER` | 应用数据库账户 |
| `WELDON_DB_PASSWORD` | 随机强密码 |
| `WELDON_TIMEZONE` | 容器时区，默认 `Asia/Shanghai` |

环境模板不包含真实密码。实际 `deploy/.env` 被 Git 和 Docker 构建上下文排除。内部数据库 URL 由 Compose 根据这些字段组装，避免要求用户手工对密码做 URL 编码。

## 新服务器初始化

管理员执行以下逻辑流程：

1. 安装 Git、Docker Engine 或 Docker Desktop，以及 Compose v2。
2. Clone 仓库到任意正式源码目录。
3. 复制生产环境模板为 `deploy/.env`，设置数据根目录和数据库随机密码。
4. 执行预检，确认 Docker 版本、端口、目录权限、环境变量和可用磁盘空间。
5. 构建本仓库当前提交对应的应用镜像。
6. 启动 `agent-pg` 并等待健康检查通过。
7. 运行一次性 `agent-init`，创建目录、执行 Alembic 数据库升级并初始化应用基础配置。
8. 启动 `agent-app`，等待应用健康检查通过。
9. 在受信任网络中打开登录页，创建首位管理员并配置模型。
10. 登录后创建测试用户、智能体和对话，验证文件上传、知识库检索、记忆与产物。

初始化必须幂等：已初始化的数据目录再次运行时只检查并补齐数据库版本，不覆盖管理员、模型、密钥、智能体或用户数据。数据库升级保持为明确步骤；普通容器重启不隐式执行不可逆迁移。

仓库提供 Linux shell 和 Windows PowerShell 两个薄入口，它们只组织相同的 Compose 命令，不各自实现业务逻辑。至少支持 `init`、`up`、`down`、`status`、`logs`、`backup` 和 `restore`。`down` 不删除卷或宿主数据；删除数据必须使用独立命令并再次确认。

## 备份、恢复和未来迁移

完整备份是一个一致性单元，必须同时包含：

- PostgreSQL 自定义格式转储；
- `working` 文件树；
- `secrets` 密钥与凭据；
- 部署环境配置的脱敏副本和版本清单；
- 源码提交号、镜像摘要、数据库 Alembic 版本和备份时间。

备份流程默认要求短暂停服，避免数据库记录与文件正文不一致。输出为带清单和校验和的目录或压缩包，备份完成后重新启动应用。数据库密码不写入清单和日志。

恢复只能写入空数据根目录或显式指定的新实例。恢复顺序为 PostgreSQL、文件、密钥、数据库升级检查、应用启动和业务验证。源服务器保持不变，验证通过后再切换访问入口。

跨 Windows/Linux 恢复时，逻辑工作区必须使用容器内路径。历史数据中保存的 Windows 盘符或旧宿主机绝对路径需要由预检报告列出；恢复工具只修改已识别的路径字段，禁止对数据库和文档正文做无条件字符串替换。

## 外部白标和隐私显示

所有用户可见界面统一使用 WeldonAgent，包括：

- 登录、首次管理员注册和浏览器页面标题；
- 左上角产品名称、空状态、异常页和通知；
- 聊天消息中的机器人名称；
- 安装初始化输出、Docker 服务名和公开部署文档。

以下入口从生产 Web 界面隐藏：

- 产品版本号和在线更新检查；
- GitHub、上游文档、FAQ 和 Changelog；
- 上游项目下载、反馈和发布地址。

隐藏入口不删除开源许可证、源码中的版权声明或内部依赖元数据。仓库维护者仍可通过 Git 和包元数据追溯来源；普通平台用户不会在运行界面看到这些维护信息。

物理目录属于运维信息。普通用户不应看到宿主机盘符、容器路径、工作目录、内部智能体 ID 或 `default` 标识。聊天输入区只显示当前智能体的展示名称；文件中心显示“智能体工作区”等逻辑名称。管理员编辑智能体时也默认使用逻辑目录选择器，只有受控的运维诊断接口可以返回脱敏路径和存储状态。

后端仍应校验实际路径和用户/智能体作用域，前端隐藏不能代替访问控制。

## 开发文件与构建上下文

新服务器通过 Git Clone 获得干净源码，因此本机被 Git 忽略的开发产物不会被复制。生产构建还应通过 `.dockerignore` 排除：

- `tmp`、`data`、`logs` 和本地运行目录；
- `.venv`、Node 依赖、构建缓存和测试缓存；
- Playwright 输出、截图、测试日志、数据库 dump 和本地备份；
- 本机私有配置、账户交接文件和环境文件；
- 测试目录、验收证据与开发计划文档中镜像不需要的部分。

仓库内正式测试、迁移脚本和项目文档继续保留，它们是维护资产，不因生产镜像不使用而删除。当前本机文件先生成分类清单：

1. 当前业务数据：禁止清理；
2. 验收证据与历史备份：可归档到仓库外；
3. 可再生缓存、日志和测试运行目录：确认服务不依赖后可以删除。

清理是独立操作，不与部署功能实现混在同一次文件变更中。

## 错误处理与可观测性

- 缺少必填变量、密码仍为示例值或数据根目录不可写时，初始化立即失败并给出字段级错误。
- 数据库启动、迁移或应用健康检查失败时，入口脚本返回非零，不把失败实例报告为已启动。
- 日志输出服务名和阶段，不输出数据库密码、令牌、Secret 内容或完整连接串。
- 初始化标记包含数据库版本和配置格式版本；标记存在但实际数据库不匹配时拒绝覆盖并提示修复步骤。
- 备份、恢复和升级均生成机器可读结果清单，便于自动核验和人工审计。

## 验收标准

1. 在干净 Linux 主机和 Windows Docker Desktop 上，从 Clone 到登录页可按同一份文档完成。
2. 源码目录删除后重新 Clone，使用原数据根目录可以恢复同一用户和业务数据。
3. 重建 `agent-app` 不影响 PostgreSQL、知识库、记忆、产物、智能体和密钥。
4. 未设置真实数据库密码时无法启动生产实例。
5. 普通页面、登录页、聊天、页面标题和运维命令输出中不出现 QwenPaw 或 CoPaw。
6. 页面不显示版本号、GitHub、上游文档链接、物理工作目录和内部 `default` ID。
7. Docker 构建上下文不包含本机 `tmp`、业务数据、密钥、日志、测试输出或数据库转储。
8. 初始化可重复执行且不会覆盖已有数据；数据库升级失败时应用不进入就绪状态。
9. 备份清单、校验和和恢复预检可证明数据库、文件与密钥属于同一实例版本。
10. 保留现有多用户权限、文件隔离、知识库、记忆、对话和智能体测试基线。
