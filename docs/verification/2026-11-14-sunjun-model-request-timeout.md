## 结论

已找到会话及当天访问记录。报错来自浏览器的 30 秒请求计时器，触发点是发送消息前读取会话模型信息。该会话当天没有新的生成 Run 落库，不能把此报错解释为大模型生成超过 30 秒。

浏览器同域连接排队是当前最值得优先验证和处理的方向：线上 HTTPS 使用 HTTP/1.1，前端有长连接订阅；本地使用项目真实 `request.ts` 成功复现“6 条长连接占满后，模型信息请求 30 秒超时且服务端没有收到请求”。但是，原用户浏览器的网络记录没有留存，不能把本地机制复现作为原事故根因已经确认的证据。

## 请求链路分析

- `console/src/api/request.ts` 为请求设置默认 30,000 毫秒 AbortController 计时器，超时生成用户反馈中的原文。
- `console/src/pages/Chat/index.tsx` 的 `customFetch` 在真正 POST 聊天前等待 `loadConversationModel()`。失败时返回模型加载错误，消息不进入生成链路。
- `console/src/pages/Chat/conversationModel.ts` 将现有会话的读取转为 `GET /chats/{id}/model`。
- 已核对线上 `model_governance.chat_model`：执行会话授权、模型配置和目录权限解析，不执行大模型文本生成。
- `sessionEventStream.ts` 持续建立状态订阅；用户输入、执行状态、计划等功能分别使用流连接。HTTP/1.1 下，多标签页或其他持续请求可能占满同域连接，使普通请求在浏览器中排队。

MDN 说明，非 HTTP/2 的 SSE 通常受每浏览器、每域名约 6 条连接限制，多个标签页会共享这一限制：[Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。

## 本地对照实验

实验使用真实 Chrome、真实本地 HTTP/1.1 服务器和项目当前 `request.ts`。鉴权环境用无凭据测试上下文替代；模型信息端点返回固定合成数据；不向线上施加并发流量。

| 场景 | 结果 |
| --- | --- |
| 无长连接占用 | 读取成功，约 15.0 毫秒 |
| 6 条同域长连接占用 | 约 30,016 毫秒后报错，错误文字与用户提供的一致 |
| 超时期间服务端是否收到模型信息请求 | 没有收到 |
| 释放连接后 | 读取成功 |

实验复现的是可能机制，未捕获原用户浏览器当时的连接数、排队时间或网络代理状态。其他仍不能彻底排除的原因包括用户链路抖动、浏览器主线程短时卡顿，以及事故当时的应用/数据库短时等待。

## 建议处理顺序

1. 在单独的修复发布中启用 Nginx HTTP/2，保留 SSE 流式代理配置，验证实际协商结果及聊天功能；当前 Nginx 已编译 HTTP/2 模块。参考：[Nginx HTTP/2 模块](https://nginx.org/en/docs/http/ngx_http_v2_module.html)。
2. 合并同一会话重复的模型信息读取；让状态流按需连接，并评估多标签页共享订阅，减少连接占用。
3. 将模型信息加载超时显示为明确的可重试提示并保留输入。重试只读模型查询，避免盲目重发已经执行的聊天或工具任务。
4. 补充请求耗时、上游耗时和请求 ID，以及不含凭据/正文的前端超时诊断，便于下次直接对齐浏览器与服务器记录。

不建议仅把 30 秒改为更长时间：连接槽被持续占用时，延长时间不会消除排队原因。

本次没有修改线上配置、重启服务、调用模型生成、修改账号或会话数据，也没有提交/推送代码。
