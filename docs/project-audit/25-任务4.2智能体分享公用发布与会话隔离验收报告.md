## 2. 本轮修复的根因

前端聊天页实际仍调用 `/api/chats`、`/api/console/*` 等非 Agent-scoped 路径，并通过 `X-Agent-Id` 指定当前智能体。原实现只有 `/api/agents/{agentId}/...` 路由统一校验 Agent 成员关系；旧路径中的 `get_agent_for_request()` 只校验文件配置存在和启用状态，未校验当前用户是否有 owner、collaborator、user 或 public 使用权。

这会造成两个风险：

- 用户可以伪造 `X-Agent-Id` 选择无权访问的 Agent。
- scoped 与非 scoped 路径的配置写权限可能发生漂移。

本轮将两类路径统一到同一套 Agent 请求授权核心，并在获取 workspace 前完成成员关系校验。

## 3. 已实现内容

- 多用户模式下，会话 `user_id` 只能来自认证后的稳定用户 UUID；客户端传入的 `default` 或其他用户 UUID 会被覆盖。
- 会话列表忽略客户端伪造的 `user_id` 查询参数，只返回当前登录用户的会话。
- 会话读取、编辑、删除、归档、取消归档、批量操作和项目目录操作均先校验会话所有者。
- 越权读取统一返回 404，不泄漏其他用户会话是否存在。
- `/console/chat` 和 `/console/chat/task` 在进入 Session 与 ChatManager 前写入可信 `sender_id` 和 `meta.user_id`。
- 非 scoped 请求通过 `X-Agent-Id` 选择 Agent 时，必须通过 capability、成员关系和资源角色校验。
- 普通 `user` 角色不能通过旧路径修改配置、MCP、技能、工具、自动化、工作区、插件和检查点；owner/collaborator 保留配置写权限。
- 管理员作为自己 Agent 的 owner 时，可以读取原项目 `user_id=default` 的历史会话；该兼容仅限管理员 owner，不扩展为全局管理员读取任意用户会话。
- Legacy 模式保持原会话筛选与 Console 身份行为，不强制引入多用户主体。

## 7. 工程原则

- **SOLID：** 会话身份解析、会话所有权校验和 Agent 请求授权分别承担单一职责。
- **DRY：** scoped 与非 scoped 路径复用同一 Agent 授权核心和角色计算规则。
- **KISS：** 不改写原 ChatManager、Session、消息事件或工具执行展示模型，只在现有边界前增加可信身份和所有权门禁。
- **YAGNI：** 本轮不迁移聊天消息到 PostgreSQL，不引入新的会话共享模型，也不提前实现频道绑定和撤销后的只读投影。
