# QwenPaw 多用户架构分阶段实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: `executing-plans`。必须逐任务执行；每个任务完成后提交测试、接口、页面和差异证据给用户确认，未确认不得进入下一任务。禁止并行修改共享业务模块。

**目标：** 在完整保留 QwenPaw v2.1.0 原有页面、交互、Agent 运行能力和丰富对话事件的前提下，渐进实现多用户登录、Agent 资源权限、管理员治理和 PostgreSQL 结构化事实存储。

**架构：** 保持现有 FastAPI + React + Agent Runtime 模块化单体，通过 Repository、ActorContext、AuthorizationService 和 WorkspaceResolver 在现有功能外围建立隔离层。每个领域先保留 Legacy Adapter，再增加 PostgreSQL 实现，通过明确切换门迁移事实来源；禁止一次性重写或长期双写。

**技术栈：** Python 3.11–3.13、FastAPI、React 18、TypeScript 5.8、Zustand、PostgreSQL、SQLAlchemy 2.x async、asyncpg、Alembic、pytest、Vitest、Playwright E2E。

## 全局约束

- 基线提交固定为 `4726195905e0f96a6529b77dfbf0210d01f127ee`，执行前记录实际 HEAD 和工作区状态。
- 不修改 AgentScope Runtime 的原始语义；优先增加边界适配器，不侵入 `react_agent.py`、工具卡片渲染和渠道 SDK 内核。
- 原功能保真契约以 `12-原功能保真与页面验收契约.md` 为强制门禁。
- 每个内部实现步骤遵循 TDD：先失败测试，再最小实现，再目标测试，再完整回归。
- 从阶段 2 开始，只允许按“纵向验收任务”执行：同一任务必须包含真实数据库/文件事实来源、后端接口、前端交互和浏览器验收；Repository、Service、DTO、迁移脚本等横向技术工作只能作为任务内部步骤，不能单独申请用户确认。
- 每个纵向验收任务必须同时提供后端测试、前端测试、双浏览器或双账户操作证据，以及受影响原功能的回归证据。不存在可操作页面的基础能力必须并入第一个消费它的页面任务，不得用命令行输出代替用户验收。
- 每个纵向验收任务完成后停止，向用户展示文件差异、数据库变化、测试结果、API 响应、页面截图或录屏和零新增基线失败报告；只有用户明确确认才执行下一任务。
- 不执行 `git commit`、`git push`、建分支或清理用户修改，除非用户另行明确授权。
- 不删除旧数据库、旧 JSON、SQLite、workspace、备份或卷。结构变更、数据迁移写入和恢复操作执行前必须再次进行危险操作确认。
- 不以隐藏菜单代替服务端授权；所有直接 API 调用必须有相同权限结果。
- 不以最终文字回答替代原对话事件；Reasoning、Skill、Plugin、MCP、命令、审批、进度、图片、文件、错误和最终回答必须保持顺序与关联。
- 第一阶段不建设组织、计费、配额、自定义 RBAC、MFA、SSO、Outbox、分布式 Lease 或微服务。
- ACP 仅关闭产品入口和新调用，不删除影响历史兼容的源码。
- `QWENPAW_MULTI_USER_ENABLED=false` 时保持原 Legacy 行为；只有完成对应确认门后才允许设为 `true`。
- `QWENPAW_STORAGE_MODE` 仅允许 `legacy` 或 `postgres`；不得增加长期 `dual_write` 模式。

## 任务执行统一协议

每个任务都按以下步骤执行，任务描述中的文件、测试和证据不得省略：

1. 读取目标模块和相邻测试，记录原行为。
2. 编写指定的失败测试并单独运行，保存失败原因。
3. 实现最小改动，不顺手重构无关代码。
4. 运行目标后端测试、目标前端测试和类型检查。
5. 运行本阶段受影响的原功能回归用例。
6. 启动隔离测试实例，通过浏览器验证可见效果。
7. 生成任务验收记录，停止并等待用户确认。

阶段 2 及之后，每个纵向验收任务还必须满足以下固定确认门：

1. **前后端闭环：** 用户可从页面触发业务操作，后端完成真实鉴权、持久化和结果查询，禁止只做 Mock 页面或只提供内部类测试。
2. **双实例对照：** Legacy 基线实例保持原配置和原存储；Multi-user 验收实例使用独立端口、测试 Schema 和测试运行目录。两者不得共享可变测试数据。
3. **双角色/双会话：** 至少使用管理员与普通用户两个独立浏览器上下文；涉及 Agent ACL 时增加 owner、collaborator、user 和未授权主体。
4. **正向与拒绝场景：** 同时展示允许操作、直接 API 越权拒绝、页面状态和刷新后的持久结果。
5. **原功能回归：** 运行 `12-原功能保真与页面验收契约.md` 中与本任务相关的菜单、交互和丰富事件用例；新增基线失败必须为 0。
6. **可恢复性：** 数据库结构变更、迁移、恢复、删除或事实来源切换仍需单独危险操作确认；未确认时只能生成预览。

每个任务使用其“Test”字段中的精确文件路径。阶段 0 的首组验证命令为：

```powershell
python -m pytest "tests/parity/test_route_manifest.py" -q
npm --prefix "console" run test:run -- src/layouts/registry/builtinRoutes.contract.test.tsx
npm --prefix "console" run build
python -m pytest "e2e/tests/test_smoke_infrastructure.py" -q
```

## 文件边界规划

新增模块只承担单一职责：

```text
src/qwenpaw/persistence/       PostgreSQL 连接、事务、迁移状态
src/qwenpaw/identity/          用户、密码、登录会话
src/qwenpaw/access/            ActorContext、capability、资源授权
src/qwenpaw/workspaces/        授权后的 workspace 逻辑解析
src/qwenpaw/publications/      共享应用草稿、审核、发布快照
src/qwenpaw/automation/        调度授权、通知、审批、用量归属
src/qwenpaw/platform_ops/      系统设置、安全基线、备份编排
console/src/stores/authStore.ts 当前用户、会话和 capability
console/src/access/            路由、菜单和操作权限判断
console/src/pages/Admin/       用户、发布审核、平台治理页面
tests/parity/                  Legacy 与 PostgreSQL 行为等价测试
tests/isolation/               多用户越权、串流和数据隔离测试
```

现有大模块只增加调用边界，不直接替换内部算法：

- `src/qwenpaw/app/auth.py`：保留兼容读取，逐步委托 IdentityService。
- `src/qwenpaw/app/routers/agent_scoped.py`：从“注入 Agent ID”升级为“解析并授权 Agent”。
- `src/qwenpaw/app/chats/repo/base.py`：扩充稳定仓储接口，不改聊天业务语义。
- `src/qwenpaw/app/workspace/workspace.py`：通过 WorkspaceResolver 获得路径。
- `src/qwenpaw/drivers/`、`src/qwenpaw/app/crons/`、`src/qwenpaw/plugins/`：接收 ActorContext，不另建权限系统。
- `console/src/layouts/registry/builtinMenu.ts`：增加 capability 元数据，由统一过滤器决定可见性。
- `console/src/pages/Chat/` 和 `console/src/components/Chat/ToolCards/`：保持事件渲染组件，主要替换数据作用域和恢复逻辑。

## 计划调整规则

1. 前一任务发现原功能与文档不一致时，先更新审计和后续任务，不强行按旧计划实施。
2. 用户未确认的任务不得标记完成，也不得执行其依赖任务。
3. 任务只允许修改“Files”列出的文件；新增必要文件必须先说明原因。
4. 若一个任务的差异超过可独立评审范围，必须拆分任务并重新确认。
5. 任何阶段出现新增基线失败、数据串流、Secret 回显或消息事件丢失，立即停止并回退该任务改动。
6. 每个阶段结束后重新运行阶段 0 的完整基线清单，确认新增失败为 0。
7. 不得把“后端已通过测试”“前端页面已画出”或“数据库表已创建”中的任一项单独视为完成；三者必须在同一纵向任务中通过真实操作闭环。
8. 若纵向任务实施过程中需要拆成多次编码，只记录为内部步骤 A/B/C，不新增用户确认门；直到页面可操作、后端真实生效且原功能回归通过才停止请求确认。
9. 用户验收发现原功能退化时，当前纵向任务保持未完成，先修复并重新提交整套对照证据，不得以“将在后续任务修复”为由进入下一任务。
