## 结论

当前项目已实现多用户架构主体，但此前“技术验收完成”不能等同于没有隔离缺陷。本次从设计、阶段任务、最终报告和实际调用链交叉检查，发现并修复了下列问题。原最终报告保留为历史证据，本报告补充其结论和限制。

## 已修复问题

| 问题 | 触发与影响 | 修复及回归证据 |
|---|---|---|
| 运行状态跨用户广播／查询 | 共用 Agent 的用户可接收其他用户的运行信息 | `runtime_status` 缓存和 SSE 使用 Agent＋可信用户作用域；查询也绑定当前主体 |
| 交互问答越权 | 问题按 Agent 广播；仅凭 request_id 可回答另一用户的问题 | pending 查询、SSE、回答、取消统一校验用户和 Agent；未知主体默认拒绝 |
| 工具与后台身份传递遗漏 | 只修状态服务会使合法频道、自动化和子 Agent 丢失可用状态 | 频道绑定、Cron、Heartbeat、工具 ContextVar、子 Agent 均传递服务端签发的 actor 快照；不信任客户端 user_id |
| 账号切换残留文件状态 | diff.original 持久化及文件缓存可能由下一用户复用 | 统一身份清理覆盖 tabs、diff、文件缓存、文件抽屉、项目目录及待选目录状态 |
| 公共／私人记忆切换串写 | 同名 daily/digest 标签保留旧正文，保存却使用新 memoryScope | 标签工作台按 memoryScope 隔离；验证同名文件内容、未保存编辑及保存目标 |
| 删除会话遗漏个人检查点 | 同 Agent 先初始化 A 后删除 B，原逻辑只选第一个缓存库；重启时只查草稿库 | 定位草稿、关联缓存和用户确定性运行库；取消匹配定时器后清理对应会话引用，邻用户数据保留 |
| Windows 检查点长引用失败 | 多用户深目录＋长 session ref 导致 Git update-ref 失败 | 短 session key／必要时短名称引用；完整名称保留在元数据，兼容旧 refs 与 heads |
| 检查点名称恢复受分页限制 | 哈希引用或旧格式快照超出 timeline_max_limit 后无法按名称恢复 | 精确名称／ref／commit 在完整会话引用中查找；数字索引保留分页语义；覆盖重复长名称 |
| 平台备份遗漏正文 | 数据库已有用户运行、资料库、发布等记录，ZIP 却未包含正文 | 增加 user_workspaces、user_libraries、published_workspaces、media 的正文；空／不存在根目录有显式标记；恢复使用现有 staging／交换链路 |
| 局部备份错误导出全库 | 未选择全局配置仍追加全量数据库快照 | 数据库快照遵循备份 scope.include_global_config |
| 平台恢复并发与生命周期缺口 | 数据库和文件恢复可交错；请求取消后线程继续写；后台重启越过锁 | 恢复编排锁覆盖保护备份、数据库、文件、回滚与重启；屏蔽关键任务取消直到完成；恢复数据库时停止所有运行 Agent；保护备份在停机后创建 |

## 尚不能承诺的范围

1. **在线跨存储一致性仍是设计差距。** 文件与数据库按顺序采集，数据库自身使用 repeatable-read；停止 Agent 不等于冻结所有 HTTP 写入、所有进程和外部文件写入。本轮增加明确的 `cross_store_consistency=sequential_files_and_database` 描述。在线严格原子备份需要统一维护／写入准入门和多进程协调；未将局部恢复锁当成该能力。当前应在禁止并发写入的维护窗口进行完整备份／恢复验收。
2. **旧备份不会自动补回遗漏正文。** 本轮补齐只对新备份生效；旧归档缺失的数据无法从元数据重建。应用修复后应重新生成完整备份。
3. **Windows 环境限制。** 四个符号链接测试仍因权限失败；未调整系统权限。真实数据库组合出现 Windows asyncio Proactor 底层 access-violation 提示，但断言完成且退出码 0；仍应在目标运行时／CI 复核稳定性。
4. **浏览器与生产演练未重做。** 本次前端验证为自动化测试及构建；未重新执行历史报告全部角色截图、真实外部模型调用或现有业务数据恢复。独立测试 Schema 的数据库恢复测试通过，不等同于生产灾备演练。
5. **未复现的历史清理竞态。** 本次单元全集未再次出现历史报告中的 wechat_context_tokens.json 退出清理竞态；不能因此声明其已修复。

## 工程约束

以可信身份、集中状态重置、既有路径解析和分阶段文件交换复用落实 DRY/KISS；修复限于可复现的问题，未新建组织／复杂 RBAC（YAGNI）；临时状态授权、持久化和恢复编排保持各自职责。每项实质修复均由失败回归或已失败原测试验证后再修改。没有覆盖或撤销原有未提交重构。
