# 纵向 Task 3.2：菜单与 Agent 路由统一授权验收报告

## 1. 当前结论

Task 3.2 已完成实现和自动化、真实 API、浏览器、Multi-user/Legacy 对照验收，并于 2026-08-21 获得用户确认。本任务没有新增数据库表或迁移，也没有改写 Agent、技能、MCP、工具、聊天等业务子路由的内部实现。

## 2. 后端实现

- 新增 `agent.use` capability，管理员和普通用户均具备该基础能力，保持“管理员 = 普通用户能力 + 管理增量权限”。
- 在 `/api/agents/{agentId}` 父 Router 注入统一授权依赖，现有 16 组 Agent-scoped 子 Router 自动继承，不逐个侵入业务代码。
- Multi-user 模式统一拒绝以下请求：
  - 路径 `agentId` 与 `X-Agent-Id` 不一致；
  - 不存在的 Agent；
  - 已禁用的 Agent；
  - 不具备 Agent 使用 capability 的主体。
- 拒绝结果统一为 `403 forbidden`，不向未授权主体泄露资源细节。
- Legacy 模式保留原路径优先和下游资源解析行为，避免破坏旧页面、CLI 和 Header 兼容入口。
- Agent `ContextVar` 改为严格请求作用域：有 Agent 的请求设置对应 ID，无 Header 的全局请求显式清空，请求完成后恢复外层上下文，避免串 Agent。

## 3. 本阶段权限边界

Task 3.2 建立的是统一授权入口和当前可验证的资源可用性边界。Agent owner、collaborator、user 成员关系及列表过滤尚未提前伪造，仍按纵向 Task 4.1–4.2 接入；届时只需扩展这一集中入口，不需要重新修改 16 组业务 Router。

## 7. 工程原则

- **KISS / DRY：** 一个父 Router 依赖覆盖全部 Agent-scoped 子路由，不复制 16 份校验代码。
- **SOLID / OCP：** 业务 Router 保持原职责；阶段 4 只扩展集中资源判定即可接入 owner/ACL。
- **YAGNI：** 本阶段不提前创建 Agent 成员数据或空 ACL 实现，只交付已确认的统一授权边界。
