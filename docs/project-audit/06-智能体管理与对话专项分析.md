# 智能体管理、使用与对话专项分析

## 1. 结论

原项目中的 Agent 不是简单的“机器人记录”，而是一个完整运行单元。每个 Agent 通过独立 workspace 聚合配置、系统提示词、技能、会话、任务、记忆、文件、渠道、MCP、运行参数和模型选择，并由 `MultiAgentManager` 管理启动、停止与热重载。

因此，多用户改造不能只给 Agent 表增加 `user_id`。必须同时控制：

- 谁能发现、查看、使用、编辑、共享、停用和删除 Agent。
- 谁能读取其 workspace、会话、任务、记忆、技能、渠道和运行状态。
- Agent 调用其他 Agent 时，是否仍满足用户和共享权限。
- 浏览器本地状态、API 请求头和后台任务中的 `agent_id` 是否与当前登录用户的授权一致。

## 2. 原有菜单与页面能力

### 智能体管理页

“智能体”设置页提供以下能力：

- 展示 Agent 名称、描述、ID、运行后端、启用状态和启动状态。
- 新建、编辑、复制和删除 Agent。
- 启用或停用非默认 Agent。
- 固定或取消固定 Agent，并通过拖拽调整顺序。
- 在模型列展示该 Agent 当前配置的模型；目标多用户语义中应明确展示为“默认模型”。
- 默认 Agent 永远位于第一位，不能删除、停用或取消固定。
- 创建、编辑或复制完成后刷新 Agent 列表，并按需调度启动或热重载。

侧边栏 `AgentSelector` 用于切换当前 Agent。选中结果不仅影响聊天页，也通过公共 API 请求头影响技能、workspace、任务、渠道及其他 Agent 范围功能。

### Agent 创建

创建窗口支持：

- Agent 名称和描述。
- 自动生成 ID，或由用户填写自定义 ID。
- 使用默认 workspace，或指定 workspace 路径。
- 选择原生 `qwenpaw` 后端或已接入的 harness 后端。
- 填写后端专属配置。
- 原生后端可选择初始模型。
- 从技能池选择初始技能。
- 选择语言和模板，由后端生成基础 Markdown 文件。

这里的模型字段属于 **Agent 创建时的默认模型配置**，不是对话页右上角的用户运行时选择。普通用户创建自己的 Agent 时，可以从管理员已经配置并授权的模型目录中设置默认模型；不能在此配置供应商、API Key、Base URL 或模型参数。

后端创建流程为：

1. 校验自定义 ID，或生成短 ID。
2. 确定 workspace，默认位于 `~/.qwenpaw/workspaces/<agent-id>`。
3. 建立 `sessions`、`memory`、可选的 `skills` 等目录。
4. 写入模板 Markdown、`HEARTBEAT.md`、`jobs.json` 和 `chats.json`。
5. 从技能池复制用户选择的初始技能。
6. 创建完整 `agent.json`，并在根 `config.json` 中登记精简引用。
7. 将新 Agent 设为启用状态并调度启动。

如果创建时没有显式选择模型，后端会读取全局激活模型并写入新 Agent。这意味着当前实现通常是“创建时复制全局模型”，而不是长期保持一个纯粹的动态继承引用。

### Agent 编辑

编辑会读取完整 Agent 配置，可修改名称、描述、后端、后端参数、默认模型及其他创建表单字段，并允许继续添加技能池技能。已经安装在 workspace 中的技能不会在 Agent 编辑窗口中直接删除；删除和详细配置由“技能”页面负责。

对于共享应用（共享 Agent），创建/编辑页配置的模型就是该共享应用的受控默认模型。普通使用者进入共享应用对话时不能通过右上角选择器替换它；有权编辑共享 Agent 的所有者、协作者或管理员需要变更模型时，应从 Agent 编辑入口修改，从而形成明确的配置变更和审计记录。

保存后会持久化 `agent.json`，并调度 Agent 热重载，使模型、运行参数和工具等变化进入运行实例。

### Agent 复制

复制功能首先复制源 Agent 配置，但会重置渠道配置，避免新 Agent 自动继承原渠道接入。用户可以选择复制以下白名单内容：

- `AGENTS.md`、`SOUL.md`、`PROFILE.md`、`HEARTBEAT.md`、`BOOTSTRAP.md`。
- `skills` 目录及 `skill.json`。
- `jobs.json`。

复制不会带走聊天、会话、媒体、记忆数据库及其他运行产物。这一语义应在多用户版本中保留，尤其不能因“共享 Agent”而把原所有者的私密会话复制给新所有者。

### Agent 删除

当前删除接口会停止运行实例并从根配置中移除 Agent 引用，但实际实现没有删除对应 workspace 目录。接口描述写的是“Delete agent and workspace”，与真实行为不一致。

这会产生孤儿 workspace 和残留数据风险。多用户方案必须明确采用一种可审计语义：建议默认软删除 Agent 元数据并隔离 workspace，之后由管理员执行受控清理；不能继续保持“页面显示已删除、磁盘数据无归属”的隐式状态。

## 3. Agent 配置与数据边界

### 根配置中的 Agent 引用

根 `config.json` 只保存 Agent 的精简资料，核心字段包括：

- `id`
- `workspace_dir`
- `enabled`
- `pinned`

它承担实例级 Agent 注册表和排序入口。

### Agent 自身配置

每个 Agent 的 `agent.json` 保存完整运行配置，包括：

- 名称、描述、workspace 和项目目录。
- 后端类型、后端设置和模板。
- 渠道、MCP、心跳与工具配置。
- 运行参数、LLM 重试、限流和上下文压缩参数。
- `active_model`、语言、审批等级和系统提示词。
- 安全、ACP、计划模式和编码模式等配置。

### Workspace 数据

Agent workspace 是其业务数据容器，包含或关联：

- 聊天列表、会话记录、历史消息和待处理队列。
- 技能目录与技能运行状态。
- 定时任务和任务执行状态。
- 记忆目录、索引或数据库。
- 用户上传文件、生成文件及媒体资源。
- Agent 人格、说明、心跳和启动模板文件。
- 渠道、MCP 和运行时所需的附属状态。

原实现通过“选择哪个 Agent”实现数据范围切换，不具备“哪个登录用户有权访问该 Agent”的第二层判断。

## 4. Agent 启动与运行生命周期

`MultiAgentManager` 负责：

- 根据根配置发现已登记 Agent。
- 只为启用的 Agent 安排启动。
- 维护启动中、已加载、失败和停止等状态。
- 提供按 Agent 获取运行实例的入口。
- 在配置、技能或模型变化后停止、启动或热重载对应实例。

默认 Agent 具有特殊保护；其他 Agent 可按需启动和停用。列表页展示的“已启用”和“运行中”不是同一概念：前者是持久化配置，后者是当前进程状态。

多用户改造后，Agent 运行实例仍适合保持部署级复用，不能为每次用户请求复制一个完整 Agent。但是请求上下文必须同时携带 `user_id`、`agent_id` 和会话身份，避免共享运行实例导致数据串读。

## 5. Agent 切换与前端状态

`agentStore` 维护：

- 当前选中的 Agent。
- Agent 列表及刷新状态。
- 每个 Agent 最近一次聊天 ID：`lastChatIdByAgent`。
- 固定、排序、启停和删除后的本地状态修正。

选择状态同时使用：

- `sessionStorage`：保存当前浏览器标签页的 Agent。
- `localStorage`：让新标签页继承最近使用的 Agent，并保存共享状态。

聊天草稿按 Agent 使用不同存储键；聊天页切换 Agent 后恢复对应最近会话和草稿。请求工具会从本地状态生成 `X-Agent-Id`，部分 API 也在路径或请求体中显式携带 `agent_id`。

这些机制只是用户体验状态，不能成为授权依据。多用户登录后必须：

- 将本地缓存键加入用户维度，防止同一浏览器退出后新用户看到前一用户的 Agent ID、最近会话或草稿。
- 登录、退出和用户切换时清理或隔离 Agent、会话、草稿、待处理队列和标签页所有权状态。
- 后端对路径、请求头和请求体中的每个 `agent_id` 统一执行权限校验。

## 6. 智能体对话原有流程

### 选择与恢复

进入聊天页后，前端根据当前 Agent：

1. 读取该 Agent 的后端类型和能力。
2. 恢复该 Agent 最近聊天或创建新会话。
3. 恢复该 Agent 的输入草稿。
4. 为当前会话建立单标签页发送所有权，其他标签页进入仅排队模式。
5. 订阅回复、工具调用、审批和队列状态。

切换 Agent 时会推进会话所有权 epoch，避免旧 Agent 的异步返回继续写入新 Agent 页面。

### 请求范围

聊天、上传、会话、工具调用、审批、运行状态和推送队列通过路径、`X-Agent-Id` 或请求体中的 `agent_id` 绑定 Agent。后端 `get_agent_for_request` 按显式参数、请求上下文、请求头以及默认/活动 Agent 的顺序解析目标，并检查 Agent 是否已配置和启用，然后从管理器取得运行实例。

当前检查只解决“Agent 是否存在并可运行”，没有解决“当前登录用户是否有权使用或查看它”。

### 不同后端

- 原生 QwenPaw Agent 使用供应商/模型选择器，并执行 QwenPaw 的工具、技能、记忆和审批链路。
- Harness Agent 使用对应 harness 模型选择器及后端能力声明。
- 页面根据 Agent 后端能力决定是否显示 workspace、模型选择和其他交互。

模型交互需要按 Agent 类型区分：

- 用户自己的非共享 Agent：创建/编辑页设置默认模型；对话页右上角允许用户从授权模型中切换，但只对当前对话生效，新建对话重新使用 Agent 默认模型。
- 共享应用：创建/编辑页设置并维护默认模型，对话页只展示当前模型，不允许普通使用者切换。
- 模型设置页：只负责管理员配置供应商、模型目录和密钥，不承担普通用户的对话切换。

多用户方案必须保持这种后端多态，不应把权限逻辑散落到每种 Agent 后端。权限应在统一 Agent 访问服务和请求依赖层完成。

## 7. Agent 间协作能力

原项目还内置了 Agent 间协作工具：

- `list_agents`：列出可用 Agent。
- `chat_with_agent`：同步向另一个 Agent 发起对话。
- `submit_to_agent`：提交后台 Agent 任务。
- `check_agent_task`：查询后台任务。
- `spawn_subagent`：在当前 Agent 体系中派生子任务，部分模式支持 fork 工作目录。

这些工具在单用户实例中可以枚举或调用配置中的其他 Agent。多用户后它们是高风险越权入口：即使 Web API 已过滤 Agent 列表，运行中的 Agent 仍可能通过工具层调用未授权 Agent。

因此工具注册、目标解析、后台任务读取、fork 目录和结果回传都必须绑定发起用户，并执行与页面相同的 Agent ACL。共享 Agent 发起跨 Agent 调用时，权限不能继承 Agent 所有者身份，应使用当前操作者身份或受限服务身份。

## 8. 已确认的多用户权限映射

根据当前确认结果，目标语义为：

| 能力 | 普通使用者 | 协作者 | 所有者 | 管理员 |
|---|---|---|---|---|
| 查看 Agent 基本信息 | 被授权 Agent | 被授权 Agent | 自己 Agent | 全部 Agent |
| 使用 Agent 对话/运行 | 允许 | 允许 | 允许 | 允许 |
| 查看会话 | 默认仅自己的会话 | 自己的；显式共享后可看共享会话 | 自己的；显式共享后可看共享会话 | 审计可见 |
| 修改 Agent 配置/workspace | 禁止 | 允许 | 允许 | 任意 Agent |
| 管理 Agent 技能 | 禁止或按协作授权 | 允许 | 允许 | 任意 Agent |
| 管理共享成员 | 禁止 | 禁止 | 允许 | 允许 |
| 创建 Agent | 允许 | 允许创建自己的 | 允许 | 允许 |
| 复制 Agent | 仅对有读取/复制权的来源，生成自己的 Agent | 同左 | 允许 | 允许 |
| 删除 Agent | 仅自己的 Agent | 禁止删除他人 Agent | 允许删除自己的 | 任意 Agent |
| 发布为共享 Agent | 自己 Agent 可发起/执行共享 | 禁止改变所有权 | 允许 | 允许并可强制治理 |
| 转移所有权 | 禁止 | 禁止 | 建议仅转给有效用户并记录审计 | 允许 |

管理员可以查看和配置用户 Agent；共享 Agent 的治理、强制下线、成员清理和审计由管理员控制。

### 定向共享与公共共享应用

共享需要区分两种产品语义：

- **定向共享**：Agent 所有者将自己的 Agent 分享给一个或多个指定用户，并授予使用者或协作者角色。该操作不需要管理员逐次审批，但管理员可以审计、撤销和强制治理。
- **公共共享应用**：Agent 进入面向全体用户的共享应用目录。普通用户只能提交发布申请，由管理员审核后发布；管理员负责可见范围、上架、下架和紧急停用。

两者不能只用一个 `is_shared` 布尔字段表示。定向共享属于成员 ACL，公共共享属于带审核状态和发布版本的目录对象。

公共共享应用发布后采用版本隔离：

- 管理员审核通过的版本成为当前线上发布版本。
- 原所有者或协作者继续修改 Agent 配置、提示词、技能、默认模型或共享 workspace 时，修改进入草稿版本，不直接覆盖线上版本。
- 草稿重新提交管理员审核，通过后才能原子切换为新的线上版本。
- 审核拒绝不影响当前线上版本，草稿可以继续修改并再次提交。
- 管理员可以下架、紧急停用或回滚到仍满足安全和模型授权要求的历史发布版本。
- 每次提交、审核、拒绝、发布、回滚和下架都必须保留操作者、版本差异、时间和原因。

### 公共共享应用的运行 workspace

公共共享应用采用“只读发布基线 + 用户私有运行 workspace”：

- 已发布版本的提示词、技能、模板、默认模型和基础 workspace 作为只读运行基线。
- 普通用户发起对话时，为该用户的当前应用使用空间解析独立的私有运行 workspace。
- Agent 在运行中生成或修改的文件、临时数据、下载内容和其他产物只写入该用户的私有空间。
- 不同用户不能读取或覆盖彼此的运行文件；管理员审计访问必须留下记录。
- 普通用户的工具调用不能反向修改已发布基线，也不能写入所有者的草稿 workspace。
- 所有者和协作者编辑的是应用草稿 workspace；草稿审核发布后生成新的只读发布基线。
- 发布升级时保留用户私有运行数据，不用新版本基线直接覆盖用户文件；不兼容迁移必须显式设计和审计。

公共共享应用中的 MCP、外部工具和第三方服务秘密遵循以下规则：

- 应用所有者或协作者只能在草稿中配置 MCP、外部工具及其 Secret 引用。
- 管理员审核发布时同时审核工具能力、网络目标、权限范围和潜在副作用。
- 普通使用者可以间接调用发布版本中已经批准的能力，但不能查看、编辑、复制或导出实际密钥。
- Secret 不进入发布快照、普通配置响应、聊天消息、工具结果或审计正文，只保存安全引用。
- 涉及外部写入、发送、删除、支付或其他副作用的操作仍以当前实际用户身份触发审批，不能复用应用所有者的预授权。
- 工具调用审计记录应用版本、当前用户、会话、工具、目标范围和结果，但对敏感参数进行脱敏。

## 9. 目标数据模型约束

PostgreSQL 至少需要表达：

- `agents`：Agent 身份、所有者、可见性、生命周期状态、workspace 定位和版本。
- `agent_memberships`：用户与 Agent 的 `user/collaborator/owner` 关系。
- `agent_sessions`：会话归属用户、所属 Agent、共享状态和审计状态。
- `agent_share_grants` 或会话共享表：显式共享对象及权限。
- `shared_app_publications`：公共共享应用的申请、审核、草稿版本、线上版本、可见范围、回滚点和上下架状态。
- `shared_app_user_workspaces`：用户在公共共享应用下的私有运行空间、逻辑路径、配额、版本关联和生命周期。
- `agent_runtime_state`：可选的运行状态投影；真实进程状态仍由运行管理器维护。
- `audit_logs`：创建、复制、共享、修改、停用、删除、管理员代操作和跨 Agent 调用。

workspace 大文件、技能内容、消息归档和媒体不必全部塞入 PostgreSQL，但数据库必须保存其所有权、逻辑路径、版本和访问策略。任何直接文件读取都要先经过数据库授权解析，不能让客户端提交任意绝对路径。

## 10. 必须保留的原功能与回归用例

- 默认 Agent 始终存在、置顶，不能被普通操作删除、停用或取消固定。
- 普通用户可以创建、修改和删除自己的 Agent。
- 管理员可以查看和配置所有用户 Agent，并治理共享 Agent。
- Agent 所有者可以直接定向分享给指定用户；公共共享应用必须经过管理员审核发布。
- 公共共享应用发布后的修改只进入草稿，重新审核发布前不能影响线上运行版本。
- 公共共享应用基线只读，普通用户运行产物写入各自私有 workspace，用户之间不能串读或互相覆盖。
- 创建 Agent 后正确初始化模板、会话、记忆、技能和任务文件，并可启动运行。
- 复制只复制勾选的白名单内容，不复制源用户会话、记忆、媒体和渠道凭据。
- Agent 启停、固定、排序及启动状态展示保持原交互。
- 切换 Agent 后恢复该用户在该 Agent 的最近会话和草稿，不串到其他用户或 Agent。
- 旧 Agent 的流式回复、审批和后台队列不能写入新 Agent 页面。
- Agent 配置、技能或模型变化后只重载目标 Agent。
- 会话默认按用户私有；显式共享后仅授权成员可见；管理员审计访问被记录。
- `X-Agent-Id`、路径和请求体篡改均不能访问未授权 Agent。
- Agent 间工具只能发现和调用当前用户有权使用的目标 Agent。
- 删除流程不产生无主 workspace；恢复、保留期和最终清理均可审计。
