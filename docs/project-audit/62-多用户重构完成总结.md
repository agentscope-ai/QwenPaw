# QwenPaw 多用户重构完成总结

> 总结日期：2026-09-16  
> 对应分支：`dev-my-fix`  
> 文档用途：汇总本轮多用户重构、后续交互优化、部署规范和验收结果，作为代码提交与后续维护入口。  
> 详细设计、实施步骤和逐项证据仍以本目录及 `docs/superpowers/` 中的原始文档为准。

## 1. 重构目标与最终状态

本轮工作将 QwenPaw 从面向本地单账户的运行模式，改造成可配置启用的企业多用户智能体平台。改造保留 Legacy 单用户兼容路径，同时在多用户模式下建立 PostgreSQL 结构化事实源、可信用户身份、统一授权、用户与智能体双重作用域、私人运行目录和正式部署入口。

当前完成的核心闭环包括：

- 用户可以独立登录、维护个人资料和修改密码；管理员可以创建、编辑、禁用用户、重置密码并撤销会话。
- 智能体具备所有者、协作者、使用者和公开可用等明确关系；会话、文件、记忆、频道及运行时资源按实际用户隔离。
- 聊天消息、工具过程、审批、附件、产物和丰富事件可以持久化、恢复和完整回放。
- 模型、技能、MCP、工具、频道、应用、插件、自动化、收件箱、统计、备份和日志均纳入服务端授权边界。
- 代码目录与运行数据目录分离，Windows、Linux 和容器均有正式启动、检查、迁移与运维方式。

## 2. 身份、账户与权限治理

### 2.1 用户身份

- 新增用户、登录会话、角色、状态、个人资料和审计数据的持久化模型。
- 密码使用哈希保存，访问令牌和刷新令牌具有会话生命周期；禁用用户或撤销会话后立即失效。
- 首个用户可完成管理员初始化；后续账户由管理员在“用户管理”创建和维护。
- 用户可在左下角账户入口查看及修改自己的资料；自行修改密码时必须校验旧密码。
- 管理员可维护用户基本信息和重置密码，解决企业场景中的账号找回问题。

### 2.2 可信授权链

- 后端统一构造 `ActorContext`，不信任客户端自行传入的 `user_id`、所有者字段或伪造请求头。
- 权限判断收口到 capability、资源成员关系和 Repository 查询条件，前端菜单隐藏只作为交互优化，服务端仍执行最终授权。
- 管理员治理能力与普通业务数据读取分离；管理员不能因为角色而直接读取其他用户的私人会话、资料库或记忆。
- 对会话、附件、检查点、环境变量、调试日志、MCP、审批等高风险入口补充 IDOR 与跨用户访问测试。

## 3. 智能体、模型与运行时

### 3.1 智能体生命周期

- 支持智能体创建、编辑、复制、排序、启停、软删除、成员管理、所有权转移和导入导出。
- 支持管理员发布公用智能体，普通用户使用公用智能体时仍写入自己的会话和私人运行目录。
- 智能体列表区分“我的、协作、可使用、全部智能体”，管理能力与运行能力分别授权。
- 用户管理入口调整到管理员设置菜单底部，侧边栏全部业务菜单使用同一滚动区域，账户入口固定在左下角。

### 3.2 模型继承

- 模型选择形成“平台默认 → 智能体默认 → 私人会话覆盖”的解析顺序。
- 智能体配置为“使用全局默认”时，进入聊天会正确解析并展示当前有效模型，不再误报未配置 LLM。
- 新建智能体和既有智能体使用同一模型继承逻辑，并对配置修订、并发保存和热重载状态做一致处理。

### 3.3 私人运行目录

- 普通聊天默认运行在 `用户 × 智能体` 的私人工作区，而不是智能体共享根目录。
- 后台任务、Heartbeat、自动化、频道消息和工具调用携带实际用户身份，避免产物、记忆和审批落到错误主体。
- Shell 和文件 API 的路径解析拒绝绝对路径注入、`..` 穿越和符号链接逃逸；系统级进程隔离仍由独立账户或容器负责。

## 4. 会话、实时事件与聊天体验

- 建立 Conversation Repository 契约，并在多用户模式下以 PostgreSQL 保存会话、消息、Run、工具调用和丰富事件。
- 完成旧会话、消息和智能体关系的预览、幂等迁移与切换；已切换领域禁止继续双写 Legacy 业务事实。
- SSE、审批、停止、重连和后台完成事件绑定用户、智能体、会话及 Run，避免跨用户订阅和状态串扰。
- 修复工具已经完成但前端长期显示“执行中”的终态归并问题。
- 修复页面恢复焦点、切换浏览器标签、切换应用菜单后回到聊天时的重复消息、错误新建页和路由内容不同步问题。
- 新建对话会显式清空旧会话视图并创建独立会话，避免首次点击只改变地址或需要点击两次。
- 聊天滚动改为尊重用户当前位置；仅在用户接近底部时自动跟随新内容，避免拉到底后反复向上弹。

## 5. 统一文件中心与资料生命周期

文件中心统一为五类内容，独立文件页与聊天预览共用同一套定位、权限和预览逻辑：

| 类别 | 作用域 | 主要规则 |
| --- | --- | --- |
| 临时附件 | 用户 × 智能体 × 会话 | 对话上传，用户可显式保存到个人资料库 |
| 个人资料库 | 用户 × 智能体 | 跨会话长期资料，不需要向其他智能体额外授权 |
| 产物 | 用户 × 智能体 × 源会话 | 最终交付文件自动登记，可下载、删除或保存到资料库 |
| Agent 配置 | 智能体 | 只展示平台允许管理的配置文件及相应只读/编辑权限 |
| 记忆 | 用户 × 智能体或智能体公共范围 | 日记记忆和长期记忆只读展示，索引异常不阻断已有文件查看 |

### 5.1 附件与产物

- 上传附件记录所有者、智能体、会话、逻辑路径和生命周期，不再依赖共享工作区文件名推断归属。
- 最终文件写入私人会话产物目录；`.work`、缓存和中间文件不会自动登记。
- 工具完成、后台任务完成和会话结束都会触发产物收集；登记按用户、智能体、会话和内容摘要幂等，解决重复产物问题。
- 已登记内容保留独立快照；删除使用墓碑，后续扫描不会把用户删除的记录自动复活。
- 修复中文文件名、聊天内链接、文件中心打开和左侧预览使用不同路径导致的“文件加载失败”。

### 5.2 个人资料库

- 资料库按当前认证用户和当前智能体隔离，Agent 运行时只注册本作用域的只读搜索、读取工具。
- 检索先进行文件名和相对路径匹配，再按需提取正文；完整文件名命中优先于部分文件名和纯正文命中。
- 支持 Markdown、TXT、CSV、JSON、YAML、XML、HTML、PDF 文本层、DOCX、PPTX、XLSX、ODT、ODP、ODS 等格式。
- 扫描图片型 PDF 暂不执行 OCR；旧 `.doc/.ppt/.xls` 需转换为现代格式后再索引。

### 5.3 记忆

- ReMe 记忆划分为“我的记忆/公共记忆”和“日记记忆/长期记忆”两个正交维度。
- Auto-memory、Auto-dream 和收件箱通知携带受控相对路径，可直接定位到实际记忆文件。
- 修复记忆页请求竞态、频闪、重复标签、列表为空、会话记忆无法预览及 `needs_reindex` 被误当成文件不可读的问题。
- `MEMORY.md`、日记和 Dream 沉淀文件可在文件中心只读查看；Agent 配置页继续只展示受管理配置子集。

## 6. 技能、MCP、应用与平台治理

### 6.1 技能发布与授权

- 明确区分技能池草稿、正式发布版本、智能体授权和智能体载入。
- 管理员可直接发布技能；普通用户提交申请后由管理员审核，已处理申请保持只读快照。
- 技能池列表、已发布技能和发布申请拆分为独立标签页，减少信息拥挤。
- 广播交互改为显示技能名、智能体名和成功/失败说明，不向用户暴露内部 UUID 或难以理解的 `ready` 状态串。
- 智能体从技能池载入时按正式发布版本与显式授权判断，管理员创建的智能体也遵守同一规则。

### 6.2 其他平台资源

- 模型供应商、MCP 凭据、环境变量和频道 Token 采用 Secret 引用或加密存储，API 不回传明文。
- 共享应用和插件具有草稿、发布、下架、回滚、授权及用户数据隔离边界。
- 自动化、Heartbeat、收件箱、审批、Token 用量和 Agent 统计按平台、智能体、用户分层查询。
- 检查点、备份、恢复预览、调试和系统状态补充管理员能力与资源归属校验。

## 7. 部署、存储与运维

- 增加统一 `python -m qwenpaw service --config <绝对路径>` 运维入口，支持 `init`、`check`、`start`、`run`、`status`、`restart`、`stop`、`logs` 和数据库升级。
- 正式部署要求项目目录、工作目录、密钥目录、备份目录、状态目录和日志目录分离；运行数据不再放在源码或 `tmp` 中。
- 提供 Windows 计划任务、Linux systemd 和 Docker Compose 示例；部署模板不包含可用密码。
- Alembic 迁移覆盖身份、智能体、会话、共享、附件、资料库、产物、技能、应用、插件、自动化和账户资料等领域。
- 备份与恢复同时覆盖 PostgreSQL、工作目录、Secret、实例配置及外部文件引用，避免只备份文件或只备份数据库造成不一致。

## 8. 兼容、迁移与安全收口

- Legacy 单用户模式继续可用；多用户模式只在显式配置和数据库检查通过后启动。
- 迁移支持预览、备份、幂等执行和结果核验，源文件不在迁移过程中删除。
- 已切换领域以 PostgreSQL 为权威结构化事实源，Legacy 文件仅承担迁移、归档或必要的运行寻址投影。
- 安全测试覆盖跨用户会话、Agent、文件、记忆、MCP、审批、环境、日志、技能、应用、插件及 Secret 泄露矩阵。
- 账户交接文件 `docs/accoun.md` 属于本地部署资料，包含实例特定凭据，不纳入版本控制或远程仓库。

## 9. 测试与验收资产

本轮形成了四类长期可维护的验证资产：

1. 后端单元测试：验证身份、Repository、路径解析、运行时、文件生命周期和各领域服务。
2. 集成与隔离测试：验证 PostgreSQL 迁移、RLS/查询边界、双用户并发、跨域授权和 Legacy 切换。
3. 前端 Vitest：验证登录、菜单、聊天恢复、文件中心、技能发布、用户管理和设置页面。
4. 真实浏览器验收：覆盖管理员/普通用户双会话、刷新与标签切换、聊天恢复、资料库检索、文件预览和多页面跳转。

原始设计、计划、逐阶段验收和截图证据保存在：

- `docs/project-audit/`
- `docs/superpowers/specs/`
- `docs/superpowers/plans/`
- `docs/superpowers/verification/`

## 10. 后续优化边界

多用户主体架构已经完成，后续工作应以小范围体验优化和生产化加固为主：

- 如需要检索扫描 PDF，可增加受控 OCR 队列和资源限额。
- Linux 容器镜像仍应在目标服务器完成独立构建、备份恢复和反向代理验收。
- 系统级 Shell 隔离应通过专用运行账户、容器或独立主机落实，不能只依赖应用层路径检查。
- 新增领域必须继续使用可信 `ActorContext`、作用域 Repository、统一 WorkspaceResolver 和审计事件，避免重新引入客户端信任、共享目录写入或双写。

## 11. 结论

本轮重构已经形成“身份可信、权限可审计、数据按用户与智能体隔离、运行目录私有、文件生命周期统一、部署入口规范”的完整多用户基础。原有智能体平台功能已迁入新的授权与存储边界，并通过分阶段设计、实现、复核、修复和真实页面验收持续校正。后续可以在该基线上进行功能迭代，无需再次重做多用户核心架构。
