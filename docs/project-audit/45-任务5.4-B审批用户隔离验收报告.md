# Task 5.4-B 审批用户隔离验收报告

## 1. 验收结论

Task 5.4-B 已将待审批请求的列表、轮询推送、批准和拒绝全部绑定到 `approval_user_id`。多用户模式下，服务端不再返回全局审批集合供前端自行过滤；非指定审批用户无法发现、批准或拒绝其他用户的审批请求，管理员也不会因为平台角色自动获得代替其他用户审批的权限。

## 2. 实现内容

### 2.1 审批记录显式审批人

- `PendingApproval` 增加 `approval_user_id`，表示唯一可查看和决定审批的平台用户。
- Console 和已绑定个人频道默认将可信运行用户写入 `approval_user_id`。
- 保留对既有内存审批记录的兼容读取：旧记录缺少该字段时，使用已存在的可信 `user_id` 作为回退。

### 2.2 统一服务端查询

- `ApprovalService.list_pending_for_user()` 统一处理审批用户和可选根会话过滤。
- `GET /approval/list` 只返回当前认证用户的审批。
- `GET /approval/list?session_id=...` 同时满足审批用户和根会话两个条件，不能通过指定其他会话越权查询。
- `/console/push-messages` 的 `pending_approvals` 在序列化前完成服务端用户过滤。

### 2.3 批准与拒绝门禁

- `/approval/approve` 和 `/approval/deny` 在会话所有权校验之前先校验 `approval_user_id`。
- 非指定审批用户统一得到 `404 Approval not found`，不会暴露审批是否存在。
- 校验失败不会从全局待审批集合移除记录，也不会解析对应 Future。
- 原有会话所有者写权限、根会话匹配和审批范围规则继续保留，形成“指定审批人 + 会话所有者 + 根会话”三重约束。

### 2.4 Legacy 兼容回归

- 单用户模式继续允许列出原有全局审批集合。
- 回归中发现并修复未知运行的停止接口退化：Legacy 模式恢复返回 `200 {"stopped": false}`；多用户模式仍对未知会话返回 `404`。

## 3. 自动化验证

### 3.1 新增隔离契约

- 用户 A 的审批列表不包含用户 B 的请求。
- 即使指定用户 B 的 `session_id`，用户 A 仍得到空审批列表。
- Console 全局轮询只返回当前用户审批。
- 用户 B 不能批准用户 A 的请求。
- 用户 B 不能拒绝用户 A 的请求。
- 审批创建时将可信运行用户写入 `approval_user_id`。

### 3.2 受影响回归

```text
77 passed
```

覆盖范围：

- 实时流与审批隔离契约。
- ApprovalService 生命周期、GC、Driver gate 和 scope。
- 共享会话审批写保护。
- Runtime `/approval` 控制命令。
- Governance tool adapter。
- Approval 与 Console HTTP 集成契约。

## 4. 页面验收方法

服务更新后可按以下步骤验收：

1. 用户 A 发起一个需要人工批准的工具调用，保持审批卡片未处理。
2. 用户 A 的对话页、收件箱角标或系统通知中应出现该审批。
3. 使用另一浏览器登录用户 B；用户 B 的审批列表、收件箱角标和系统通知中均不应出现用户 A 的审批。
4. 用户 B 即使取得用户 A 的 `request_id` 并直接调用批准或拒绝接口，也只能得到 `404`。
5. 回到用户 A，原审批仍存在，可以正常批准或拒绝，智能体随后继续或终止工具执行。
