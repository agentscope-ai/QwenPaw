# Task 4.4-A 运行配置并发保护验收报告

## 1. 验收结论

Task 4.4-A 已完成前后端实现和真实页面验证，当前停在用户确认点。

- 运行配置页面读取当前 `config_version`。
- 保存时通过 `If-Match` 提交用户实际读取到的版本。
- 另一窗口已经保存后，旧窗口再次保存会收到 `409 config_version_conflict`，不会覆盖新配置。
- 前端显示“配置已被其他窗口修改”弹窗，并提供“重新加载”入口。
- 相同内容重复保存保持当前版本，不创建重复修订，也不触发内容哈希唯一约束。
- `agent.json` 仍是运行配置内容源；PostgreSQL 只保存版本、结构化快照和内容哈希，没有搬移 workspace Markdown。

## 2. 可见验收过程

验收实例：`http://127.0.0.1:18089`，管理员账号操作默认智能体。

1. 两个独立浏览器会话同时打开“运行配置”，初始 Shell 超时均为 `60`。
2. 会话 A 改为 `61` 并保存，`PUT /api/workspace/running-config` 返回 `200`。
3. 会话 B 基于旧版本改为 `62` 并保存，页面显示版本冲突弹窗。
4. 点击“重新加载”后，会话 B 显示会话 A 已保存的 `61`，证明旧值没有覆盖新值。
5. 验收结束后将 Shell 超时恢复为原值 `60`，恢复请求返回 `200`。

## 3. 后端实现

- 新增 PostgreSQL 配置修订仓储，使用行锁校验预期版本并生成稳定 SHA-256 内容哈希。
- `GET /api/workspace/running-config` 返回 `ETag` 和 `X-Config-Version`。
- 新增 `GET /api/workspace/running-config/version`。
- 多用户模式下保存必须携带 `If-Match`；缺失返回 `428`，版本过期返回 `409`。
- 单用户旧模式不强制 `If-Match`，避免侵入原有调用方式。
