# 当前技术与数据架构

## 1. 技术栈

### 后端

- Python 3.11–3.13。
- FastAPI/Starlette Web 服务，Uvicorn 运行。
- AgentScope 2.0.4.post1 作为 Agent 运行框架。
- APScheduler、多个渠道 SDK、Playwright、SQLite 和本地文件系统。
- 配置与业务状态主要通过 Pydantic 模型、JSON/YAML 和目录结构持久化。

### 前端

- React 18、TypeScript 5.8、Vite 6。
- Ant Design 5、Zustand、React Router、i18next。
- AgentScope Chat SDK、Monaco 编辑器和插件模块注册系统。

审计基线当时没有 PostgreSQL ORM、迁移框架或数据库驱动；Task 1.1 已旁路加入 SQLAlchemy 2.x async、asyncpg 和 Alembic，默认 Legacy 数据路径仍保持不变。

## 2. Web 请求结构

FastAPI 将主要路由挂载在 `/api` 下，同时提供全局接口和 Agent 范围接口：

```text
浏览器
  -> React API 模块
  -> /api 全局路由
       /auth /agents /models /envs /token-usage /backups ...
  -> /api/agents/{agentId} Agent 范围路由
       /chats /config /cron /mcp /skills /tools /workspace /console ...
  -> 本地配置、workspace、运行时服务和外部渠道/模型
```

前端 API 客户端依据当前 Agent 拼接 Agent 范围请求。部分接口仍保留全局路径，当前安全假设是“同一部署实例由同一位操作者控制”，而不是“每个请求属于不同登录用户”。

## 3. 当前认证模型

`src/qwenpaw/app/auth.py` 的设计特征：

- `auth.json` 位于 `SECRET_DIR`。
- 单一 `username`、密码盐和密码哈希。
- 自定义 HMAC 签名 Token，载荷包含用户名、过期时间和 JTI。
- 全局 Token 撤销列表，以及轮换单一 JWT 密钥来撤销所有会话。
- `AuthMiddleware` 验证 Token 后只把用户名字符串写入 `request.state.user`。
- 本机回环地址可根据安全配置跳过认证。
- 登录具备用户/IP 速率限制和可信代理解析。

缺失能力：稳定用户 ID、多个账户、角色、权限、用户状态、密码重置、会话设备、MFA、组织/租户、资源归属和数据行级隔离。

## 4. 当前持久化布局

默认工作目录为 `~/.qwenpaw`，密钥目录默认与其相邻。当前运行环境观察到：

```text
~/.qwenpaw/
  config.json              全局配置
  settings.json            全局设置
  inbox_events.json        收件箱事件
  token_usage.json         Token 用量
  skill_pool/              全局技能池
  plugins/                 插件
  runtime/                 运行时状态
  workspaces/
    default/
    <agent-id>/
      agent.json           Agent 配置
      chats.json           对话索引/元数据
      jobs.json            定时任务
      skill.json           Agent 技能关联
      sessions/            会话 JSON
      history.db           历史/运行数据 SQLite
      memory/              记忆文件
      skills/              Agent 技能内容
      checkpoints/         检查点
      resource/ media/ ... 其他 Agent 资源
```

此外还有：

- `~/.qwenpaw.backups`：备份。
- `SECRET_DIR/auth.json`：单账户认证数据。
- 渠道和模型密钥：配置/凭据存储及系统 Keyring。
- 安全审计：SQLite。
- 调试日志、浏览器状态、插件和本地模型目录。

## 5. 数据范围现状

| 数据类别 | 当前范围 | 当前隔离键 | 多用户风险 |
|---|---|---|---|
| 全局模型/提供商 | 部署实例 | 无用户键 | 所有登录者可能读取或修改密钥与模型 |
| Agent | 部署实例 | `agentId` | Agent 不属于任何用户，无法安全授权 |
| Chat/Session | Agent/渠道 | `agentId`、chat/session ID、部分 `user_id` | `user_id` 多为渠道或会话身份，不是 Web 主体 |
| 技能池 | 部署实例 | 技能名 | 私有/共享/管理员发布边界缺失 |
| Agent 技能 | Agent | `agentId`、技能名 | 没有用户所有权或共享授权 |
| 工具/MCP/频道 | Agent 或全局 | `agentId`、配置键 | 包含敏感凭据，普通用户不可直接共享管理权限 |
| 环境变量/安全/备份 | 部署实例 | 无用户键 | 必须是管理员能力 |
| 用量/统计/审计 | 部署实例或 Agent | 日期、模型、Agent | 缺少用户维度和管理员/个人视图 |
| workspace 文件 | Agent 文件系统 | 路径、`agentId` | 路径授权与所有权必须在服务端强制执行 |

## 6. 现有安全机制与多用户授权的边界

项目已有 Tool Guard、File Guard、Skill Scanner、沙箱、渠道访问控制、MCP principal 策略和审批流。这些能力保护的是 Agent 执行和外部渠道访问，不能直接替代 Web 管理面的 RBAC。

后续设计可以复用其“策略判定、审计、显式主体”思想，但必须新增统一的 Web Principal、资源所有权和服务端授权层，不能把渠道 `user_id` 或工具 permission 当成登录用户角色。

## 8. Task 1.1 PostgreSQL 旁路连接层

Task 1.1 只增加连接基础设施，不创建表、不迁移数据，也不连接遗留 `qwenpaw-pg`：

- `QWENPAW_MULTI_USER_ENABLED=false` 且未配置 DSN：保持 `legacy`。
- `QWENPAW_MULTI_USER_ENABLED=true`：默认要求 `postgres`，缺少 `QWENPAW_DATABASE_URL` 时在旧数据迁移前终止启动。
- `QWENPAW_STORAGE_MODE` 只接受 `legacy` 或 `postgres`。
- `postgresql://` DSN 在内部规范化为 `postgresql+asyncpg://`，密码不会进入设置对象的 `repr`、健康状态或 API 响应。
- SQLAlchemy async engine 使用连接预检、有限连接池和单任务单 `AsyncSession`；`database_session()` 负责事务提交、异常回滚和会话关闭。
- `/api/system/storage-status` 只返回 `legacy`、`disconnected` 或 `ready` 以及脱敏状态字段。

Task 1.2 已建立新的 Alembic Schema 定义并在临时 Schema 中完成验证；Task 1.4
起，状态接口在 PostgreSQL 连通时只读查询目标 Schema 的版本，在 Legacy 或
断连状态下仍返回 `null`。这不表示正式业务 Schema 已部署或业务已切换。

## 9. Task 1.3 Repository 选择边界

Task 1.3 增加 `StorageMode` 和泛型 `RepositoryProvider`，但没有创建任何
PostgreSQL 业务 Repository，也没有修改现有 Chat、Cron、Agent 或配置模块的
Repository 注入：

- 默认环境直接返回调用方提供的 Legacy Repository，不连接 PostgreSQL。
- PostgreSQL 模式先只读检查目标 Schema 的 `alembic_version`。
- 缺少版本表返回 `schema_not_initialized`。
- 版本不是 `0003_governance_operations` 返回
  `schema_revision_incomplete`。
- 即使 Schema 已到 head，调用方没有显式提供 PostgreSQL Repository 时仍返回
  `postgres_repository_unavailable`。
- 选择器只返回一个 Repository，不执行双读、双写或后台同步。

因此当前所有正式业务仍使用原文件、目录和 SQLite 路径；PostgreSQL 仍只是
经过验证但尚未接管业务事实来源的旁路基础设施。

## 10. Task 1.4 只读系统状态面

Task 1.4 将 `/api/system/storage-status` 从健康探针路由拆分到独立的
`system_status` 路由，并新增 `/system-status` 前端页面：

- Legacy 模式不读取 PostgreSQL 或迁移版本，明确显示当前业务仍使用原存储。
- PostgreSQL 连通时只读查询 Alembic revision，并分别返回当前版本和期望版本。
- `active_repository` 与 `storage_mode` 分开呈现，避免把“已配置 PostgreSQL”
  误报为“业务已切换 PostgreSQL”。当前 `active_repository` 仍为 `legacy`。
- 项目尚无迁移锁执行器，接口如实返回 `not_applicable`、`not_configured`
  或 `unknown`，本任务不创建锁表、不获取锁，也不修改数据库。
- API 响应模型不包含 DSN、密码、Secret、数据库地址或连接目标。
- 页面只提供刷新操作，不提供迁移、重建、删除、DROP 或存储切换入口。

身份与管理员 capability 尚未进入实施阶段，因此当前只完成管理设置入口的
路由注册；真正的管理员服务端授权必须在后续身份与授权阶段接入。

## 11. Task 2.1 用户与密码领域层

Task 2.1 新增独立 `qwenpaw.identity` 领域层，但尚未接入 HTTP 登录、令牌、
中间件或前端账户菜单：

- `UserRecord` 只暴露稳定 UUID、用户名、平台角色和状态，不包含密码哈希。
- 第一阶段平台角色只有 `admin` 与 `member`，自助注册默认关闭。
- 新密码使用 `pwdlib` 推荐的 Argon2id 自适应哈希；算法参数变化时，成功登录
  会通过 `verify_and_update()` 返回新哈希并写回 Repository。
- 旧 `auth.json` 只提取单用户的 username、salted SHA-256 hash 和 salt，
  不迁移 JWT Secret、旧令牌或撤销列表。
- 旧 SHA-256 凭据仅以内部迁移格式临时保存在 `password_hash`，第一次成功登录
  后立即升级为 Argon2id；错误密码不会触发升级。
- 首用户角色判断和旧管理员“仅空库迁移”判断均在 PostgreSQL advisory
  transaction lock 内重新确认，避免并发请求创建两个首管理员。
- SQL 全部使用显式 Schema 限定表名；用户名唯一冲突映射为稳定领域异常，
  其他完整性错误不会被错误吞并。

当前还没有正式身份 Runtime，因此本任务没有自动读取现有 `auth.json`，没有
向正式数据库写入用户，也没有替换旧单用户认证入口。这些接线必须按后续任务
逐步完成，避免侵入原有登录功能。
