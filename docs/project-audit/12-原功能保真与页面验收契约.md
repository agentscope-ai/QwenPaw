# 原功能保真与页面验收契约

## 1. 核心原则

多用户改造只允许增加：

- 登录用户身份。
- 资源归属。
- 角色和权限。
- 用户间隔离。
- 审核、发布和审计。

不得以“方便迁移到 PostgreSQL”或“简化多用户实现”为理由删除、合并或降级原有产品能力。任何页面在新版本中都必须同时满足：

1. 原有功能等价。
2. 新权限正确。
3. 数据隔离正确。
4. 错误、并发和恢复行为可预测。

## 2. 浏览器实况核验

2026-08-20 通过当前运行中的 QwenPaw v2.1.0 页面核验了真实聊天会话。当前一轮对话不是单纯的用户文本和助手文本，而是按执行顺序呈现：

1. 用户请求。
2. “执行 Skill”卡片。
3. 可折叠的 Thinking/Reasoning。
4. 命令或其他工具执行卡片，展示具体动作。
5. 工具执行状态和输出。
6. 图片查看等多媒体工具结果。
7. 文件发送卡片。
8. 最终 Markdown 回答。
9. 复制按钮和消息时间。

同一页面还包含：

- 当前 Agent 和 Agent 状态。
- 当前模型展示/切换。
- 新建会话和历史会话。
- 工作区入口。
- 语音输入和附件上传。
- Loop 模式选择。
- 本轮 Token 与上下文用量。
- 当前会话项目目录。
- 工具执行安全级别。
- 停止、审批、重连和快捷指令语义。

这些都属于原功能，不得在多用户版本中被缩减成普通聊天列表。

## 3. 源码证明的对话消息类型

后端 `src/qwenpaw/schemas.py` 的流式信封包含：

- `message`
- `reasoning`
- `plugin_call`
- `plugin_call_output`
- `function_call`
- `function_call_output`
- `mcp_tool_call`
- `mcp_tool_call_output`
- `progress`
- `result`

内容块包含：

- text
- image
- audio
- video
- file
- data
- refusal

每个内容块还可能携带：

- 是否为增量。
- 内容索引。
- created/in-progress/completed/failed/cancelled 状态。
- 消息 ID。
- 工具调用 ID及扩展元数据。

前端 `HostBubbles.tsx` 进一步区分并渲染：

- 普通消息。
- Plugin/Tool/MCP 调用及输出。
- MCP 审批请求。
- Reasoning。
- Error。
- 图片、视频、文件和音频卡片。
- 插件对请求和响应卡片的 prepend/append/render 扩展。

因此目标数据模型必须保存可以重建上述顺序和关联关系的结构化数据，不能只保存最终 Markdown。

## 4. 对话数据保真模型

### 4.1 Conversation

保存会话身份、Agent、所有者、分享、标题、归档、固定、当前模型覆盖、项目目录和更新时间。

### 4.2 Run

每次用户提交产生一个 Run：

- 用户请求消息。
- 实际用户和外部渠道身份。
- Agent 和共享应用发布版本。
- 实际模型。
- 审批级别、Loop 模式和项目目录。
- created/running/completed/failed/cancelled 状态。
- 开始、完成和取消时间。

### 4.3 RunEvent

按 `run_id + sequence_no` 保存可重放事件：

- reasoning delta/complete。
- message delta/complete。
- skill/plugin/tool/MCP call created/running/completed/failed/cancelled。
- approval requested/approved/denied/timeout。
- progress。
- image/audio/video/file/data content。
- error 和最终 result。

客户端首次加载和断线重连都从同一种规范事件恢复 UI，不能让“实时观看”与“历史重放”呈现不同内容。

### 4.4 ToolCall

保存：

- 稳定调用 ID。
- 工具来源：builtin、plugin、skill、MCP、Harness；ACP 只兼容历史记录，不开放新调用。
- 工具名和可展示标题。
- 输入参数或安全引用。
- 状态和执行时长。
- 审批请求与决定。
- 输出内容块或外置内容引用。
- 错误、取消和后台执行状态。

敏感参数可以脱敏或进入受限字段，但不能因为审计脱敏而丢失当前授权用户恢复工具卡片所需的业务信息。

### 4.5 Message

Run 完成后可以形成便于分页和搜索的规范消息记录，但 Message 是展示索引，不得覆盖或破坏 RunEvent 的过程事实。消息内容使用有序内容块，而不是单一字符串。

## 5. 对话页禁止退化清单

多用户版本不得出现：

- 历史会话只显示最终回答，工具过程消失。
- 刷新后 Reasoning、工具状态、图片或文件卡片丢失。
- MCP/Plugin/Skill 调用统一显示成无法区分的纯文本。
- 工具调用和输出失去 `tool_call_id` 关联。
- 工具审批在其他用户窗口出现或被其他用户响应。
- 普通用户切换共享应用模型并影响其他用户。
- 切换用户后保留前一用户的会话、草稿、模型覆盖、项目目录或待审批状态。
- SSE 重连重复追加消息、丢事件或改变事件顺序。
- 大型工具输出直接塞入普通消息导致页面或数据库失控。

## 6. 全页面功能保真方法

每个菜单迁移前建立一份页面基线，至少包括：

- 路由和菜单入口。
- 初始加载状态、空状态和错误状态。
- 所有按钮、表单、抽屉、弹窗、标签和批量操作。
- API 请求和响应结构。
- 数据落点和运行时副作用。
- Agent 切换、用户切换和刷新行为。
- 可见权限、直接 API 权限和管理员代操作。

对交互复杂或源码语义不明确的页面，必须使用当前运行版本浏览器核验实际呈现。不能只凭组件名称或接口名称猜测产品行为。

## 7. 浏览器核验优先级

以下页面必须在设计和实施阶段做浏览器实况核验：

1. 聊天、工具执行、审批、重连和历史重放。
2. Agent 创建/编辑及默认模型差异。
3. 技能载入、冲突覆盖和技能池广播。
4. MCP OAuth、工具白名单和访问策略。
5. 文件上传、编辑、预览和 workspace 切换。
6. 定时任务运行、历史和收件箱跳转。
7. Checkpoint 预览、恢复和失败回滚。
8. 备份创建、导入冲突和恢复确认。
9. 插件/PawApp 安装、内嵌页面和卸载。
10. 所有因角色不同而变化的页面受限态。

## 8. 迁移任务门禁

每个具体实施任务必须提交以下证据后才能进入下一步：

1. 改造前功能清单和浏览器/源码证据。
2. 数据模型与原功能逐项映射。
3. 管理员、所有者、协作者、使用者、未授权用户测试。
4. 原功能回归测试。
5. 跨用户隔离测试。
6. 刷新、重连、并发、失败恢复测试。
7. 用户确认。

如果某个旧行为存在缺陷，应单独记录为缺陷并取得修复确认，不能在多用户改造中无声改变其产品语义。

## 9. 对总体架构的直接约束

- PostgreSQL 消息模型必须支持有序、多类型内容块。
- 必须保留 Run、RunEvent 和 ToolCall，而不能只建 conversations/messages。
- 附件和大型工具输出使用内容引用，但历史重放仍能恢复卡片。
- SSE 推送、持久化和历史读取共享统一事件 Schema。
- 用户/Agent/会话/Run/ToolCall/Approval 都必须有明确外键或领域关联。
- 共享应用运行事件记录实际用户和发布版本，不继承所有者身份。
- 前端现有 HostBubbles、ResponseTool、ResponseReasoning、多媒体卡片和插件扩展点应尽量复用，不重写为简化组件。

### 10.1 固定 Run fixture

1. `reasoning`
2. `assistant_delta`
3. `tool_start`
4. `approval_required`
5. `approval_decided`
6. `tool_output`
7. `skill`
8. `plugin`
9. `mcp`

11. `image`
12. `file`
13. `progress`
14. `error`

每个事件固定 `run_id`、`sequence_no`、`event_id`，并按事件需要固定 `message_id`、`tool_call_id` 和 `approval_id`。其中：

- `assistant_delta` 与 `final` 必须关联同一个 `message_id`。
- 工具开始、审批请求、审批决定和工具输出必须关联同一个 `tool_call_id`。
- 审批请求与审批决定必须关联同一个 `approval_id`。
- 规范事件类型与当前渲染载体分离；例如审批决定当前可通过审批状态或工具输出载体呈现，但不得丢失其规范事件语义和关联 ID。

## 11. Task 13.1 多用户全角色逐页验收契约（2026-09-09）

### 11.1 六类主体

最终验收必须使用彼此隔离的登录会话，并覆盖以下主体：

1. 管理员普通路径：按自身可访问 Agent 使用普通页面和 API，不隐式绕过成员关系。
2. 管理员代操作：只通过显式 `/api/admin/agents/{agentId}/config` 治理入口读取或修改目标 Agent，并保留审计请求 ID。
3. owner：创建、查看、编辑、成员管理、批量会话操作和删除均只作用于自己创建的临时 Agent。
4. collaborator：可以查看和编辑目标 Agent，但不能获得 owner 专属能力。
5. user：可以使用 Agent 和维护自己的运行数据，只能查看脱敏配置摘要，完整配置接口返回 403。
6. 未授权：撤销成员关系后，目标 Agent 的详情、会话和运行接口均返回 403；另以匿名上下文验证登录重定向。

角色流转使用一次验收创建的唯一 Agent：`task42-user` 为 owner，`task62-user-b` 依次成为 collaborator、user、未授权。不得改变已有 Agent 的成员关系或删除已有会话。

### 11.2 页面矩阵

管理员普通路径逐页覆盖全部内置静态路由：Chat、收件箱、应用、频道、会话、定时任务、心跳、文件、技能、工具、MCP、运行配置、智能体统计、检查点、智能体管理、Token 消耗，以及模型、用户、发布审核、技能池、环境、卸载策略、安全、系统状态、迁移预览、语音转写、调试、备份和插件管理。

owner 与 collaborator 覆盖全部普通和 Agent 作用域页面；user 覆盖可使用的工作页面及只读/受限配置态；未授权覆盖 Chat、文件、运行配置和会话受限态；匿名覆盖 Chat、智能体管理和用户管理的登录重定向。ACP 已在 Task 12.4 按产品决策退役，不再属于路由契约。

每个页面必须满足：

- 页面正文非空，且没有 `Something went wrong` 或 `ChunkLoadError` 致命错误。
- 登录态或重定向符合主体权限。
- 保存最终 URL、正文字符数和整页截图。
- 任一页面失败立即停止，报告状态记为 `failed`，并保留现场供定位。

### 11.3 关键功能和失败回滚

自动化脚本 `e2e/tests/test_multi_user_full_matrix.py` 以真实浏览器和 API 组合验证：

- Agent 列表、详情、创建、owner 编辑、collaborator 编辑和管理员显式代管编辑。
- 两个临时会话的批量归档、反归档和批量删除。
- 工作区文件上传、下载及同名冲突；冲突返回 409 后下载内容必须仍等于首次上传内容。
- Runtime Status SSE 首事件必须为 `connected`。
- owner、collaborator/user 的审批列表按登录用户过滤；不存在的审批请求安全返回 404。
- 成员角色从 collaborator 降为 user 后，完整 Agent 配置返回 403；撤销后 Agent 详情和会话列表返回 403。
- 最终删除必须走多用户软删除并返回 `soft_deleted=true`。

脚本为每个 API 请求生成唯一 `X-Request-ID`。数据库证据在清理前后分别记录 Agent owner、成员角色/撤销时间、会话 owner/status，以及关联的审计日志。报告和截图统一写入 `tmp/task-13-1-<run-id>/`，明文密码和访问令牌不得写入报告。

### 11.4 危险操作门禁

完整运行前必须获得用户对以下操作的明确确认：撤销本轮临时成员、批量删除本轮两个临时会话、软删除本轮临时 Agent。脚本只有在显式传入 `--allow-destructive-cleanup` 时才执行，且仅使用本轮唯一 ID；不删除既有 Agent、既有会话或用户，不修改数据库结构，不执行 Git 提交。
