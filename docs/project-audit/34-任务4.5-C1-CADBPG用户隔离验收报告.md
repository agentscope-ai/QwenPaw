# Task 4.5-C/1-C ADBPG 用户隔离验收报告

## 1. 本阶段目标

为 ADBPG 的每次私有记忆写入和检索绑定可信的登录用户、目标 Agent 与运行标识，禁止使用 `shared` 或空身份作为普通用户的回退值。

## 2. 根因

原 `ADBPGMemoryManager` 在初始化时预设：

- `_effective_agent_id = "shared"`
- `_effective_user_id = "shared"`
- `_effective_run_id = "shared"`

随后 `add_memory` 和 `search_memory` 直接使用这些字段。原 `ADBPGMemoryClient` 还会忽略空身份字段，导致请求可能以空过滤条件访问 ADBPG，存在跨用户数据混入风险。

## 3. 实现内容

### 3.1 请求身份绑定

在 `ADBPGMemoryManager` 增加 `for_request(request_context)`，由现有运行时构建器在每次请求构造 `ScopedADBPGMemoryManagerView`。视图固定：

- `user_id`：服务端认证后的登录用户
- `agent_id`：当前 Agent，必须与 manager 自身一致
- `run_id`：请求提供的运行 ID；缺失时使用当前 `session_id`

搜索工具、自动检索、自动记忆写入和摘要写入均通过该视图传递身份，不接受客户端在工具调用中覆盖身份。

### 3.2 客户端 payload 与校验

ADBPG REST add/search 请求现在都包含：

```json
{
  "agent_id": "agent-a",
  "user_id": "user-a",
  "run_id": "run-a"
}
```

search 的权限过滤仍只使用 `agent_id + user_id`，`run_id` 作为顶层审计字段，不限制同一用户跨会话检索长期记忆。

客户端和 manager 均拒绝：

- 缺少用户身份
- 缺少 Agent 身份
- Agent 与当前 manager 不一致
- 缺少运行身份
- 任一身份值为 `shared`

旧 ADBPG `shared` 数据不会因空过滤条件或 shared 回退进入普通用户私有搜索。旧数据未被自动归属或删除，后续如需转为公共记忆，应另设管理员审核迁移流程。

### 3.3 其他保护

同一条消息的去重键由 `user_id + message_id` 组成，避免两个用户恰好使用相同消息 ID 时互相抑制写入。

使用隔离 HTTP mock，未连接生产 ADBPG，也未记录真实密钥。


结果：**8 passed**。

```powershell
& ".venv/Scripts/python.exe" -m pytest `
  "tests/unit/agents/memory" `
  "tests/isolation/test_memory_scope_isolation.py" `
  "tests/isolation/test_memory_runtime_user_isolation.py" `
  "tests/isolation/test_adbpg_memory_scope.py" -q
```

结果：**123 passed**。

覆盖证据：

1. user-a 和 user-b 的 add/search payload 各自携带自己的 `user_id + agent_id + run_id`。
2. 缺少用户、Agent、run_id 或使用 shared 身份时直接抛出 `MemoryScopeDenied`。
3. 模拟服务同时返回旧 shared 记录和 user-a 记录时，user-a 私有搜索只返回 user-a 记录。
4. HTTP mock 实际检查 add/search JSON，而不是只断言 mock 调用次数。
