## 2. 前端结果

### 生产构建

`npm run build:prod` 成功。存在以下非阻断风险：

- `utils-vendor` 与 `ui-vendor` 循环 chunk 警告。
- 多个模块同时被动态和静态导入。
- 主包约 6.88 MB、UI vendor 约 8.52 MB，显著超过 1 MB 警告阈值。

### 测试

Task 0.4 修复后结果：

```text
228 个测试文件通过
1747 个测试通过
```

原失败用例是 `replaySdkIntegration.test.ts` 的真实断线重连回放夹具。

根因已经定位：

- 真实夹具使用 `\r\n\r\n` 分隔 SSE 事件。
- `wrapReplayFastForward.splitEvents()` 只按 `\n\n` 分割。
- 8 个 `data:` 事件被读取为一个载荷，断言期望大于 3 个，实际为 1 个。

修复：事件分隔由仅识别 `\n\n` 改为同时识别 LF/CRLF，并新增 CRLF 回归用例。真实 SDK 集成测试 3 项通过，轻量解析测试 8 项通过。该变更不改变消息、工具过程或回放结构，只修复分隔符兼容性。

## 4. 浏览器运行时结论

- 全部内置菜单路由均可进入。
- 聊天、收件箱、频道、会话、定时任务、心跳、技能、工具、MCP、ACP、Agent 管理、模型、安全、统计、备份、调试和插件等页面均呈现预期核心控件。

- 控制台偶发 `[moduleRegistry] Module not found`，根因是后台动态模块注册采用 fire-and-forget，而路由懒加载会先查询 registry。当前页面仍回退到原模块并正常工作，因此这是时序噪声和插件可观测性问题，不是页面缺失。

## 5. 当前关键风险清单

### P0：多用户设计前必须约束

- 当前认证是单账户，没有稳定 Web 用户 ID 和角色。
- 所有 Agent 和全局资源默认属于部署实例，无法实施可靠授权。
- 全局模型密钥、环境变量、频道、备份、安全配置等敏感能力没有管理员边界。
- Chat、文件、技能、MCP 等 API 需要统一服务端资源授权，不能仅靠前端隐藏。
- 旧文件数据迁移到 PostgreSQL 时必须保持 Agent workspace 和文件类资源的语义。

### P1：现有核心回归

- CRLF SSE 重连解析失败已在 Task 0.4 修复并保留回归测试。
- unit/contract 当前有 8 个失败。
- 测试环境变量会跨用例污染，降低测试结论可信度。
- 前端 bundle 过大，增加加载与插件预热时序风险。

### P2：可维护性与可观测性

- API 同时存在全局和 Agent 范围形式，后续容易形成授权旁路。
- 多种 `user_id` 语义并存，命名不足以区分 Web 用户与渠道用户。
- 本地文件、SQLite、Keyring 和运行时状态分散，缺少统一数据目录和归属文档。
- 动态模块注册警告会掩盖真正的插件加载错误。

## 6. 第一阶段验收建议

用户确认本项目现状文档时，应重点核对：

1. 页面和功能目录是否遗漏实际业务入口。
2. 哪些全局设置必须仅管理员可用。
3. 普通用户应拥有独立 Agent，还是可以共享管理员创建的 Agent。
4. 当前本地数据是否全部需要迁移，哪些文件必须继续保留在文件系统/对象存储。
5. 历史对话中还有哪些业务规则必须纳入新方案。

上述基线确认后，再进入目标架构候选方案比较和逐段设计确认。
