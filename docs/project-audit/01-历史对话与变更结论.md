# 历史对话与变更结论

## 1. 对话一：检查多用户架构实现

该对话最初围绕一批未提交的多用户改造进行审计和修复。对话中出现过以下设计或实现方向：

- 引入 PostgreSQL、Alembic、数据库角色和 RLS。
- 将本地 QwenPaw 与 Docker PostgreSQL 服务连接。
- 区分管理员与普通成员，增加用户、角色、能力、资源归属及管理接口。
- 尝试为 Agent、会话、技能、工具、MCP、配置等资源增加用户范围或访问控制。
- 增加用户账户菜单、身份资料、头像、频道身份关联等概念。
- 反复修复菜单隐藏、路由跳转、Legacy API、技能池语义、斜杠命令、Agent 绑定、聊天历史及数据迁移问题。

对话中曾多次报告“大量测试通过”或“主要功能完成”，但同时也持续暴露以下结构性问题：

- 多用户入口不可见，普通菜单被错误隐藏。
- 多个菜单路由被重定向到聊天页。
- 新旧 API 并存，前端仍调用缺少租户约束的 Legacy API。
- Agent 技能与全局技能池的边界被混淆。
- `/` 技能菜单暴露内部资源键。
- Default Agent、设计器与用户归属绑定不一致。
- 聊天、历史、会话和数据访问出现回归。

因此，该对话能提供需求线索、失败模式和设计教训，但不能作为“已完成实现”的可信证明。

## 2. 对话二：完善侧边栏用户账户菜单

该对话先设计并实现了侧边栏账户菜单，讨论过：

- `display_name`、头像和对象存储。
- 账户安全、频道身份等标签页。
- 登录后用户资料展示和账户操作。
- 与第一段对话中的多用户实现继续整合并修复功能。

随后用户要求回到稳定代码。对话最终在用户明确回复“确认恢复”后执行了：

```text
git reset --hard HEAD
git clean -fd
```

该操作删除了当时 182 个已跟踪文件的未提交修改和 148 个未跟踪路径，其中包括多用户代码、数据库迁移、设计文档和参考快照。恢复后的版本为当时本地 Git HEAD（对话中为 `ab915d6` / v2.0.1），之后项目又合并到了当前 v2.1.0 基线。

## 3. 当前仓库与历史对话的关系

当前仓库状态：

- 分支：`dev-my-fix`
- HEAD：`4726195905e0f96a6529b77dfbf0210d01f127ee`
- 工作树在审计开始时干净。
- `pyproject.toml` 无 PostgreSQL、SQLAlchemy、asyncpg、Alembic 依赖。
- 当前认证源码明确声明单用户设计。
- Git 不跟踪 `src/qwenpaw/tenancy`、`src/qwenpaw/identity`、`src/qwenpaw/object_store` 的任何源码。

这意味着：

1. 历史多用户实现已不可直接恢复为可审查源码。
2. `.pyc` 仅说明本机曾运行过相关代码，不具备完整性、可维护性或可信来源。
3. 新方案必须从当前 v2.1.0 的真实架构出发，吸收历史教训，而不是继续修补已删除实现。
4. 后续每个阶段必须形成可复核的文档、测试与用户确认点，避免再次出现“大范围改造后才发现原功能丢失”。

## 4. 从历史失败中提炼的强制约束

- 原有菜单、路由和交互必须逐项建立回归清单，不能只验证登录和管理后台。
- 新接口必须明确替代关系，禁止长期保留不受租户约束的旁路 Legacy API。
- “Web 用户”“渠道外部用户”“Agent”“会话”“资源所有者”必须使用不同领域概念。
- 全局资源、用户私有资源、Agent 资源和共享资源必须分别定义归属与授权。
- 数据迁移必须可预演、可校验、可回滚；迁移完成前旧数据不能被破坏。
- 后端授权是事实来源；前端菜单隐藏只能改善体验，不能代替权限校验。
- 管理员能力必须采用显式权限矩阵，不能简单地把所有现有设置页面全部开放或全部关闭。
- 每个阶段先完成设计和验收证据，经用户确认后再进入下一阶段。
