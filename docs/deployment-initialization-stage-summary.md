# 部署初始化阶段优化总结

日期：2026-09-17

## 阶段目标

修复“PostgreSQL 运行在 Docker、应用运行在 Windows/Linux 宿主机”部署过程中暴露的初始化缺口，将临时排障结论落实到代码、部署手册和回归测试中。重点覆盖环境准备、配置生成、数据库迁移、首次管理员注册和首次会话创建。

## 问题与原因

1. **Python 命令不可用**：原手册依赖 Windows 的 `py` 启动器，而实际安装的是 Anaconda；全局 `python` 又指向 WindowsApps 占位入口。虚拟环境未创建成功，后续命令仍继续执行。
2. **数据库认证失败**：本地服务模板使用 `qwenpaw` 用户和数据库，而数据库容器配置使用 `weldon` / `weldonagent`，需要手工同步的字段过多。
3. **schema 缺失**：Windows 检出的 shell 脚本使用 CRLF，容器首次初始化脚本执行失败；数据库仍能响应健康检查，但 Alembic 建表时找不到目标 schema。
4. **切换声明缺失**：新实例配置中的三个 PostgreSQL 领域切换声明为空，数据库迁移完成后仍被启动检查拒绝。
5. **首次会话不存在**：服务首次启动时尚无管理员，智能体治理元数据登记被跳过；注册管理员后没有再次登记，创建会话触发智能体外键约束失败。
6. **残留无效会话**：会话先写本地列表再登记数据库，数据库操作失败后，本地仍保留无法正常使用的会话。
7. **错误提示不够具体**：服务只显示 `InvalidPasswordError`、`DBAPIError` 等概括错误，难以区分认证、权限和初始化问题。

## 已实现的优化

### 统一生成宿主机配置

- `service init` 新增 `--env-file`，调用 Docker Compose 自身解析配置，避免自行实现一套不同的环境变量插值规则。
- 根据实际解析结果生成用户名、数据库名、密码连接串、schema、映射端口和外置工作/密钥/备份/日志/运行状态目录。
- 使用 URL 构建器编码密码，并还原 Compose 导出时对字面量 `$` 的二次转义。
- 新增 `--fresh`，由部署者明确声明全新实例，无旧业务数据待迁移，然后填入全部领域切换声明。
- 不带 `--fresh` 时保留原有迁移核验门槛；不覆盖已有配置，解析失败不落盘，也不打印包含凭据的 Compose 输出。

推荐的全新 Windows 部署配置生成命令：

```powershell
& ".venv/Scripts/python.exe" -m qwenpaw service --config "deploy/service.local.json" init --env-file "deploy/.env" --fresh
```

### 完善数据库迁移前置条件

- `.gitattributes` 为 `.sh` 文件指定 LF，修正初始化脚本的本地换行格式。
- 在线迁移幂等执行 `CREATE SCHEMA IF NOT EXISTS`，不再完全依赖容器首次启动钩子。
- 保留非空且无版本记录 schema 的拒绝逻辑，防止误把已有业务数据当作空库初始化。
- 普通启动仍不自动升级数据库，升级继续要求显式执行 `database-upgrade --yes`。

### 补全首次管理员初始化

- 首次注册管理员后，在签发登录会话之前，完成文件智能体向数据库治理元数据的登记和模型模式同步。
- 管理员登录时也执行幂等补登记，使首次注册过程中未完成的步骤可以重试。
- 初始化失败返回明确的 `admin_initialization_incomplete` 提示，不签发本次登录凭据；已创建的管理员无需重复注册，可在数据库恢复后重新登录。
- 新部署注册管理员后即可创建 `default` 会话，不再依赖额外重启。

### 调整会话持久化顺序

- 显式创建和自动创建会话，都先完成数据库登记回调，再更新本地会话列表。
- 数据库登记失败时，不再留下本地可见但数据库不存在的会话。
- 本改动不宣称文件与数据库具备跨存储事务；数据库成功后若本地文件写入失败，仍应依据日志排查文件权限或磁盘问题。

### 提升诊断可操作性

- 识别嵌套驱动异常中的 SQLSTATE，分别提示认证失败、数据库不存在、schema 不存在和权限不足。
- 对领域切换声明、数据库迁移版本及非空无版本 schema 提供处理方向。
- 使用固定的允许列表提示，不输出驱动原始异常、SQL 参数或密码；异常链循环也不会导致无限遍历。

## 部署文档调整

更新 `docs/database-container-host-service.md`：

- 使用已确认可用的 `python -m venv`，解释 `py` 与 `python` 参数区别及 WindowsApps/Anaconda 排查方式。
- 强调在项目根目录执行、逐条确认成功，不复制 PowerShell 提示符。
- 使用新配置生成命令，说明 `--fresh` 的适用范围和已有数据迁移的区别。
- 解释特殊字符密码、修改 `.env` 不会修改已有数据库密码，以及 `healthy` 不等于应用初始化完成。
- 移除首次注册后必须重启的旧版临时措施，改为注册自动完成登记及失败重试说明。
- 明确模型未配置、浏览器 INFO 提示和技能授权提示的含义，不把基础就绪等同于模型调用成功。
- 日常运维使用虚拟环境中的解释器；说明 Windows 任务计划脚本默认是用户登录后启动，而非无人登录时的开机启动。
- 补充旧实例更新顺序和常见错误排查表。

## 验证与范围

相关回归集合包含 86 项测试，覆盖：

- 配置生成、凭据编码、真实 Compose 特殊字符解析、不覆盖已有配置及错误输出脱敏；
- 缺少 schema 的首次升级、重复升级、版本迁移与非空无版本 schema 保护；
- 初始化应用、启动服务、注册管理员后不重启直接创建数据库会话；
- 管理员初始化失败后的登录重试；
- 数据库登记失败时不产生本地残留会话；
- Windows 检出脚本在 Linux PostgreSQL 容器内执行；
- 原有领域切换、智能体登记、模型模式同步和会话管理行为。

数据库测试使用独立 PostgreSQL 容器、专用测试数据库和隔离 schema。没有在当前业务数据库中运行测试迁移。完整服务流程在 Windows 宿主机验证，shell 初始化脚本在 Linux 容器中验证；未声称完成独立 Linux 宿主机的全套部署验收，也未调用付费模型验证生成效果。

当前实例保留既有配置和业务数据，重启服务即可加载本阶段代码。新服务器应使用更新后的部署手册；已有实例不得以 `--fresh` 代替数据迁移。
